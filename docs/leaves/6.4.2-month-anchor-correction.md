# 6.4.2 month-anchor correction

Survey date: 2026-09-10

## Scope

Fix the pure upcoming projector when a monthly or annual stream originates on a
day that a later month does not contain. Preserve the original day-of-month
anchor across each projection step while clamping only the target occurrence.
Keep the existing month horizon, one-missed-occurrence stale rule, overdue
semantics, weekly/biweekly arithmetic, annual cadence, currency grouping, and
clock-free API unchanged.

No database, API, browser, recurring detection, matching, or provider behavior
changes are in scope. The stream's `lastDate` remains the observed transaction;
the projector does not persist a synthetic date.

## Regression evidence

The shipped code calls `nextExpectedDate` repeatedly with the previous projected
date. For a monthly stream whose last observed date is `2026-01-31`, that gives:

```text
2026-01-31 -> 2026-02-28 -> 2026-03-28
```

At reference `2026-03-29`, the projector sees two missed dates and incorrectly
marks the stream stale. The intended sequence is:

```text
2026-01-31 -> 2026-02-28 -> 2026-03-31
```

The focused test therefore requires an overdue February 28 occurrence, a March
31 occurrence, a two-charge total, and no stale stream. It failed against the
original projector and passes with the correction.

## Chosen design

`nextExpectedDate` accepts an optional stable `anchorDay`. Monthly and annual
projection passes capture the day from the stream's observed `lastDate` once,
then pass it through every step. Each target year/month computes its real month
length and clamps `anchorDay` to that month. Weekly and biweekly paths ignore the
optional value and continue adding exact seven/fourteen-day intervals.

This is intentionally a projection-only correction. A February clamp is not
rewritten into the stream or detector output, so the next real transaction can
still advance the observed `lastDate`. The existing stale logic remains exact:
one expected date before the reference is listed overdue; when the second
expected date is also before the reference, the stream is stale. A date equal to
the reference remains due rather than overdue.

## Rejected alternatives

- Treat every month as 30 days: this breaks calendar-month semantics and annual
  dates.
- Mutate `stream.lastDate` or persist the clamped February date: projections are
  pure and `lastDate` is observed ledger data, not forecast state.
- Skip February for a January 31 anchor: this hides an expected bill and
  contradicts the existing clamp behavior and overdue contract.
- Change recurring detection or add a last-day-of-month cadence: this is a
  projection bug, and detection's cadence windows and persisted stream identity
  are outside 6.4.2.
- Special-case only January 31: the invariant is the original day anchor, which
  also covers 29/30 and leap-year annual dates without date-specific branches.

## Primary sources and prior art

The existing 6.4.1 and 6.4.2 surveys were re-read, and the following primary
specifications and implementation documents were opened for this correction:

| # | Source | Decision or boundary |
|---:|---|---|
| 1 | [6.4.1 recurring prior art](6.4.1-prior-art.md) | The stream contract exposes an observed last date and derives the next date; do not persist forecast state. |
| 2 | [6.4.2 upcoming prior art](6.4.2-prior-art.md) | The view projects every occurrence through the reference month's end and allows one overdue occurrence before staleness. |
| 3 | [iCalendar RFC 5545](https://www.rfc-editor.org/rfc/rfc5545.html) | Calendar recurrence is expressed in calendar fields and recurrence rules, not fixed 30-day durations; invalid date handling must be an explicit product choice. |
| 4 | [TC39 Temporal PlainDate](https://tc39.es/proposal-temporal/docs/plaindate.html) | Calendar date arithmetic distinguishes constrained month/year arithmetic from fixed duration arithmetic; retain a stable day constraint. |
| 5 | [ECMAScript date specification](https://tc39.es/ecma262/multipage/numbers-and-dates.html) | Native date arithmetic normalizes calendar fields; use UTC month lengths explicitly to keep this pure code timezone-free. |
| 6 | [.NET `DateTime.AddMonths`](https://learn.microsoft.com/en-us/dotnet/api/system.datetime.addmonths) | Each call clamps an out-of-range day to the target month's last day; repeated calls can drift from an original 31st, so the caller must retain the anchor as this fix does. |
| 7 | [Java `LocalDate.plusMonths`](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/time/LocalDate.html#plusMonths(long)) | Java's calendar API documents month adjustment with the resulting day constrained to the last valid day; the original anchor must be retained by the caller for later months. |
| 8 | [Python dateutil `relativedelta`](https://dateutil.readthedocs.io/en/stable/relativedelta.html) | Relative month arithmetic applies calendar components and never crosses the target month's boundary; it is prior art for explicit month semantics. |
| 9 | [date-fns `addMonths`](https://date-fns.org/docs/addMonths) | The JavaScript date library provides month-aware rather than 30-day arithmetic; the implementation remains dependency-free because the repo already has a UTC helper. |
| 10 | [PostgreSQL date/time functions](https://www.postgresql.org/docs/current/functions-datetime.html) | Database date functions distinguish calendar months from intervals; the projector stays in pure TypeScript and does not move this calculation into SQL. |
| 11 | [Google Calendar Events API](https://developers.google.com/workspace/calendar/api/v3/reference/events) | Calendar events carry recurrence rules and instances separately; this supports deriving occurrences for a requested window rather than persisting projections. |
| 12 | [Actual Budget schedules](https://actualbudget.org/docs/schedules/) | Actual exposes explicit day-of-month schedules and a last-day option; it also warns that selecting day 31 skips short months, reinforcing that Cash Lens must preserve its chosen clamp contract explicitly. |
| 13 | [Plaid Transactions API](https://plaid.com/docs/api/products/transactions/) | Plaid's recurring output includes observed last dates and predicted next dates; Cash Lens keeps the observed stream and derives the display projection locally. |

The adopted rule is therefore: preserve the stream's original calendar anchor,
clamp each generated month independently, and apply the existing stale policy
to those generated dates.
