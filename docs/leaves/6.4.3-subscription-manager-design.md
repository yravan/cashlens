# 6.4.3 Subscription Manager — Approved Design

Status: founder-approved on 2026-09-13 (rulings relayed verbatim by the coordinator); implemented in this leaf's PR.

Prior art: [`6.4.3-prior-art.md`](./6.4.3-prior-art.md)

## Scope and approved rulings

> All recurring items with annual cost; confirm, dismiss, or mark canceled; price increases highlighted.

This leaf grows `/recurring` into the manager: every detected stream shows its yearly cost, per-currency yearly totals sit at the top, a third decision `canceled` joins `confirmed` and `dismissed`, and two markers appear on rows — a price increase, and a charge dated after the day the user marked the stream canceled. Nothing here cancels anything with a provider, sends a notification, or sets a reminder. Detection (6.4.1) and projection (6.4.2) keep their rules; canceled streams simply leave the projection the way dismissed ones do.

Founder rulings (decided 2026-09-13):

1. **Price-increase rule — decided: above the 7.5% band, outflows only.** An outflow stream whose latest kept charge is larger in magnitude than its typical (median) amount by more than the detector's stability band, using the same exact-rational compare 6.4.1 uses; deposits never flag. Rejected: any increase at all; 10% (KeepMySubs' default); only after two charges at the higher amount. The >25% ejection ceiling inherited from 6.4.1 is a named deferral (below).
2. **Cancel day — decided: the decision row's `updated_at` day.** The UTC day of the row's own `updated_at`, which `setRecurringStatus` already stamps on every post; no new column. A charge dated strictly after that day shows "charged after cancel" with "It's back" and "Still canceled"; "Still canceled" re-posts the same status and re-stamps it. Rejected: a `canceled_on` date column carrying the browser-local day like 2.2.3's `reported_on`; no "charged after cancel" marker at all.
3. **Yearly totals scope — decided: to review + confirmed.** The same predicate `/upcoming` projects; canceled and dismissed are out. Rejected: confirmed only; two figures.
4. **Yearly cost basis — decided: typical (median) × cycles per year (52/26/12/1).** The figure `/upcoming` already projects, with the price-increase marker disclosing the latest amount beside it. Rejected: latest charge × cycles; both when they differ.

Delivery ruling: one PR (~420 hand-written lines); the fallback split (status + yearly cost, then the two row markers) is allowed if the diff grows past one sitting.

## Existing seams

- `RecurringStream` (`lib/ledger/recurring-detection.ts`) already carries both numbers a price change needs — `typicalAmountMinor` (median of kept occurrences) and `lastAmountMinor` (latest kept occurrence) — plus `cadence`, `direction`, `lastDate`, `confidence`. `withinBand` and `STABLE` (3/40) are module-private; they become exports.
- `recurring_streams` (migrations 0023/0024) stores one row per decided identity with `status recurring_stream_status`, `created_at`, `updated_at`; own-row select/insert policies plus `recurring_streams_update_own`; app-role grants `SELECT, INSERT, UPDATE ("status","updated_at")`, no DELETE; FORCE RLS. `setRecurringStatus` inserts or `ON CONFLICT` updates `status` and `updated_at = now()`, and only for an identity the detector currently finds (404 otherwise).
- `recurringOverview()` joins detected streams with decisions by identity key; `upcomingOverview(reference)` filters `status !== "dismissed"` for `trackedCount` and calls `projectUpcoming`, which skips `status === "dismissed"` at line 73 of `lib/ledger/upcoming.ts`.
- `POST /api/recurring/streams`: `guardPost` → JSON → `parseStreamIdentity` + status allowlist → 400 → `setRecurringStatus` false → 404 → `{ ok: true }`.
- `/recurring` renders `StreamSection` × 3 (`recurring-proposed|confirmed|dismissed`), `StreamRow` (`recurring-stream`, `stream-amount`), and the client `StreamActions` (POST then `router.refresh()`; aria-labels `"<Label>: <name>"`).
- Seed: demo has STREAMFLIX (card, outflow, −2300 monthly, last 2026-03-29) and ACME CORP (checking, inflow, 250000 monthly, last 2026-03-27), both amount-identical across occurrences; `EXPECTED[persona].recurring` / `.upcoming` are hand-written and cross-checked in `tests/api/seed-dataset.test.ts` (lines 382–409). No seed stream exhibits a price change, and adding one would cascade through flow, spending, history, and category anchors — price-change coverage therefore uses `provision()` (api) and `adminQuery` row edits (e2e), never the seed.
- `formatMinorUnits`, `shortDate`, `signed` exist on the page; `isIsoDate` in `lib/ledger/history-query.ts`.
- PostgreSQL 16 (probed on 16.13): `ALTER TYPE … ADD VALUE` runs inside a transaction block; only *using* the new value in the same transaction fails (`unsafe use of new value`). drizzle's `migrate()` applies pending migrations in one transaction, so a migration that only adds the value is safe as long as no migration in the same batch references `'canceled'`.

## Pure rules — `lib/ledger/subscriptions.ts` (new)

One small module, exhaustively unit-tested, imported by the DAL, the projector, and the page. No clock, no I/O.

```ts
export type StreamStatus = "proposed" | "confirmed" | "dismissed" | "canceled";
export const tracked = (status: StreamStatus) => status === "proposed" || status === "confirmed";

export const CYCLES_PER_YEAR: Record<RecurringCadence, number> = { weekly: 52, biweekly: 26, monthly: 12, annual: 1 };
export const annualAmountMinor = (s: Pick<RecurringStream, "cadence" | "typicalAmountMinor">) =>
  s.typicalAmountMinor * CYCLES_PER_YEAR[s.cadence];

export type AnnualTotal = { currency: string; outMinor: number; inMinor: number };
export function annualTotals(streams: readonly (Pick<RecurringStream, "currency" | "direction" | "cadence" | "typicalAmountMinor"> & { status: StreamStatus })[]): AnnualTotal[];
// tracked streams only; one entry per currency, sorted by currency; outMinor sums outflows (negative), inMinor sums inflows; never netted, never converted.

export const priceIncreased = (s: Pick<RecurringStream, "direction" | "typicalAmountMinor" | "lastAmountMinor">) =>
  s.direction === "outflow" &&
  Math.abs(s.lastAmountMinor) > Math.abs(s.typicalAmountMinor) &&
  !withinBand(s.lastAmountMinor, s.typicalAmountMinor, STABLE);

export const chargedAfterCancel = (s: { status: StreamStatus; decidedOn: string | null; lastDate: string }) =>
  s.status === "canceled" && s.decidedOn !== null && s.lastDate > s.decidedOn;
```

Rules the code above fixes:

- **Yearly cost** is integer minor units with the stream's sign (−27600 for Streamflix, 3000000 for Acme); biweekly is 26, not 24; annual streams count once. It is the projection's own amount (`typicalAmountMinor`), so `/recurring` and `/upcoming` never disagree about what a stream costs.
- **Totals** follow the `tracked` predicate — the single place that decides which statuses count anywhere: `annualTotals`, `projectUpcoming`, and `trackedCount` all call it. Outflows and inflows are separate sums per currency (the 6.4.2 rule), never netted, never combined across currencies, no FX.
- **Price increase** is retrospective and relative: the latest kept charge exceeds the stream's typical amount by more than the 7.5% band, outflows only. `withinBand` is exact integer arithmetic, so the boundary is exact: typical −2300 → last −2472 is within (40·172 ≤ 3·2300), last −2473 is flagged. A high-confidence stream is amount-stable by definition and can never carry the marker; a stream whose typical has caught up with the new price stops carrying it (three old charges plus three new put the median midway; a fourth new charge makes the new price typical). A decrease is never flagged; a bigger deposit is never flagged.
- **Ceiling inherited from 6.4.1.** The detector's 25% acceptance band ejects a single charge more than 25% above the median, so a large hike (Disney+-style 40%) does not show as an increase: the stream's `lastDate` stalls at the old-price charge, `/upcoming` shows the expected date as not seen, then "Gone quiet", until a third new-price charge moves the median. Documented deferral (6.4.1 level-shift rule / 6.5.2 amount anomalies), not built here.
- **Charged after cancel** compares two calendar days as ISO strings, strictly: a charge dated the cancel day is not flagged (bank posting dates carry no time, so the same day is ambiguous either way). Re-posting `canceled` re-stamps `updated_at`, which clears the marker until the next posted charge — that is the "Still canceled" action. Nothing ever auto-reactivates a canceled stream.

## Status model

`recurring_stream_status` gains `canceled`. Absence of a row is still `proposed`. Any decision may follow any other at the API — there is no state machine, exactly as confirm/dismiss flip today — and every post re-stamps `updated_at`.

| Status | Where it renders | In `/upcoming` | In yearly totals | Actions offered |
|--------|------------------|----------------|------------------|-----------------|
| proposed | To review | yes | yes | Confirm · Mark canceled · Not recurring |
| confirmed | Confirmed | yes | yes | Mark canceled · Not recurring |
| canceled | Canceled (new section, between Confirmed and Dismissed) | no — not even "Gone quiet" | no | It's back (→ confirmed) · Still canceled (→ canceled; shown only while the charged-after-cancel marker is up) |
| dismissed | Dismissed | no | no | Mark recurring (→ confirmed) |

*Dismissed* keeps meaning "the detection was wrong"; *canceled* means "the detection was right and the service ended" (Monarch's not-recurring vs Canceled, Copilot's Pause vs Archive). A canceled stream stays listed for as long as the ledger still detects it — history is never hidden — and leaves the page only when the account is purged (cascade) or the pattern falls below three occurrences.

## API and validation boundary

`POST /api/recurring/streams` is reused unchanged in shape; the status allowlist widens by one literal.

| Route | Body | Success |
|-------|------|---------|
| `POST /api/recurring/streams` | `{ accountId, currency, direction, normalizedName, status }` with `status ∈ confirmed \| dismissed \| canceled` | 200 `{ ok: true }` |

Error precedence, unchanged:

| Order | Condition | Status | Body |
|------:|-----------|-------:|------|
| 1 | not signed in | 401 | `{ "error": "unauthorized" }` |
| 2 | browser `Origin` not the request host | 403 | `{ "error": "cross_origin" }` |
| 3 | unparsable JSON, identity fails `parseStreamIdentity`, status not one of the three | 400 | `{ "error": "invalid_request" }` |
| 4 | identity not among the caller's currently detected streams (unknown, no longer detected, or another user's) | 404 | `{ "error": "not_found" }` |

Every 404 is byte-identical: a neighbor posting `canceled` for the demo user's Streamflix, a random identity, and a stream that stopped being detected produce the same bytes. `parseStreamIdentity` is untouched; `status` is compared against three literals, never interpolated.

## DAL

`lib/data/recurring.ts`:

- `RecurringDecision = Exclude<StreamStatus, "proposed">`; `RecurringStatus = StreamStatus` (both re-exported from `lib/ledger/subscriptions.ts`, the one source).
- `RecurringOverviewStream = RecurringStream & { status: RecurringStatus; decidedOn: string | null }` — `decidedOn` is the UTC calendar day of the decision row's `updated_at` (`toISOString().slice(0, 10)`), `null` for proposed streams. It is the only new field on the read model; the page derives every marker from it and the stream's own numbers.
- `recurringOverview()` adds `updatedAt` to the decisions select and returns `{ streams, annual: annualTotals(streams) }`.
- `upcomingOverview(reference)` counts `tracked(stream.status)`; `projectUpcoming` skips `!tracked(stream.status)`.
- `setRecurringStatus(identity, status)` is unchanged in code; its `status` parameter type now admits `canceled`. The detect-first guard, the identity-keyed upsert, and `updated_at = now()` stay as they are.

Nothing new is stored: no column, no table, no policy, no grant.

## Least-privilege migration

- `0038_recurring_stream_canceled.sql`: `ALTER TYPE "public"."recurring_stream_status" ADD VALUE 'canceled';` — `schema.ts` appends `"canceled"` to `recurringStreamStatus`; this is drizzle-kit 0.31.10's exact output (verified on a throwaway copy of the schema and migrations before implementation; the committed migration is generated by `pnpm db:generate` and renumbered after any sibling leaf merges first).
- No grant migration: the app role's `UPDATE ("status","updated_at")` already covers the new value; `INSERT` already covers a first `canceled` decision.
- Constraint carried forward: no later migration may reference `'canceled'` in the same `migrate()` batch on a fresh database (the api template, CI, `db:setup`) — PostgreSQL refuses to use an enum value added in the same transaction.

## Downstream and security invariants

- Nothing here writes `transactions`; cash flow, spending, history, categorization, and detection are unchanged. `/upcoming` changes only by excluding canceled streams and by the copy line above.
- The only persisted change is a new enum value on user-scoped rows already under own-row policies and FORCE RLS; the app role's UPDATE surface on `recurring_streams` stays exactly `status`, `updated_at`; DELETE stays absent; account purge still cascades decisions.
- Cross-user: the neighbor can neither see the demo user's `annual`, `decidedOn`, nor markers, and cannot post `canceled` for a demo stream (404, byte-identical to unknown). The existing raw-RLS backstop test extends to the new status.
- Input: `status` is an allowlist of three literals; identity parsing unchanged; nothing from the request reaches SQL unbound.
- Nothing logs names, amounts, or dates. No new dependency, upload, webhook, background job, or secret — no new risk surface.

## Explicit deferrals

- Provider-side cancellation, concierge, bill negotiation; notifications, reminders, renewal alerts.
- FX conversion and a single base-currency total.
- A `canceled_on` day the user can backdate, and a user-timezone decision day (the stamp is UTC like `as_of`).
- Detector level shifts: a hike above 25% is ejected by 6.4.1's acceptance band and surfaces only as a stalled stream (6.4.1 follow-up / 6.5.2 amount anomalies); per-occurrence deviation markers (6.5.2).
- Staleness on `/recurring`: a stream that went quiet but was never canceled still counts toward the yearly total, because the page has no reference date; the `/upcoming` "Gone quiet" note now points at Mark canceled, which is the remedy.
- Savings-from-cancellation statistics (Wallos 2.33.0), collapsing or hiding the Canceled section, sorting by yearly cost, month-anchored views.
