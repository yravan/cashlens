# 4.5 - Transaction understanding: scope and prior art

Research date: 2026-09-11. Roadmap only; no connector, schema, model switch,
production rewrite, or new data access ships here. The feature tree defines
scope; this note records dependencies and acceptance boundaries. Each leaf
still needs its own implementation survey and review before coding.

## Product decisions

- Investigate a target transaction through relevant authorized email and other
  connected records, not just a merchant-name prompt. Appointment confirmations
  and other relevant non-receipt mail are in scope.
- Understand actual items and services, then allocate evidenced amounts through
  existing splitting and categorization leaves. A booking platform alone does
  not prove which service was bought.
- Let users volunteer personal context and answer grouped questions. Knowledge
  must be editable and time-scoped, not a permanent merchant-wide guess.
- Fully automatic operation is the destination. Version one requires confirmation
  before applying proposed enrichment or derived financial changes; investigation
  and proposal generation do not require confirmation per transaction.
- Notes are a presentation of structured supported facts, never the sole input
  to reporting. A plausible explanation is not evidence.
- Public lookup can establish merchant/service background, not private purchase
  facts. Public queries must exclude private transaction details and email text.

## Prior art

The following are source findings and proposed adoptions, not vendor selections.

| # | Primary source | Finding and scope consequence |
| --- | --- | --- |
| 1 | [Gmail filtering](https://developers.google.com/workspace/gmail/api/guides/filtering) | Search supports sender/date/query filters, with API/UI differences in aliases and threads. Adopt bounded candidate searches, explicit time windows, and retrieval tests; reject assuming inbox UI search and API search are identical. |
| 2 | [Gmail scopes](https://developers.google.com/workspace/gmail/api/auth/scopes) | Read access is broader than financial mail and includes restricted scopes. Enforce purpose limitation in Cash Lens; resolve verification/security-assessment requirements before shipping Gmail access. Do not advertise a receipt-only OAuth permission. |
| 3 | [Gmail message retrieval](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/get) | Message retrieval is a separate API operation. Retrieve selected candidates through the authorized connector rather than scraping browser sessions or copying an entire mailbox into a prompt. |
| 4 | [Gmail synchronization](https://developers.google.com/workspace/gmail/api/guides/sync) | Incremental history can expire and require full synchronization. Preserve coverage checkpoints and bounded recovery; no-results must not imply complete historical coverage. |
| 5 | [Textract expense analysis](https://docs.aws.amazon.com/textract/latest/dg/invoices-receipts.html) | Receipt extraction distinguishes totals, tax, discounts, shipping, gratuity, and line items. Adopt structured fields; extraction does not itself prove payment matching or category correctness. |
| 6 | [Document Intelligence receipts](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/prebuilt/receipt?view=doc-intel-4.0.0) | Prebuilt receipt extraction is an existing capability to evaluate. Compare maintained extraction tools before custom OCR; retain field-level evidence and validate arithmetic separately. |
| 7 | [W3C PROV](https://www.w3.org/TR/prov-overview/) | Provenance models entities, derivation, and activities. Adopt source/version/derivation relationships; reject requiring a graph database or full ontology for this product. |
| 8 | [OWASP prompt injection](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html) | External content can carry hostile instructions. Treat email, attachments, and public pages as untrusted evidence; enforce tool permissions outside the model. Prompt wording alone is not the security boundary. |
| 9 | [Evaluation concepts](https://docs.langchain.com/langsmith/evaluation-concepts) | Datasets, reference outputs, and experiments separate test inputs from evaluated runs. Adopt versioned cases and reproducible comparisons, not one successful model batch as proof. |
| 10 | [Retrieval evaluation](https://docs.langchain.com/langsmith/evaluate-rag-tutorial) | Retrieval relevance, correctness, and grounding are distinct measurements. Evaluate finding the right receipt separately from interpreting it. |
| 11 | [Judge alignment](https://docs.langchain.com/langsmith/improve-judge-evaluator-feedback) | Judge outputs should be checked against human labels. Model judges may assist triage but cannot establish financial truth or approve their own generator. |
| 12 | [Apple purchase history](https://support.apple.com/en-us/118212) | Purchase history offers evidence beyond a bank descriptor. Reuse planned 2.7 for selected Apple evidence; this does not establish a general third-party Apple connector. |

Adopt these patterns without uploading private traces to an evaluation SaaS by
default. This cross-cutting survey is not a substitute for connector-specific
privacy reviews, extraction comparisons, or leaf-level research.

## Required behavior

1. Start from an owner-scoped canonical transaction. Gather merchant aliases,
   dates, currency, amount, existing source links, and applicable user context.
2. Search connected evidence in bounded stages, including relevant appointments
   and payment confirmations. Track searched sources/time windows and failures.
   Do not equate a failed connector or exhausted budget with no supporting email.
3. Preserve competing candidates. Equal amount/date alone is not identity proof;
   recurring same-price purchases, tips, partial payments, and grouped bills matter.
4. Extract structured claims with source locations and status. User-confirmed
   purpose is distinguishable from a receipt fact and from model inference.
   Conflicting evidence must not silently overwrite a user correction.
5. Request matching, categorization, and splits from their owning leaves. A
   receipt is evidence, not another cash outflow. Preserve original ledger rows.
6. Require exact signed minor-unit reconciliation per currency. Item amounts plus
   discounts, tax, shipping, and tips must reconcile; unresolved residuals stay
   explicit. Any proportional allocation is a disclosed policy, not a receipt fact.
   Cross-currency differences require sourced FX/fee evidence, not forced equality.
7. Explain what is known concisely, with evidence accessible in 3.6.2. Preserve
   manual notes separately from generated text. Never infer a subscription tier
   from merchant or amount alone when multiple products fit.
8. When facts/context change, mark dependent conclusions stale and propose only
   affected changes. Recompute downstream views from accepted structured data;
   retain prior accepted results with visible stale status until replacement or
   explicit withdrawal. Source deletion must remove retained private content and
   invalidate unsupported derivatives according to 9.2, not preserve a hidden copy.

## Context and review experience

Allow entry independently of a transaction and from transaction detail. Show
scope, effective dates, provenance, affected examples/count, and edit/delete
controls. A household agreement does not classify every peer-to-peer deposit.
Questions should group genuinely related ambiguity and prioritize financial
impact; offer answer, narrow scope, defer, and dismiss. Do not make thousands of
individual confirmations the normal workflow. Bulk proposals still expose
exceptions and exact effects; they cannot silently broaden a user's statement.

## Security and operating limits

All evidence/context/derived records require owner isolation and deletion tests.
Read-only Gmail access does not authorize sending/deleting mail, following email
instructions, executing attachments, or opening arbitrary private-network URLs.
Bound connector calls, fetched bytes, attachment parsing, model tokens, retries,
elapsed time, and total cost before starting work; record resumable progress and
deduplicate retries. Resolve provider retention, credential handling, and Google
policy requirements during connector design. No email bodies, credentials, or
private evaluation examples belong in public code, CI logs, or artifacts.

## Evaluation and automation gates

### Gmail search and retention boundary

Use `gmail.readonly`, not mail modification permissions. This token can read the
mailbox: search filters are application controls, not Google-enforced access
restrictions. Account compromise remains a broader risk requiring credential
protection and revocation. Do not describe the connector as technically limited
to receipts or financially relevant messages.

The proposed investigation service accepts a transaction and a validated search
plan, not arbitrary model-selected HTTP requests. Server code derives the owner
and connected mailbox. Start with merchant/platform aliases and a date window;
widen dates and terms in bounded stages when evidence is missing. Amount is a
matching signal, not a mandatory exact email-search term: receipts may contain
different formatting, several amounts, or a later tip. Search relevant non-receipt
mail too. Resolve limits without asking for confirmation on each search; disclose
incomplete coverage if the search budget is exhausted.

List candidate message IDs first, then retrieve selected messages and attachments
under byte/count limits. Prefer parsing MIME/structured receipt content before
model extraction. Send only relevant content to the approved model provider;
selection is fallible, so do not promise that unrelated sensitive text can never
reach processing. Do not fetch remote tracking images or automatically follow
links found in mail. Public merchant lookup is a separate tool with server-side
query restrictions, not a channel for passing private snippets or transaction
details to a search engine.

Unmatched candidate bodies are transient processing inputs, not a permanent
mailbox mirror. Retain the minimum supporting extract or selected document needed
to inspect a matched claim, its source identifier, and structured facts under
owner isolation and encryption appropriate to sensitive content. A source ID
alone is insufficient when evidence is later unavailable; mark the support lost
rather than fabricate reproducibility. Selected financial documents retained by
2.3 must have explicit retention and deletion policy, not an implicit forever copy.

Logs contain operational counts/status, not queries, subjects, bodies, or model
payloads. Expiry/deletion must cover caches, retained documents, derived search
indexes, and provider-side retention where applicable; backup expiry and any
limits must be disclosed. Disconnect stops access and queued work; offer a clear
delete-imported-evidence action with its downstream consequences. Concrete TTLs
and provider handling are connector-design gates before release, not solved by
the phrase "minimal retention."

Test candidate overfetch, broadening, owner isolation, hostile search instructions,
log redaction, disconnect during queued work, and deletion/invalidation across
derived records. Use realistic missing-receipt tests to ensure minimization does
not silently make investigation ineffective.

### Quality gates

Maintain separate development cases and a frozen, independently adjudicated
holdout, grouped across merchants, time, and document families to reduce leakage.
Private production cases may be used only under explicit authorization; this
roadmap neither spends the previous evaluation budget nor grants new access.
Public regression cases must remain synthetic or appropriately de-identified.

Measure retrieval recall and false matches, field correctness and evidence
support, raw invalid/duplicate/missing outputs, abstention and coverage, item
allocation correctness, exact downstream totals, correction propagation, user
effort, latency, and cost. Exact arithmetic alone cannot validate an allocation.
Score raw model output and accepted output separately so parser filtering cannot
hide failures. Prove negative tests go red when the guarded behavior is broken.

Required scenarios: mixed-category receipts; platform-to-service evidence;
unknown subscription tier; repeated equal-price charges; refunds and partial
refunds; split tenders; grouped payments; changed household agreements; misleading
merchant descriptions; missing/deleted/contradictory evidence; historical source
gaps; malicious email instructions; neighboring users with similar purchases;
retries, concurrency, stale previews, and rollback after later manual edits.

Version one proposes changes for confirmation, including grouped acceptance.
Promotion is capability-specific, not a global confidence-score switch. Before
enabling automatic application, pre-register risk tolerances, minimum sample
sizes, error bounds, and rollback/demotion triggers; pass heldout and shadow
evaluation, then staged rollout monitoring. Zero observed errors in a small
selected sample does not mean zero risk. Uncertain cases may remain unresolved;
the target is minimal intervention without fabricating certainty.

## Decisions deferred to implementation design

Specify retention durations, connector history limits, per-user cost budgets,
tax/discount allocation policies, statistical promotion thresholds, and deletion
effects on previously accepted reporting. These are explicit pre-launch gates,
not permission to choose silently. No model, vector database, extraction vendor,
or autonomous framework is selected by this roadmap.
