# 2.2.3 Offline Accounts — Approved Design

Status: founder-approved on 2026-09-12; implementation has not started.

Prior art: [`2.2.3-prior-art.md`](./2.2.3-prior-art.md)

## Scope and approved rulings

> Track accounts with no feed — cash, prepaid balances, niche platforms like Kalshi — by periodically updating a balance.

This leaf lets a signed-in person create an offline account, re-enter its balance whenever they like, and delete it. It adds no ledger model, no balance history, and no reconciliation. Provider accounts are untouched by every rule below.

Founder rulings, 2026-09-12:

1. **Balance model: anchor plus ledger.** The balance the user enters is an anchor, stored as the account's single `account_balances` row (`current_minor`, `as_of` = server now, `reported_on` = the user's local calendar day). The balance shown for an offline account is the anchor plus the account's POSTED transactions that fall after the anchor. Held types (depository, investment, other) add the signed ledger amounts; owed types (credit, loan — stored positive when owed, the Plaid and 6.3.1 convention) subtract them, so a charge raises the amount owed and a payment lowers it. Updating the balance re-anchors and never creates a transaction. Rows show the current figure plus "Reported X on <day>" and, when non-zero, the count of transactions since. Cash-on-hand and credit-owed totals use the derived figure for offline accounts.
2. **Mutations in this leaf: create, update balance, delete.** Delete cascades the account's transactions, balance row, recurring decisions, and transfer pairs through the existing composite-FK cascades, behind an inline confirm that names the transaction count; after commit the 2.2.1 transfer repair runs. Rename ships as a separate PR (policy `accounts_update_own` plus `GRANT UPDATE ("name", "updated_at")`), started only after this PR merges. Editing type or currency, archive/close, opening-balance transactions, balance-history snapshots (3.1.2), net worth (6.3.2), and reconciliation or drift adjustments stay deferred.
3. **Types, currency, balance.** All five `account_type` values, labelled Cash / Credit card / Loan / Investment / Other. Currency is chosen from a select of the ledger's currencies plus a short fixed list, USD default; the boundary accepts any `^[A-Z]{3}$` code (the column CHECK). Credit and loan balances are entered as "Amount owed". A balance is required at creation ("0" is valid); negative balances are allowed; no opening-balance transaction is ever written.
4. **FEATURES.md.** The 2.2.2 line gains a one-line note that 2.2.3 was built first (an import needs a destination account, and an unconnected institution's account exists only as an offline account), committed on its own.

## Existing seams

- `accounts` already represents offline accounts: `source='manual'`, `connection_id` NULL, `source_id` NULL. The seed's "Cash Wallet" is one.
- `account_balances` holds one current row per account (`account_id` is the primary key), requires `as_of`, and requires `available_minor` or `current_minor`. The app role has INSERT plus column UPDATE on `available_minor`, `current_minor`, `limit_minor`, `as_of` (migration 0009); `plaid-sync.ts` already upserts on `account_id`.
- The app role has SELECT, INSERT, and RLS-scoped DELETE on `accounts` (0004, 0016) and no UPDATE. Deleting an account cascades `transactions`, `account_balances`, and `recurring_streams`; deleting transactions cascades `transfer_pairs`.
- `accountOverview()` in `lib/data/ledger.ts` reads accounts plus the balance row and totals depository as cash on hand and credit as credit owed; `historyOptions` lists every owned account, so the 2.2.1 form picks up a new offline account with no change.
- `guardPost()`, the closed plain-object parser pattern, `isEmptyMutationBody`, `isIsoDate`, `parseMajorUnits`, `formatMajorUnits`, `formatMinorUnits`, and `currencyExponent` exist. `repairTransfers` is private to `lib/data/manual-transactions.ts`.
- `transactions.created_at` defaults to the database clock at insert; 2.2.1 edits never touch it.

## Canonical rows

Create inserts one account and one balance row in one transaction:

```ts
accounts: {
  userId: authenticatedUser.id,
  connectionId: null,
  name,
  type,
  subtype: null,
  mask: null,
  currency,
  source: "manual",
  sourceId: null,
}
account_balances: {
  accountId: created.id,
  userId: authenticatedUser.id,
  availableMinor: null,
  currentMinor: anchorMinor,
  limitMinor: null,
  asOf: now(),
  reportedOn,
}
```

Update balance upserts the same balance row: `current_minor = anchorMinor`, `available_minor = NULL`, `limit_minor = NULL`, `as_of = now()`, `reported_on = reportedOn`. Offline accounts never carry available or limit figures.

## The anchor and the derived balance

For an account with `source = 'manual'` and a balance row whose `reported_on` is set:

```
since  = Σ amount_minor of the account's transactions where
           status = 'posted'
           and (date > reported_on
                or (date = reported_on and created_at > as_of))
shown  = current_minor + since        for depository, investment, other
shown  = current_minor - since        for credit, loan
```

`current_minor` NULL means no anchor; the row shows "Balance unavailable" and contributes nothing to totals, as today. A balance row without `reported_on` has no anchor day, so nothing counts as after it and the reported figure is shown unchanged; the app always writes `reported_on`, so this only concerns rows written outside the app. Provider accounts (`source` `plaid` or `import`) always show `current_minor` verbatim; the `source = 'manual'` predicate is part of the rule, not an optimization.

The anchor day is the user's local calendar day at the moment they entered the balance, sent by the browser exactly like the 2.2.1 date field and validated with the shared `isIsoDate`. `as_of::date` in UTC would give a Californian entering a balance at 8 pm tomorrow's day and exclude the evening's spending. The tie-break for rows dated the anchor day is the ledger row's insertion instant against the anchor instant, both from the database clock: a cash purchase recorded after the balance was entered moves the shown figure; one recorded before it was already reflected in the figure the user typed. Rows dated before the anchor day never count, however recently they were recorded, because the entered figure already reflected that day. 2.2.1 edits keep `created_at`, so re-dating a row onto the anchor day leaves its side of the tie-break unchanged.

Near midnight the browser day and the server instant can disagree: a balance entered at 23:59 local carries that day even if the request lands after midnight, and a transaction entered a minute later dated the next local day counts as after the anchor (date > day). A transaction dated the anchor day but entered before the balance stays excluded even if it has not yet hit the account; the remedy is to enter the balance again, which is the feature.

An edit or delete of a transaction moves the shown figure through the rule; an import (2.2.2) of historical rows after an anchor counts only rows dated after the anchor day. Nothing ever rewrites an earlier anchor.

## API and validation boundary

All three routes are POST, run `guardPost()` before reading the body, and parse the body as a closed plain object with exactly the listed keys. Pure parsing lives in `lib/ledger/offline-accounts.ts`; no raw input reaches SQL.

| Route | Body | Success |
|-------|------|---------|
| `POST /api/accounts/manual` | `{ name, type, currency, balance, reportedOn }` | 201 `{ accountId }` |
| `POST /api/accounts/[accountId]/manual` | `{ balance, reportedOn }` | 200 `{ accountId }` |
| `POST /api/accounts/[accountId]/manual/delete` | `{}` | 200 `{ accountId }` |

Field rules:

- `name`: string, trimmed, 1–200 characters.
- `type`: one of `depository`, `credit`, `loan`, `investment`, `other` (the keys of `OFFLINE_TYPE_LABELS`, a `Record<AccountType, string>` so a new enum value fails the build).
- `currency`: string matching `^[A-Z]{3}$`.
- `balance`: string, at most 32 characters, matching `^-?\d+(\.\d+)?$`; converted exactly by `parseMajorUnits` on the digits at the account's currency exponent with the sign applied (`"-0"` is `0`). More fraction digits than the exponent allows, or a value past the safe-integer range, is `invalid_request`. On update the currency is the stored account's, never the request's.
- `reportedOn`: string accepted by `isIsoDate` (shape and real calendar day). Any valid day is accepted; a wrong day affects only the sender's own derived figure.

Error precedence, identical on every route:

| Order | Condition | Status | Body |
|------:|-----------|-------:|------|
| 1 | not signed in | 401 | `{ "error": "unauthorized" }` |
| 2 | browser `Origin` not the request host | 403 | `{ "error": "cross_origin" }` |
| 3 | unparsable JSON, wrong keys, wrong types, out-of-range values, inexact balance | 400 | `{ "error": "invalid_request" }` |
| 4 | account id malformed, unknown, another user's, or not `source='manual'` | 404 | `{ "error": "account_not_found" }` |

Every 404 is byte-identical: a UUID that fails `UUID_PATTERN`, a random UUID, a neighbor's offline account, and the caller's own Plaid account all produce the same bytes, so no route is an existence oracle. Create has no 404.

## DAL and transaction ordering

`lib/data/offline-accounts.ts` derives the user from `requireUser()` only, runs each operation inside `withRequestScope()`, and keeps explicit `user_id` and `source = 'manual'` predicates in addition to forced RLS.

### Create

1. Convert `balance` at `input.currency`; `null` → `invalid_request`.
2. Insert the account row, returning `id`.
3. Insert the balance row with `as_of = now()` and `reported_on`.
4. Return `{ accountId }`.

### Update balance

1. `UUID_PATTERN` pre-check; failure → `account_not_found`.
2. `SELECT id, currency FROM accounts WHERE id AND user_id AND source = 'manual'`; no row → `account_not_found`. No `FOR UPDATE`: every Postgres locking clause needs an UPDATE privilege on the table, which the app role does not hold on `accounts` until PR 2's rename grant, and the lock is not load-bearing — the balance row's composite FK to `(id, user_id)` makes a concurrent delete either cascade the fresh anchor away or reject the insert, never orphan it.
3. Convert `balance` at the stored currency; `null` → `invalid_request`.
4. Upsert the balance row on `account_id` (the `plaid-sync.ts` pattern), setting `current_minor`, clearing `available_minor` and `limit_minor`, `as_of = now()`, `reported_on`.
5. Return `{ accountId }`.

### Delete

1. `UUID_PATTERN` pre-check; failure → `account_not_found`.
2. `DELETE FROM accounts WHERE id AND user_id AND source = 'manual' RETURNING id`; zero rows → `account_not_found`. The composite-FK cascades remove the account's transactions, balance row, recurring decisions, and transfer pairs inside the same transaction.
3. After commit, call the exported 2.2.1 `repairTransfers(user, "delete_offline_account")`, whose failure logs `transfer_match.run_failed` with the operation and a sanitized error class and never changes the response.

### Overview read

`accountOverview()` keeps its select and ordering and adds `source`, `reported_on`, and three correlated scalar subqueries over `transactions` bound to the account row (`account_id`, `user_id`): the since-anchor sum and count under the rule above (which also requires `accounts.source = 'manual'` and `status = 'posted'`), and the account's total transaction count for the delete confirm. The derived `currentMinor`, `reportedMinor` (the stored figure), `reportedOn`, `sinceCount`, and `transactionCount` are computed per row in TypeScript; `cashOnHand` and `creditOwed` sum the derived `currentMinor`. `EXPECTED[persona].overview` derives the same fields from the seed rows with an independent TypeScript implementation of the rule.

## Least-privilege migration

- `0032_offline_account_anchor.sql`: `ALTER TABLE "account_balances" ADD COLUMN "reported_on" date;` (nullable; NULL for every provider row).
- `0033_offline_account_anchor_grant.sql`: `GRANT UPDATE ("reported_on") ON TABLE "account_balances" TO "cashlens_app";`

`schema.ts` gains `reportedOn: date("reported_on")` on `accountBalances`. No new table, policy, role, dependency, secret, upload, webhook, or background job; the FORCE RLS coverage test is unaffected. The seed's "Cash Wallet" balance row gains `reportedOn: "2026-03-31"`; its only transaction is dated 2026-03-14, so every seed figure is unchanged.

## Downstream and security invariants

- Nothing here writes `transactions`, so cash flow, spending, recurring detection, upcoming, history, and auto-categorization are unchanged. The only new figure is a display derivation in `accountOverview()`.
- A manual transfer between two offline accounts moves both derived figures in opposite directions.
- Deleting an offline account is the 2.1.5 purge for one account: RLS-scoped DELETE, cascades bounded by composite `(id, user_id)` FKs, so a cascade can never cross a user boundary.
- Every write carries `user_id` and `source = 'manual'` predicates under forced RLS. Ids pass `UUID_PATTERN`, the type is an enum value, amounts are integers, days are validated; parsed strings are bound parameters.
- Nothing logs names, amounts, days, or request bodies.
- Manual rows are always `source='manual'`, `connection_id NULL`, `source_id NULL`; nothing in the request can set them.

## TDD and behavioral proof

Unit (`tests/unit/offline-accounts.test.ts`): closed key sets for both parsers; type allowlist; currency shape; balance regex, length, sign, `"-0"`, exponent (USD `1.234`, JPY `1.5`, KWD `1.2345` rejected; JPY `1234`, KWD `1.234` accepted), safe-integer bound; `reportedOn` calendar validity.

API (`tests/api/offline-accounts.test.ts`, real PostgreSQL through the route handlers):

- Create as a fresh user: exact `accounts` and `account_balances` rows, 201 body, overview row and totals move by the exact amount for a depository account and not for `other`; a credit account lands in credit owed.
- Derived balance with admin-inserted rows: dated after the day (counted), same day created after `as_of` (counted), same day created at exactly `as_of` (excluded), same day created before (excluded), dated before (excluded), pending (excluded); held and owed signs; provider account with identical rows shows `current_minor` verbatim; totals follow the derived figure.
- Update balance: `current_minor`, `as_of`, `reported_on` replaced, `available`/`limit` NULL; since-rows recomputed against the new anchor.
- Delete: exact before/after counts of transactions, balance rows, recurring streams, and transfer pairs; the neighbor's rows untouched; empty-body rule.
- Authority: neighbor updating or deleting the owner's account, a random UUID, a malformed id, and the owner's own Plaid account answer byte-identical 404s; raw RLS backstop through `withRequestScope` as the neighbor sees zero rows.
- Precedence on all three routes: signed-out with a bad body → 401; cross-origin → 403; bad body → 400 before any 404.
- Seed: `EXPECTED.overview` rows carry the new fields; `seed-dataset.test.ts` anchors extended with the same values.

E2E (`e2e/offline-accounts.signed-in.spec.ts`, real Clerk): user A adds "Petty Cash" (Cash, USD, 100.00) → row in Cash at $100.00 and cash on hand up by exactly $100.00 → the 2.2.1 form lists it → an outflow of 25.00 dated today on it → row shows $75.00 and "1 transaction since" → update balance to 80.00 → $80.00 with no since-count → delete, confirm names 1 transaction → row and totals back to the seed → user B's page unchanged. A second case runs at 320 px and asserts no horizontal overflow.

Mutation proofs (each observed red, then restored byte-for-byte): drop `source = 'manual'` from delete (own Plaid account becomes deletable); turn the tie-break `>` into `>=` (the exactly-at-`as_of` case flips); drop `status = 'posted'` (the pending case flips); flip the owed-type sign (the credit case flips); drop the `source = 'manual'` predicate from the overview rule and stamp a provider balance row with `reported_on` (a Plaid account starts deriving); accept an extra request key; parse the balance with `Number()` (JPY `1.5` passes); swap guard and parse order (signed-out bad body answers 400); change the seed rule to `>=` on the day (the DAL and `EXPECTED` disagree).
