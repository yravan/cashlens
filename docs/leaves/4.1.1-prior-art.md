# 4.1.1 Category Taxonomy & Manual Assignment — Prior Art

Survey date: 2026-08-30

Scope: category taxonomy shape (hierarchy depth, system-vs-user rows), default-set curation, uncategorized representation, assignment storage and UX, seams for LLM auto-categorization (4.2.1) and history filtering (3.6.1).

## Sources and decisions

| # | Source | Evidence | Cash Lens decision |
|---:|---|---|---|
| 1 | [Plaid PFC migration guide](https://plaid.com/docs/transactions/pfc-migration/) + [taxonomy CSV](https://plaid.com/documents/transactions-personal-finance-category-taxonomy.csv) | Plaid replaced its 600+ three-level legacy hierarchy with exactly two levels: 16 primary and 104 detailed categories; every primary ends in an `OTHER_*` detailed catch-all; `detailed` doubles as a unique id. | Adopt two levels — the industry converged there after trying deeper trees. Adopt a general/other leaf per group so nothing is forced into a wrong leaf. Reject importing Plaid's SCREAMING_SNAKE taxonomy verbatim: names are bank-centric (BANK_FEES, TRANSFER_IN) and merchant-type-shaped (DEPARTMENT_STORES), not intent-shaped. |
| 2 | [Plaid categorization taxonomy blog](https://plaid.com/blog/transactions-categorization-taxonomy/) | Plaid's stated lesson from the redesign: fewer, better-defined categories beat a large ambiguous list; the old system's 600+ entries produced inconsistent assignment. | Adopt a curated set (~60 leaves), not a maximal one. Adopt per-user editable rows (defaults are the user's rows, not shared system rows). Reject "Uncategorized" as a row: it is the absence of assignment (NULL), which is why Monarch must special-case it everywhere. |

Enforce name uniqueness only within a level per user. |
| 7 | [Firefly III: Organizing transactions](https://docs.firefly-iii.org/explanation/data-classification/what-to-use/) + [discussion #5275](https://github.com/orgs/firefly-iii/discussions/5275) | Firefly categories are deliberately flat (no hierarchy), one per transaction; granularity is pushed to tags; users migrating from hierarchical tools report friction and adopt coarse categories. | Reject fully flat: the vision explicitly demands "groceries vs supermarkets, glasses vs derm vs psych" — that is a grouped tree. | 11 | [YNAB: How many categories](https://www.ynab.com/blog/how-many-ynab-categories) | Budgets start with a small default group/category set; guidance is to keep the list small and personal; groups are folders with no money assigned. | Reinforces #2 (curated, scannable default) and #4 (groups organize, leaves act). |

| 13 | [GnuCash docs: Accounts (income/expense as accounts)](https://www.gnucash.org/docs/v5/C/gnucash-guide/chapter_accts.html) | Double-entry: categories are income/expense accounts in an arbitrarily deep tree; every transaction is a split between accounts. | Reject double-entry category accounts for this product: the ledger is single-entry provider rows enriched with labels; splits arrive later (3.4.1) as decomposition of a row, not as accounting postings. ## Distilled design (what 4.1.1 builds)

1. **Per-user rows, no system taxonomy table** (#3, #8, #16, #20): one `categories` table, every row owned by a user, RLS `user_id = app_current_user_id()` exactly like every other user table. The default tree is a constant in code, planted idempotently for a user the first time a category surface loads and the user has zero rows.
2. **Two levels via self-reference** (#1, #4, #8, #19, #21): `parent_id` nullable, composite-FK'd `(parent_id, user_id) → (id, user_id)`. Groups are rows with children; leaves are assignable. Depth beyond one level is prevented by construction now, revisited in 4.1.2.
3. **Assignment is one nullable FK on transactions** (#7, #10): `transactions.category_id uuid null`, composite FK `(category_id, user_id)`, NULL = uncategorized, rendered as "Uncategorized", never a row. Groups reject assignment (#9) — enforced in the DAL (target with children refuses) and by the native `optgroup` UI.
4. **Curated default tree, intent-shaped names** (#1, #2, #17): 15 groups / 65 leaves; includes the vision's mandated distinctions (Groceries vs Superstores & Wholesale; Vision & Eyewear vs Dermatology vs Mental Health); explicit `sort_order` preserves curated order (#4).
5. **Minimal assignment surface on the placeholder transactions route** (#18, #24): date-desc row list, per-row native select with optgroups, save-on-change. Search/filters/pagination are 3.6.1; rules are 4.2.2; bulk is 5.3.
6. **Seams**: 3.6.1 reads `category_id`/name per row and the user's categories as filter options; 4.2.1 writes the same column through the same DAL and adds its own confidence/reason storage. Zero LLM code, zero flags, zero transfer semantics here.
