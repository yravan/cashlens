# 2.2.2 Statement File Import — Approved Design

Status: founder-approved on 2026-09-13; implementation has not started.

Prior art: [`2.2.2-prior-art.md`](./2.2.2-prior-art.md)

## Scope and approved rulings

> Upload CSV or statement exports to backfill accounts a connection can't reach; rows land in the ledger like any other source. (Built after 2.2.3: an import needs a destination account, and an unconnected institution's account exists only as an offline account.)

This leaf lets a signed-in person pick a CSV export from their bank, map its columns once, see how the rows will be read, and land them in one of their offline accounts as ordinary posted transactions. Re-importing the same file, or an overlapping later export, adds nothing twice. The rows behave exactly like every other posted row: they appear in history, cash flow, spending, recurring detection, transfer matching, and auto-categorization, and they move the 2.2.3 anchor balance by the rule that already exists.

Rulings (founder, 2026-09-13):

1. **Formats: CSV only.** Papa Parse in the browser. OFX/QFX/QIF/CAMT are deferred (below), not partially supported.
2. **Dedup key: date + amount + normalized description + occurrence.** A hash of the date, the minor-unit amount, the description lower-cased with whitespace collapsed, and the row's occurrence count among identical tuples in the same file becomes `transactions.source_id`.
3. **Destination: offline accounts only.** The 2.2.3 `source='manual'` accounts; provider accounts, connected or disconnected, are never a destination.
4. **Wrong-import recovery: the existing 2.2.1 per-row delete path.** Imported rows become deletable one by one from the transactions page. No undo-last-import button and no import-batch record.

### Non-goals

- OFX, QFX, QIF, CAMT, XLSX, PDF (ruling 1).
- Matching imported rows against hand-entered manual rows, or against provider rows (3.3.2 cross-source merge).
- Importing into connected or disconnected provider accounts (ruling 3).
- Creating an account from a file, or importing several accounts from one file.
- Categories, tags, notes, or balances read from the file.
- Saved column mappings, per-bank presets, scheduled or emailed imports.
- Editing imported rows; tombstones that keep a deleted row from re-importing.
- Undoing a whole import at once, or recording which import a row came from (ruling 4).
- Balance adjustments or reconciliation at the end of an import (3.2.x).

## Existing seams

- `transactions.source` already has the `import` value and `transactions.source_id` already carries per-source identity; the partial unique index `transactions_account_source_row_key` on `(account_id, source, source_id) WHERE source_id IS NOT NULL` is the idempotency guarantee, and `plaid-sync.ts` already inserts in chunks of 500 with `onConflictDoNothing()` against it.
- The app role's `transactions` privileges (INSERT, column-scoped UPDATE, DELETE, all RLS-scoped) already cover an insert of `source='import'` rows. No migration, no grant.
- 2.2.3's `manualAccount(accountId, userId)` predicate in `lib/data/offline-accounts.ts` names the only legal destination (`source='manual'`, owned).
- 2.2.1's closed parser conventions in `lib/ledger/manual-transactions.ts` (`isPlainObject`, exact key sets, `AMOUNT` regex, description trimmed to 1–200) and `parseMajorUnits` in `lib/ledger/minor-units.ts` define the wire shape of one transaction.
- `guardPost` (401 → 403), `offlineAccountResponse` (400 for `invalid_request`, byte-identical 404 otherwise), and `repairTransfers(user, operation)` are the route, response, and post-commit conventions.
- The 2.1.4 webhook route's read loop is the repo's bounded body consumption.
- `accountOverview` already computes anchor ± posted rows after the anchor; imported rows need nothing from it.
- `OfflineAccountActions` in `app/(app)/accounts/offline-account-controls.tsx` renders per-row actions for `source === "manual"` accounts (balance, rename, delete) with `useMutation`, `RowForm`, and `ERROR_COPY`.

## Where parsing happens

The file is read and parsed in the browser. The route never receives a file: it receives a JSON body of already-normalized rows in the 2.2.1 shape. This is the Lunch Money model and it removes the whole upload surface (multipart parsing, filenames, content types, stored bytes, server-side encoding negotiation, Vercel's 4.5 MB function payload cap) while keeping the server boundary identical in kind to every other write route. The server still validates every row as untrusted input and still derives every identity itself.

CSV parsing uses Papa Parse (MIT, zero dependencies, npm 5.7.0), loaded with a dynamic `import("papaparse")` when a file is chosen so the accounts page's initial bundle does not grow. Configuration: `header: true`, `delimiter: ""` (guess among `, \t | ;`), `skipEmptyLines: "greedy"`, `dynamicTyping` off, `transformHeader` trims. Papa Parse's per-row errors (`TooFewFields`, `TooManyFields`, `MissingQuotes`) are surfaced with their row numbers and block submission. The text comes from `file.text()`, which decodes UTF-8 and discards a leading BOM by spec; a Latin-1 export shows replacement characters in the preview, which is the honest outcome without an encoding select (deferred).

## Column mapping and row normalization

Pure functions in a new `lib/ledger/statement-import.ts`, shared by the browser preview and the server parser:

- `guessMapping(headers)`: pre-selects the date, amount (or money-out and money-in), and description columns from short case-insensitive synonym lists (`date`, `transaction date`, `posted date`, `posting date`, `booking date`; `amount`; `debit`, `withdrawal`, `outflow`, `money out`; `credit`, `deposit`, `inflow`, `money in`; `description`, `payee`, `merchant`, `name`, `memo`, `narrative`, `details`). A guess is a form default the person confirms against the preview, never a decision.
- `parseStatementDate(value, order)` with `order` one of `ymd`, `mdy`, `dmy`: accepts one-or-two-digit day and month and a four-digit year separated by `-`, `/`, or `.`, validates through the shared `isIsoDate`, returns `YYYY-MM-DD` or `null`. Month names, two-digit years, and time-of-day suffixes are rejected (deferred; the preview shows the failure).
- `normalizeAmount(value, decimalMark)`: trims, treats `(12.34)` as negative, strips currency symbols, spaces, and the thousands separator implied by the chosen decimal mark (`.` or `,`), and returns a string matching the 2.2.1 `AMOUNT` regex or `null`. Letters in an amount cell (`12.34 DR`) are rejected rather than stripped, because stripping them would silently drop the direction. Two-column layouts produce `-out` or `+in`; a row with both or neither is malformed. The "flip signs" checkbox negates everything, for exports where money out is positive (credit cards).
- `importRows(rows, currency)`: converts each amount with `parseMajorUnits` at the destination currency's exponent (a 3-decimal amount on a 2-decimal currency fails the whole request) and derives `source_id` = `sha256` hex of `date`, `amountMinor`, the description lower-cased with whitespace collapsed, and the occurrence index (1-based count of identical tuples earlier in the same file), joined by `\n`. Deterministic across re-exports; independent of column set, quoting, header names, and capitalization; distinct for genuinely identical rows in one file.
- `parseStatementImportInput(body)`: the closed server parser. Exact keys `{ rows }`; `rows` is an array of 1 to `MAX_IMPORT_ROWS` (5,000) plain objects with exact keys `date` (`isIsoDate`), `amount` (`AMOUNT` regex), `description` (trimmed 1–200). Any other shape is `invalid_request`.

The sign convention is the ledger's net-worth convention, money out negative, the same as manual transactions.

## Validation at the boundary

Route `POST /api/accounts/[accountId]/manual/import`, in this order:

1. `guardPost`: 401 `unauthorized`, then 403 `cross_origin`.
2. Body consumed through the 2.1.4 loop, lifted into `lib/api/body.ts` as `readBodyCapped(request, maxBytes)` and used by both the webhook route (unchanged behavior, still pinned by its tests) and this route: `MAX_IMPORT_BODY_BYTES` = 1 MiB; the first byte past the cap cancels the reader and answers 413 `too_large` before parsing; an unreadable stream answers 400 `invalid_body`. Five thousand rows with 200-character descriptions fit in about 1.2 MB, so the row cap and the byte cap bound each other; Vercel's 4.5 MB cap is never reached.
3. `JSON.parse` failure or a body rejected by `parseStatementImportInput` answers 400 `invalid_request`.
4. The DAL resolves the account with `manualAccount`; a malformed UUID, an unknown id, another user's account, and a provider account all answer the same 404 `account_not_found` body. An amount that does not fit the account's currency exponent answers 400 `invalid_request` after the account resolves.
5. Success answers 200 `{ accountId, inserted, skipped }`.

Every string that reaches SQL is a parameter; nothing is interpolated. Descriptions are stored verbatim (formula-leading characters are inert here; noted for any future export leaf).

## Dedup and idempotency rule

`source_id` = the key above, `source = 'import'`, inserted in chunks of 500 with `onConflictDoNothing()` against the partial unique index, the driver's `rowCount` for the inserted count (no rows cross the wire); `skipped = rows.length - inserted`. Consequences, all stated in the UI copy:

- Re-uploading the same file inserts nothing and reports every row as already in the ledger.
- A later export overlapping the earlier one lands only the new rows.
- Two identical rows in one file both land (occurrence 1 and 2).
- A row deleted from the ledger comes back if its file is uploaded again (no tombstones until 3.3.2).
- A manual row entered by hand for the same purchase is not matched; the import reports it as inserted and the ledger shows both until 3.3.2.
- The occurrence is counted within the submitted rows, so the whole file is submitted in one request (hence the 5,000-row cap rather than client-side chunking, which would renumber across chunk boundaries).

## Interaction with the 2.2.3 anchor

Nothing changes in `accountOverview`. Imported rows have `status='posted'` and `created_at = now()`, so the existing rule applies unchanged: rows dated after `reported_on` move the shown balance; rows dated on `reported_on` move it because their `created_at` is after `as_of`; rows dated before `reported_on` only add history. The preview states the count of rows that will move the balance ("12 of 140 rows are dated after the balance you entered on 2026-03-14 and will change it") so a person who anchored today and imports a statement through today understands why the number moves. The api suite pins all three cases against `accountOverview`.

## Transfer re-matching

After the insert commits, `repairTransfers(user, "import_statement")` runs (the `Operation` union gains the member). An imported outflow that mirrors a manual or provider inflow in another owned account within the 3.3.1 rule pairs immediately, so the dashboard's true spend is right on the next read; failures log `transfer_match.run_failed` and never fail the import.

## Least-privilege data model

No new table, column, grant, or migration. The import stores exactly the fields a manual transaction stores, minus merchant: `user_id`, `account_id`, `amount_minor`, `currency` (the account's), `date`, `description`, `status='posted'`, `source='import'`, `source_id` (the key), `category_id NULL`, `category_source NULL`. No import batch row (ruling 4): a batch table would store when and from which file rows arrived, which no read path needs; recovery uses per-row deletion instead of batch deletion for the same reason. Nothing about the file (name, size, headers, unmapped columns) is stored or logged. Logging is one `logEvent("statement_import.run", { accountId, received, inserted, skipped })` line: ids and counts, never descriptions or amounts.

## DAL

`importStatementRows(accountId, input)` added to `lib/data/offline-accounts.ts` (same `withRequestScope`, same `manualAccount` predicate, same `OfflineAccountResult` union widened with the counts): resolve the account and its currency, convert amounts and derive keys through `importRows`, insert in chunks inside one transaction, then repair transfers outside it. Returns `{ accountId, inserted, skipped }` or `{ error }`.

## UI

- `OfflineAccountActions` gains an "Import" mode next to Balance, Rename, Delete. The form lives in a new client module `app/(app)/accounts/statement-import.tsx`: a file input (`accept=".csv,text/csv"`, `data-testid="import-file"`), and once a file parses, four selects (date column, date order, amount column or the out/in pair, description column), a decimal-mark select, the flip checkbox, a five-row preview table showing the interpreted date, amount, and description, the counts (rows, malformed rows with line numbers, rows after the anchor), and Import/Cancel. Import is disabled while any row is malformed. Success replaces the form with "Imported 128 transactions · 12 were already in the ledger" and calls `router.refresh()`.
- Reuses `useMutation`, `inputClass`, `ErrorLine`, `responseErrorFor`; `ERROR_COPY` gains `too_large` and `invalid_body`.
- 320px: controls stack in one column (the `RowForm` flex-wrap convention), the preview table sits in an `overflow-x-auto` container, and the file input's label wraps.
- Wrong-import recovery (ruling 4): the 2.2.1 delete route's predicate widens to `source IN ('manual','import')` and the transactions page shows its existing Delete control on import rows.

## Tests

- **Unit** (`tests/unit/statement-import.test.ts`, exhaustive): date orders and separators, invalid calendar days, two-digit and textual dates rejected; amount normalization (thousands separators for both decimal marks, parentheses, currency symbols, letters rejected, flip, two-column layouts with both/neither filled, zero, leading plus, exponent notation rejected); key derivation (case and whitespace insensitivity, occurrence numbering, column-set independence, currency exponent); the closed parser (exact keys, extra keys, `__proto__`, non-array, 0 and 5,001 rows, non-string fields, 201-character descriptions); header guessing.
- **API** (`tests/api/statement-import.test.ts`, the `offline-accounts.test.ts` helpers): 401 signed out; 403 cross-origin; 413 for a body one byte over the cap, verified to be answered without any row landing; 400 for malformed JSON and every parser rejection; byte-identical 404 for a malformed id, an unknown id, user B's account, and a Plaid account; 200 with exact stored rows (source, status, currency from the account, `source_id`, NULL category); a second identical upload inserting 0 and skipping all; an overlapping upload inserting only the new rows; identical rows in one upload both landing; 3-decimal amounts on a 2-decimal currency rejected; the anchor rule (before, on, after `reported_on`) through `accountOverview`; transfer pairing after import; the log line's keys; cross-user isolation (user B's import into A's account answers the same 404 and A's ledger is unchanged; B's history and overview never show A's rows) plus the `appQueryScopedAs` RLS backstop.
- **E2E** (`e2e/statement-import.signed-in.spec.ts`, desktop and 320px): user A uploads a fixture CSV (`e2e/statement-fixture.csv`, fake data, mixed date order and a parenthesized amount) into the seeded Cash Wallet through `setInputFiles`, corrects the date order from the preview, sees the after-anchor count, imports, sees the exact inserted count, the reported balance moving by exactly the after-anchor sum, and the rows in `/transactions`; re-uploads and sees every row reported as already present; deletes one imported row through the 2.2.1 control; user B's pages show none of it.
- **RED proofs recorded in the PR**: drop the description from the key (unit and overlapping-upload tests fail), remove `onConflictDoNothing` (re-upload test fails with the unique violation), remove the `source='manual'` predicate (provider-account 404 test fails), skip `repairTransfers` (pairing test fails), raise the byte cap (413 test fails). Each mutation restored byte-identically.

## Risk surface

The leaf's new surface is a user-controlled bulk write route. Mitigations, each pinned by a test: origin guard and Clerk auth before any read; byte cap enforced while consuming the stream; row cap and exact-shape parser before any SQL; amounts re-derived on the server at the account's currency exponent; destination restricted to the caller's own offline accounts through both the explicit predicate and RLS; identity derived on the server so a client cannot choose `source_id` values; insert-or-ignore so replays cannot amplify; nothing from the file persisted or logged beyond counts. There is no file upload surface: no multipart parser, no filename, no stored bytes. Papa Parse is a new dependency (MIT, zero runtime dependencies, current release) and runs only in the browser on the person's own file.

## Rejected alternatives

- **CSV plus OFX/QFX, or CSV plus OFX and QIF** (ruling 1): no maintained, widely used parser to adopt, OFX 1.x is SGML with unclosed tags, and CSV is every bank's lowest common denominator. FITID-based identity is the reason to revisit OFX later.
- **Date + amount + occurrence key** (YNAB's `import_id`; ruling 2): two different purchases of the same amount on one day would collide and the second would be silently skipped. The description is cheap to include and the same export produces the same description each time.
- **Whole-row hash** (Firefly's classic `import_hash_v2`; ruling 2): breaks on capitalization, column order, quoting, and any extra column a bank adds to a later export.
- **Any owned account as a destination, or offline plus disconnected provider accounts** (ruling 3): provider rows and import rows have disjoint identities, so a file overlapping a synced range would double every row until 3.3.2's cross-source merge exists; a disconnected account can be reconnected, at which point the same problem returns.
- **Undo-last-import button** (ruling 4): needs a batch marker on every imported row that no read path uses; per-row deletion already exists and covers the wrong-file case.
- **No recovery this leaf** (ruling 4): a wrong import with no way out is worse than the fifteen lines that widen the delete predicate.

## Deferrals

- OFX/QFX/QIF/CAMT with FITID-based identity in the same `source_id` slot.
- Matching against manual and provider rows, tombstones, "reimport deleted" (3.3.2).
- Encoding select (`TextDecoder(label)`), month-name and two-digit-year dates, time-of-day suffixes in date cells, exponent amounts, `DR`/`CR` direction suffixes and amount-type columns.
- Saved mappings and bank presets.
- Multi-account files, account creation from a file.
- Undo-whole-import (would need a batch marker).
- CSV export sanitizing (whenever an export leaf ships).
