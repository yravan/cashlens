# 6.2.1 Spending filter state correction

Scope: keep the existing period controls consistent with the report URL. No changes to
ledger arithmetic, transfer classification, categorization, or provider ingestion.

## Failure

After editing and applying a period, Clear navigated to the all-time report but retained
the previous input values. Applying again silently restored the old period. The inputs
are uncontrolled; changing their default values does not reset their current values.

## Adopted pattern

The original [prior-art survey](6.2.1-prior-art.md) defines the URL as the report's state.
The Transactions page already keys its filter component by query state. Spending now
uses the same component-remount pattern for valid and invalid queries, without client
state, effects, or a second source of truth.

The installed Next.js Form documentation confirms that GET submissions use client-side
navigation and preserve client state. The key is on the enclosing SpendingFilters
component, not a prop passed to Next's Form component.

## Regression evidence

The new signed-in browser test failed before the fix: after Clear, the URL and totals
were all-time while From still contained the synthetic fixture date `2026-03-01`.
It checks all three controls, exact per-currency totals, Back/Forward navigation, and
Apply after clearing. Existing tests retain invalid-query, drill-down, cross-user
isolation, and mobile-layout coverage.

Tests use the existing synthetic dataset and an isolated local database. Temporary
local test-port overrides are not part of this change. No production records or
credentials are included in fixtures or this note.
