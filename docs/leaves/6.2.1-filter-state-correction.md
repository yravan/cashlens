# 6.2.1 Spending filter state correction

Scope: keep the existing period controls consistent with the report URL. No changes to
ledger arithmetic, transfer classification, categorization, or provider ingestion.

## Failure

After editing and applying a period, Clear navigated to the all-time report but retained
the previous input values. Applying again silently restored the old period. The inputs
are uncontrolled; changing their default values does not reset their current values.

## Adopted pattern

The original [prior-art survey](6.2.1-prior-art.md) defines the URL as the report's state.
The Transactions page already keys its filter component by query state. Spending now
uses the same component-remount pattern for valid and invalid queries, without client
state, effects, or a second source of truth for the applied period.

A second live reproduction found that editing an unsubmitted period on the unfiltered
URL also survived Clear. A key cannot change when the URL stays the same. Clear now
resets its containing native form on Next's `onNavigate`, in addition to navigating.
Modifier-clicks that open a new tab do not reset the current form. The small client
link owns only a DOM ref, not copies of the filter values.

The installed Next.js Form documentation confirms that GET submissions use client-side
navigation and preserve client state. The key is on the enclosing SpendingFilters
component, not a prop passed to Next's Form component.

`onNavigate` rather than `onClick` is load-bearing, and the installed `next/link`
source is why: `linkClicked` returns on `isModifiedEvent` before `onNavigate` is
called, and calls it after `preventDefault` but before dispatching the navigation.
So the reset runs on real navigations only, and never bypasses one.

3.6.1 shipped a byte-identical link for Transactions, so both pages now share
`app/(app)/clear-filters-link.tsx`, parameterised by `href` alone. Each page keeps its
own form, query schema, and key — Spending keys on the parsed query, Transactions on
its canonical query string. Deleting the shared reset reddens both pages' draft tests.

## Regression evidence

The new signed-in browser test failed before the fix: after Clear, the URL and totals
were all-time while From still contained the synthetic fixture date `2026-03-01`.
It checks all three controls, exact per-currency totals, Back/Forward navigation, and
Apply after clearing. Existing tests retain invalid-query, drill-down, cross-user
isolation, and mobile-layout coverage.

The unsubmitted-period regression also failed before its fix, with From retaining
`2026-03-01` on an already-unfiltered URL. It asserts every reset control and exact
per-currency totals after a subsequent Apply.

A third test pins the choice of `onNavigate` over `onClick`: modifier-clicking Clear
opens the all-time report in a new tab while this tab keeps its applied period and its
unsubmitted draft. Under `onClick` the draft is wiped, and no other test notices.

Tests use the existing synthetic dataset and an isolated local database. Temporary
local test-port overrides are not part of this change. No production records or
credentials are included in fixtures or this note.
