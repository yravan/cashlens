# 3.6.1 Transaction History — Bounded Design

Status: research/design only; no branch or repo changes.

## Existing seams and dependency

- Promise: chronological searchable list; account, category, date, and amount filters; source and status on every row (`FEATURES.md:114`).
- Current route is an authenticated count placeholder (`apps/web/app/(app)/transactions/page.tsx:8-25`).
- Transaction fields are `id`, `userId`, `accountId`, `amountMinor`, `currency`, `date`, `description`, `merchant`, `status`, `source`, `sourceId`, and timestamps (`apps/web/lib/db/schema.ts:178-193`). Status is `pending | posted` (`schema.ts:66-69`); source is `plaid | manual | import` (`schema.ts:52-56`).
- Accounts provide name, type, subtype, mask, currency, and source (`schema.ts:139-154`).
- No category column, table, or transaction-category relation exists. The category filter cannot be implemented honestly before 4.1.1 without taking that leaf's schema decisions.
- DAL convention is `requireUser()` then `withRequestScope(clerkUserId)` plus explicit `userId` predicates (`apps/web/lib/data/ledger.ts:8-20,23-39`). Transactions and accounts have own-row RLS (`schema.ts:71-77,170,207`).
- Seed coverage: 16 demo rows across USD/EUR and five accounts; two neighbor rows; one pending row; all three sources (`apps/web/db/seed/dataset.ts:27-33,62-81`). `ExpectedPersona` has no categories (`dataset.ts:100-110`).

## Required ruling

Move 4.1.1 before 3.6.1 in the MVP path in its own small `FEATURES.md` commit, then build 3.6.1 against the real taxonomy/assignment interface. A hidden, disabled, or no-op category filter would not satisfy 3.6.1; inventing a category string here would steal 4.1.1 and create rework.

## DAL and URL boundary

Add one authenticated `transactionHistory(filters)` DAL returning rows, own account/category choices, total count, page, and page count. Each row carries date, description, merchant, signed minor amount, currency, status, source, account id/name, and the category display contract from 4.1.1. Identity stays internal: `requireUser()` → `withRequestScope()` → explicit own-user predicates; callers never supply a user id.

Validate a closed URL schema before SQL:

- `q`: trimmed 1–100 character literal substring, case-insensitive over merchant and description.
- `account` / `category`: one validated UUID each; cross-user account returns no rows, never an existence signal.
- `from` / `to`: strict inclusive ISO dates with `from <= to`.
- `currency`: strict uppercase ISO-style code.
- `min` / `max`: non-negative decimal major-unit strings accepted only with `currency`, converted exactly to minor units, with `min <= max`.
- `page`: positive integer, default 1; fixed page size 50.

Malformed combinations never reach SQL; the page preserves controls and renders an accessible filter error. GET parameters keep searches shareable and back-button safe.

## Search, ordering, and pagination

Amount filters compare absolute magnitude within the selected currency, so unlike currencies are never compared and purchases do not require users to enter negative values. Search is literal substring, not global/fuzzy search. Default order is `date DESC`, then `createdAt DESC`, then `id DESC`; status never distorts chronology. Offset pagination is sufficient for a 730-day personal ledger and simpler than cursor state; Previous/Next links preserve every active filter.

## Exact result and page contract

`transactionHistory(filters)` returns:

- `rows`: transaction id, date, description, nullable merchant, signed `amountMinor`, currency, status, source, account id/name, and the nullable category id/name contract introduced by 4.1.1;
- `filters`: own account choices, own category choices, and currencies represented in the user's ledger;
- `total`, `page`, and `pageCount`.

The page uses a native GET filter form: search input; account and category selects; inclusive from/to date inputs; currency plus min/max amount inputs; Apply and Clear actions. Results are a semantic chronological list with date, merchant-or-description, account/category context, formatted signed amount, and textual source/status on every row. Use tabular numerals and keep meaning out of color alone.

Distinct states:

- no ledger rows: onboarding-oriented empty state;
- valid filters with no matches: keep controls and offer Clear filters;
- invalid query: inline accessible error and no SQL execution;
- `loading.tsx`: same list/filter geometry without fabricated values;
- `error.tsx`: generic retry boundary with no server detail.

At 320 CSS px, metadata stacks and no filter or row field disappears. Pagination and filter updates remain ordinary links/GET navigation, preserving back-button behavior and shareable URLs.

## Security and query shape

The route parser accepts only the closed schema above; unknown or repeated scalar parameters are rejected rather than silently widening the query. UUID syntax, dates, decimal precision, safe-integer conversion, and page bounds are validated before the DAL. A syntactically valid id owned by another user yields the same empty result as an unknown id.

The DAL derives identity through `requireUser()` and performs both row and filter-option queries inside `withRequestScope`; every transaction/account/category predicate is explicitly user-scoped in addition to RLS. Existing `transactions_user_date_idx` and `transactions_account_date_idx` cover the primary paths. User-local literal search and amount predicates may scan the bounded personal ledger; add no speculative index or dependency until profiling requires one.

## Behavioral verification

- Pure boundary cases: valid canonicalization; unknown/repeated params; UUIDs; inclusive dates and reversed ranges; decimal/exponent/safe-integer amount conversion; currency-required amount filters; page bounds.
- Real-Postgres API/DAL tests: exact canonical chronology and fields; literal merchant/description search; account, category, date, amount/currency, and combined filters; stable pagination ties; empty results; signed-out rejection; user-B rows/options never visible and cross-user ids disclose nothing.
- Browser coverage: exact seeded first page, source and status text, one combined GET-filter flow, filter persistence across pagination/back navigation, no neighbor content, empty/no-match behavior, and mobile reflow. Assertions scope rows to their result list rather than matching page-wide text.
- Red proof: new tests first fail because the history seam/filter behavior is absent; the isolation test must also fail under a controlled RLS-disable mutation and pass again after byte-identical restoration.
- Final gate: lint, typecheck, full API, full e2e, build, and an authenticated desktop/mobile exercise.

## Explicit deferrals

No fuzzy/global search (3.6.3), transaction detail/editing (3.6.2), category assignment controls beyond consuming 4.1.1, implicit FX or cross-currency amount comparison, alternative sorting, infinite scroll, export, bulk actions, or transaction-derived balances. Pending/posted rows share chronology; status is displayed, not used as a hidden sort key.

## Bounded implementation sequence after approval

1. In its own small commit, reorder MVP path so 4.1.1 precedes 3.6.1.
2. Build and merge 4.1.1 under its own leaf scope and review gate.
3. Build 3.6.1 against the real category interface: boundary parser/tests, authenticated DAL/API behavior, route UI/states, browser coverage, mutation proof, full verification, and independent post-PR review.

This is a dependency correction, not extra 3.6.1 scope: implementing history first would either omit a promised filter or invent the next leaf's schema.
