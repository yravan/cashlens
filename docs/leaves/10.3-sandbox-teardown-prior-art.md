# 10.3 — sandbox Item teardown: prior art and decision

The real Plaid e2e suite creates provider Items but cannot read their vaulted
access tokens. A database-only teardown can remove the local credential and
connection while leaving the provider resource alive. That is a provider
resource/lifecycle leak, not merely test-only state cleanup; this document does
not establish whether any Sandbox billing is incurred.

## External sources surveyed

|---:|---|---|
| 1 | [Playwright authentication](https://playwright.dev/docs/auth) | Authentication state is shared through storage state; retain the repo's page-fixture seam rather than inventing a second login path. |
| 2 | [Playwright fixtures](https://playwright.dev/docs/test-fixtures) | Test-scoped fixtures are torn down after each test, and hooks can use the same fixtures; adopt `afterEach({ page })` for provider teardown. |

| 6 | [Plaid Items API](https://plaid.com/docs/api/items/) | `/item/remove` invalidates the access token and is the documented disconnect endpoint; require it before deleting local credentials. |
| 7 | [Plaid Sandbox API](https://plaid.com/docs/api/sandbox/) | `/sandbox/public_token/create` creates a new Sandbox Item, so every exchanged test token is a provider resource that needs teardown. |
| 8 | [Plaid Sandbox overview](https://plaid.com/docs/sandbox/) | Plaid explicitly recommends the direct Sandbox API for automated suites; keep the test's Link bypass and make teardown equally explicit. |
| 9 | [Plaid Link API](https://plaid.com/docs/api/link/) | A public token is exchanged for an access token in the normal flow; the exchanged token, rather than an unexchanged token, defines teardown ownership. |

## Decision

Use an `afterEach` hook in each real Sandbox spec with the live page fixture and
one shared cleanup helper. It enumerates only user A's
credentialed connections, refuses any state other than `active` (reporting only
the count), and invokes
the authenticated disconnect route with purge enabled. Requests disable
redirect following and require a JSON 200 response; only an actual 307/308/401
auth rejection triggers an authenticated `/accounts` navigation and an exact
Accounts-heading readiness check before one retry. The raw SQL
cleanup remains behind an owner-scoped zero-credential guard and is retained as
the suite-level `afterAll` fail-closed check.

The spec also inserts a synthetic, non-provider credential and asserts that the
raw cleanup rejects while both local rows remain unchanged. Existing connection
management/API coverage supplies the real provider-first disconnect behavior;
the synthetic case isolates the destructive guard without inventing a provider
mock or exposing a real credential.

This deliberately does not guarantee cleanup after process termination or CI
container loss; those remain residual operational risks. It does not act on
unexchanged public tokens, which do not create an exchanged Item owned by the
app, and does not age or recover future cleanup states. An unhandled
credentialed state fails visibly and preserves its local credential for
recovery.
