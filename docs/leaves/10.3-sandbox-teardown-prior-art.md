# 10.3 — sandbox Item teardown: prior art and decision

The real Plaid e2e suite creates provider Items but cannot read their vaulted
access tokens. A database-only teardown can remove the local credential and
connection while leaving the provider resource alive. That is a provider
resource/lifecycle leak, not merely test-only state cleanup; this document does
not establish whether any Sandbox billing is incurred.

## Existing sources in this repository

| Source | Constraint adopted |
|---|---|
| [`apps/web/e2e/connections.signed-in.spec.ts`](../../apps/web/e2e/connections.signed-in.spec.ts) | Provider-backed connections are disconnected through the authenticated route before raw cleanup; cleanup refuses while credentials remain. |
| [`apps/web/lib/data/plaid.ts`](../../apps/web/lib/data/plaid.ts) | Disconnect is remote-first: `/item/remove` must succeed (or report `ITEM_NOT_FOUND`) before local credential deletion. |
| [`docs/leaves/10.3-e2e-session-lifetime-prior-art.md`](10.3-e2e-session-lifetime-prior-art.md) | A page context can refresh Clerk through navigation; an API request context cannot. Redirect-following responses must not be treated as authenticated API success. |
| [`apps/web/e2e/plaid.signed-in.spec.ts`](../../apps/web/e2e/plaid.signed-in.spec.ts) | The Plaid spec owns only Clerk user A's rows and already uses the page request context for authenticated route calls. |

## Decision

Use one `afterEach` hook with the live page fixture. It enumerates only user A's
credentialed connections, refuses any state other than `active` (reporting only
the count), and invokes
the authenticated disconnect route with purge enabled. Requests disable
redirect following and require a JSON 200 response; only an actual 307/308/401
auth rejection triggers an authenticated `/accounts` navigation and an exact
Accounts-heading readiness check before one retry. The raw SQL
cleanup remains behind an owner-scoped zero-credential guard and is retained as
the suite-level `afterAll` fail-closed check.

The spec also inserts a synthetic, non-provider credential and asserts that the
raw cleanup rejects while both local rows remain unchanged. Existing connection
management/API coverage supplies the real provider-first disconnect behavior;
the synthetic case isolates the destructive guard without inventing a provider
mock or exposing a real credential.

This deliberately does not guarantee cleanup after process termination or CI
container loss; those remain residual operational risks. It does not act on
unexchanged public tokens, which do not create an exchanged Item owned by the
app, and does not age or recover future cleanup states. An unhandled
credentialed state fails visibly and preserves its local credential for
recovery.

## Local validation

- Full API suite: 388 tests across 29 files passed (89.51s).
- Focused real Sandbox browser suite: 6 passed (47.6s), including both
  exchanged-Item flows and the synthetic credential guard.
- Removing the raw-cleanup guard made the synthetic regression fail because
  cleanup resolved instead of rejecting; the mutation was restored.
- Full browser suite: 88 passed, 2 failed (2.1m). One failure was the existing
  health spec's hardcoded port 3100 while this isolated preview used 3114.
  With that local-only URL corrected, the focused health suite passed 4/4
  (7.5s). All temporary port edits were restored.
- The other full-suite failure was the known backfill-readiness race: status
  reported completion while transaction count was zero. PR63 addresses this;
  this branch is based on PR71 and does not include that correction. Full
  integrated validation remains required rather than retrying away the race.
- Build, lint, and typecheck passed. Independent review and PR CI remain pending.
