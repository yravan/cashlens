# 2.2.2 Statement File Import — Prior Art

> Upload CSV or statement exports to backfill accounts a connection can't reach; rows land in the ledger like any other source.

Survey date: 2026-09-12. Design: [`2.2.2-statement-import-design.md`](./2.2.2-statement-import-design.md).

## Questions the survey had to answer

1. Which file formats do comparable products accept, and which one carries the most value per line of code?
2. How do importers map a bank's arbitrary columns onto date, amount, and description, and who decides when the mapping is ambiguous (date order, sign, two amount columns)?
3. What makes an import idempotent: how is "already imported" decided, and what breaks each scheme?
4. Do importers match imported rows against hand-entered ones, and how?
5. Where does parsing happen (browser or server), and what does that mean for the upload risk surface, size caps, and encodings?
6. What happens after a wrong import?
7. Which platform limits bind on Vercel and Next.js?

## Patterns adopted

- **Parse in the browser, post typed rows** (Lunch Money's "parsed in the browser and never stored"; Actual and GnuCash parse locally): the file never reaches the server; the route receives the same closed JSON shape the 2.2.1 manual-transaction route already validates (ISO date, decimal amount string, trimmed description). No multipart, no filename, no stored file, no encoding negotiation on the server.
- **User-confirmed mapping with guessed defaults and a live preview** (Actual's green date, Lunch Money steps 2–3, GnuCash preview, Tiller field mapping, Maybe): header names pre-select the date, amount, and description columns; the person confirms against the first parsed rows.
- **Explicit date order and sign** (GnuCash, Maybe, Actual "Flip amount", YNAB swap, Tiller reversed polarity): the form states the assumption; nothing is inferred from locale.
- **Three amount layouts** (Lunch Money, YNAB Outflow/Inflow, GnuCash Deposit/Withdrawal, MMEX): one signed column or two positive columns, plus a flip; parentheses negatives and thousands separators normalized deterministically (Maybe's number formats, Lunch Money's changelog).
- **Deterministic content identity with an occurrence counter** (YNAB `import_id`, Lunch Money's exact tuple, Firefly's normalized hash): `source_id` derives from date, minor amount, normalized description, and the row's occurrence among identical tuples in the file; the existing `(account_id, source, source_id)` unique index plus insert-or-ignore (the 2.1.3 sync pattern) makes re-imports and overlapping exports no-ops. Content-based, never positional (hledger's `.latest` bugs); normalized, never a raw-line checksum (ledger, Firefly's capitalization weakness).
- **Identical rows in one file both land** (hledger's rule; YNAB's occurrence): the counter, not a "duplicate lines" filter.
- **Caps on rows and bytes, enforced while consuming** (Lunch Money 3 MB / 10,000 rows, Vercel 4.5 MB, Server Actions 1 MB, the 2.1.4 loop).
- **Malformed rows block the import and are listed** (Lunch Money, GnuCash's opt-in "Skip Errors"): nothing is silently dropped.
- **No categories from files** (YNAB): rows land uncategorized and 4.2.1 picks them up.
- **Report inserted and skipped** (YNAB `duplicate_import_ids`, Lunch Money's duplicate list).
- **Balance disclosure** (Lunch Money's estimate, Beancount's assertion): the preview counts the rows that will move the 2.2.3 anchor balance.
- **Recovery by deletion** (Tiller's import tag): imported rows become deletable through the 2.2.1 delete path (founder ruling, 2026-09-13).

## Patterns rejected for this leaf

- **Server-side file upload** (multipart, `request.formData()`, blob storage): every OWASP rule and the Vercel cap exist because a file reaches the server; nothing here needs to.
- **OFX/QFX/QIF/CAMT** (Actual, YNAB): no maintained parser to adopt, OFX 1.x is SGML, and CSV is every bank's lowest common denominator; FITID-based identity is the reason to add OFX later.
- **Fuzzy matching against hand-entered rows** (YNAB ±10 days, Actual ±7 days, GnuCash ±42 days): judgment over messy data with silent-merge failure modes; 3.3.2's cross-source merge owns it.
- **Positional dedup state** (hledger `.latest`) and **raw-line checksums** (ledger `--rich-data`, Firefly classic).
- **LLM column mapping**: it would ship sample rows to a third party to answer a question the person can answer from the preview in one click.
- **Saved per-account mapping presets** (Lunch Money, GnuCash, Maybe templates): new storage for a convenience; the mapping takes seconds.
- **Re-import-deleted toggles and tombstones** (Actual, Firefly): 3.3.2 territory; a deleted import row re-imports if the file is uploaded again, and the UI says so.
- **Balance adjustment at the end of an import** (Lunch Money): the 2.2.3 anchor already defines the shown balance; adjustments are 3.2.x.
- **Categorization at import** (GnuCash Bayesian mapping, smart_importer): 4.2.1.
- **CSV-injection sanitizing**: not a risk on import; noted for any future export leaf.
- **PDF statements** (Lunch Money via a third-party converter): out of scope.
