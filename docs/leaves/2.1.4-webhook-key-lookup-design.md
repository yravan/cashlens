# 2.1.4 Webhook verification-key lookup hardening

## Scope and observed failure

This correction stays inside Plaid webhook authentication. It does not add a general
rate-limit service, queue, database table, shared cache, IP policy, or background job.

A local zero-secret probe called the production `verifyPlaidWebhook` function through
the existing Plaid substitute with 20 concurrent JWTs carrying the same well-shaped,
unknown `kid`. All 20 requests called `/webhook_verification_key/get`, then all failed
verification. The existing negative cache begins helping only after the first request
settles. An attacker can therefore amplify provider work with either concurrent copies
of one `kid` or a stream of distinct well-shaped values. The positive-key map is also
unbounded, and fetching one served new key re-fetches every cached unexpired key.

The invariant is narrower than global denial-of-service prevention:

> Within one warm application instance, concurrent lookup of one key starts at most one
> provider request, verifier memory is bounded, and attacker-selected novel key IDs can
> start only bounded provider work. Every webhook remains fail closed.

Cold starts and horizontally scaled instances each have independent state. Edge or
platform-wide controls remain a separate operational defense.

## Primary sources and decisions

| # | Primary source | Relevant contract | Decision |
|---:|---|---|---|
| 1 | [Plaid webhook verification](https://plaid.com/docs/api/webhooks/webhook-verification/) | Read `kid` from the unverified JWT header, fetch its JWK, require ES256, reject expired keys, verify the signature, enforce a five-minute `iat`, and compare the body SHA-256 in constant time. Plaid's examples cache keys. | Preserve the verification order and five-minute checks. Treat `kid` as an untrusted lookup selector, not proof of issuer identity. |
| 2 | [Plaid verification-key endpoint](https://plaid.com/docs/api/webhooks/webhook-verification/#webhook_verification_keyget) | `/webhook_verification_key/get` accepts one key ID and returns JWK metadata including `kid`, `alg`, `use`, curve data, and `expired_at`. | Validate that returned metadata matches the requested `kid` and the expected ES256 signing-key shape before caching. |
| 3 | [Plaid webhook retries](https://plaid.com/docs/api/webhooks/#webhook-retries) | Plaid retries non-200 responses for up to 24 hours; a 429 with `Retry-After` controls the next retry, capped at four hours. Excessive rejection can stop retries. | Definitive authentication failures remain 401. Local admission overload returns 429 with a short `Retry-After`; transient provider failure returns retryable 503. Never acknowledge an unverified body. |
| 4 | [Plaid invalid-input errors](https://plaid.com/docs/errors/invalid-input/) and [rate-limit errors](https://plaid.com/docs/errors/rate-limit-exceeded/) | Plaid documents `INVALID_INPUT / INVALID_WEBHOOK_VERIFICATION_KEY_ID` for an invalid key ID and exposes rate limiting as a distinct error class. | Negative-cache only that exact invalid-key pair. Treat every other provider error as temporary verification unavailability. |
| 5 | [RFC 7515, JWS](https://datatracker.ietf.org/doc/html/rfc7515#section-4.1.4) | `kid` is only a hint for selecting a verification key; unsupported algorithms or missing keys make a JWS invalid. | Shape-check `alg` and `kid` before any allocation or network work; never trust `kid` beyond map selection. |
| 6 | [RFC 7517, JWK](https://datatracker.ietf.org/doc/html/rfc7517#section-4.5) | `kid` matches a specific JWK and supports rollover; its structure is otherwise unspecified. | Keep Plaid's key rollover working. Do not impose semantic prefixes or assume only one lifetime key. |
| 7 | [RFC 8725, JWT BCP](https://datatracker.ietf.org/doc/html/rfc8725#section-3.1) | Applications must perform algorithm verification and validate all cryptographic operations. | Continue pinning ES256 in both the protected header and verifier; validate fetched JWK metadata before import. |
| 8 | [RFC 9110, 503 and Retry-After](https://www.rfc-editor.org/rfc/rfc9110.html#status.503) | 503 represents temporary inability to serve; `Retry-After` can indicate when service may recover. | Use 503 only when a lookup was admitted but Plaid or transport failed transiently. |
| 9 | [RFC 6585, 429](https://www.rfc-editor.org/rfc/rfc6585#section-4) | 429 represents excessive request rate and may carry `Retry-After`; it must not be cached. | Use 429 for verifier-local lookup admission exhaustion, with no cacheable response. |
| 10 | [ECMAScript Promise specification](https://tc39.es/ecma262/multipage/control-abstraction-objects.html#sec-promise-objects) | A Promise is a shareable eventual result, and reactions can await the same settlement. | Store one Promise per `kid` before starting the provider call; all same-key waiters await it; delete it in `finally`. |
| 11 | [Go `singleflight`](https://pkg.go.dev/golang.org/x/sync/singleflight) | The standard package names this pattern duplicate function-call suppression and guarantees one in-flight execution for a key. | Implement the few-line keyed-Promise equivalent locally; do not add a dependency or generic abstraction. |
| 12 | [Vercel Fluid compute](https://vercel.com/docs/fluid-compute#optimized-concurrency) | Multiple invocations can execute concurrently in one function instance and share its global process state. | Module-global maps need concurrency-safe ordering. Their bounds are per instance only. |
| 13 | [Vercel Functions limits](https://vercel.com/docs/functions/limitations) | Function duration, memory, and scaling have platform limits independent of application caches. | Finish lookup well inside Plaid's ten-second delivery timeout; do not describe an in-process counter as a deployment-wide quota. |
| 14 | [OWASP denial-of-service guidance](https://cheatsheetseries.owasp.org/cheatsheets/Denial_of_Service_Cheat_Sheet.html) | Perform cheap validation first, prevent input-driven resource allocation, bound expensive work, and layer infrastructure and application controls. | Retain the current cheap header/body limits, then bound maps, concurrency, and attacker-selected outbound calls. |

## Minimal correction

Keep all state private to `lib/plaid/webhook.ts` and reset it through the existing test
helper.

1. Replace the two bare maps with one small verifier state containing positive entries,
   negative entries, in-flight Promises, a novel-key token bucket, and counters for total
   and novel lookup concurrency.
2. Check the positive and negative caches before admission. Then check `inFlight.get(kid)`
   and join it before consuming a token or concurrency slot. Insert the Promise in the
   map synchronously before its provider call begins and remove only that same Promise in
   `finally`.
3. Bound positive keys to 8 and negative misses to 256 with insertion-order LRU eviction.
   A hit refreshes recency. These are conservative application constants chosen to keep
   input from growing process memory without limit; no normal-rate claim is available.
4. Give positive metadata a five-minute freshness interval. A fresh cached key verifies
   with no lookup. On expiry, refresh that same `kid` through singleflight. Stop the
   current fan-out that refreshes every cached key when one new key appears. This changes
   worst-case work from `1 + cached keys` to one request and bounds how long a formerly
   unexpired cached key can be accepted after Plaid marks it expired.
5. Permit at most 2 verification-key requests in flight per instance, of which at most 1
   may be for an uncached `kid`. This reserves capacity for refreshing an already-known
   signing key while novel-key traffic is present.
6. Permit at most 8 uncached distinct-key lookup starts and 8 stale-known refresh starts
   in separate rolling 60-second budgets per instance. Same-key joiners consume neither
   another token nor another concurrency slot. A served legitimate rollover key consumes
   one novel token and is cached. Separate budgets preserve the reserved known-key path
   without letting repeated transient refresh failures cause unbounded work. Total
   outbound starts are therefore at most 16 per rolling minute per warm instance. Use
   tiny timestamp deques rather than timers; prune them on admission.
7. Cache a definitive unknown-key response for five minutes. Do not cache timeouts,
   transport failures, Plaid 429/5xx errors, malformed provider responses, or local
   admission rejection. The Plaid client boundary may need a narrow error classifier;
   raw SDK errors and request configuration must remain contained.
8. Validate a served key before caching: returned `kid` equals the requested ID, `alg` is
   ES256, `kty` is EC, `crv` is P-256, `use` is `sig`, coordinates are present, and an
   `expired_at` key is rejected. Invalid provider metadata is temporary verification
   failure, not negative evidence about the requested ID.
9. Add a retryable verifier error distinct from `WebhookVerificationError`. Admission
   exhaustion maps to `429 { error: "verification_busy" }` with `Retry-After: 30` and
   `Cache-Control: no-store`. An admitted transient lookup failure maps to
   `503 { error: "verification_unavailable" }` with `Retry-After: 30` and no-store.
   Malformed JWTs, unknown keys, expired keys, bad signatures, bad times, and hash
   mismatches remain indistinguishable `401 { error: "unverified" }` responses.
10. Log only a bounded reason enum and aggregate/counter fields. Never log JWTs, bodies,
    `kid` values, JWK coordinates, Plaid request configuration, or secrets. The new
    overload paths do no database work and never parse or act on the webhook body.

The numeric limits are application constants, not provider facts. They intentionally
favor legitimate rollover (normally one novel key) while making one warm instance's
outbound work and memory calculable. Adjust them only from observed legitimate traffic;
do not make them environment knobs or a new configuration surface in this leaf.

## State transitions

```text
malformed header ───────────────────────────────────────────────> 401
fresh positive hit ───────────────────────────────> verify JWT/body
fresh negative hit ─────────────────────────────────────────────> 401
same kid already in flight ───────────────> await the same result
known stale kid + refresh capacity ───────> one provider lookup
novel kid + token/concurrency capacity ───> one provider lookup
admission full ───────────────────────────────────────> 429 retry
provider/transport temporarily unavailable ──────────> 503 retry
definitive unknown key ───────────────> negative cache ─────────> 401
valid served key ─────────────────────> positive cache ─> verify
```

No response reaches webhook parsing or DAL work until signature, time, and body hash all
verify. `ownersOfItem` and its active-connection/RLS constraints do not change.

## Behavioral tests

Use the existing true-external Plaid harness and production verifier interface. The core
tests are pure and need no database.

1. Reproduce the confirmed regression: 20 concurrent requests for one delayed unknown
   `kid` produce exactly one provider lookup and 20 identical authentication failures.
   Remove in-flight coalescing and observe 20 calls.
2. Twenty concurrent requests for one delayed valid new key produce one lookup and all
   verify; a later request is a positive-cache hit.
3. Distinct novel IDs can start no more than one lookup concurrently and no more than
   eight in 60 seconds; excess requests are 429 with exact `Retry-After` and no-store.
4. A known key whose metadata is stale can refresh in the reserved second slot while an
   unknown-key lookup is blocked. It does not consume the novel-key budget.
5. Provider resolution of one key does not re-fetch any other cached key. A stale key is
   refreshed only when that key is used.
6. A definitive unknown response is negative-cached for five minutes. A transient 429,
   5xx, timeout, or malformed provider response is not; retry can later succeed.
7. Every Promise settles by deleting its in-flight entry and releasing counters, for
   success, definitive miss, provider error, malformed JWK, and thrown verifier error.
8. LRU tests insert beyond 8 positive and 256 negative entries and assert exact bounds
   and deterministic eviction. The in-flight map never exceeds the concurrency bound.
9. Returned JWKs with mismatched `kid`, wrong `alg`/`kty`/`crv`/`use`, missing points, or
   malformed expiry metadata never enter the positive cache. A structurally valid key
   marked expired may be cached, but is rejected before signature verification.
10. Cached metadata expiry uses a fake clock: refresh occurs at the boundary, concurrent
    refreshes coalesce, transient refresh failure fails closed, and recovery succeeds.
11. Route-level no-DB tests pin 401 versus 429 versus 503 bodies/headers and prove none of
    those cases reaches JSON parsing, owner lookup, sync, or ITEM actions.
12. Secret sweeps inspect every rejection/overload error and response; none contains the
    JWT, body, `kid`, JWK, Plaid secret, access token, or raw SDK request configuration.
13. A no-database loopback server accepts the actual Plaid 46 SDK request and deliberately
    never responds. The production `getWebhookVerificationKey` call aborts near five
    seconds, the server observes the closed request, and a following lookup proves both
    concurrency counters were released. Do not replace this with an options-object test.

Mutation proof should delete the in-flight insertion, remove the novel budget, replace
LRU eviction with unbounded insertion, or negative-cache a transient provider error; one
focused test must fail for each invariant.

## Validation evidence

On 2026-09-10, the normal Vitest harness passed 33 tests across the webhook route
and lookup files in 29.56s, using isolated local PostgreSQL 16 with the repo's
actual roles, migrations, and RLS. The lookup tests include the installed Plaid
SDK/Axios loopback cancellation case, not merely an assertion on request options.
The original pre-fix probe observed 20 provider calls for one concurrent unknown
key; the implemented test observes one. No production webhook or real provider
credential was used by these tests.

Independent Sol static review found no blocking defect in the changed behavior.
The full normal API suite subsequently passed 410 tests across 30 files in
99.80s. The positive-cache test was then strengthened to hit the oldest key
before inserting the ninth key, proving that a hit refreshes eviction order.
Four isolated mutations each produced the expected RED: preserving insertion
order on a hit, ignoring an existing in-flight lookup, removing the novel-start
budget, and negative-caching transient provider errors. Every mutation was
removed; all 19 lookup tests then passed in 6.15s. One incorrectly named test
filter selected zero tests and was discarded, not counted as mutation evidence.
Production build, lint, and typecheck also passed on the main-based branch.
Remaining validation includes the final full suite after the assertion-only
change and protected-base rebase, browser exercise, and post-PR review/CI.
The route tests assert failure responses and absence of processing; the earlier
no-JSON/no-owner-lookup invariant is also supported by control-flow inspection,
not separate parser/SELECT instrumentation. No completion claim rests on that
instrumentation having been run.

The existing route's pre-cap body buffering is a separately confirmed defect
fixed in PR #64; this lookup change does not claim to fix request-body admission.

## Risks and open decisions

- **Fleet amplification remains.** An attacker can distribute requests across cold or
  scaled instances. This patch gives a precise per-instance bound only. A Vercel
  Firewall rule or shared limiter may be warranted from production telemetry, but is
  outside 2.1.4 and must preserve Plaid delivery.
- **Legitimate rollover during attack can be delayed.** Its first lookup can receive 429
  when the novel slot/budget is exhausted. Plaid documents retries and honors
  `Retry-After`; fail-closed delay is preferable to unbounded authenticated API calls.
- **Unknown-key classification must be confirmed against the Plaid SDK error code.** If
  the response is not exactly documented `INVALID_INPUT /
  INVALID_WEBHOOK_VERIFICATION_KEY_ID`, omit the negative cache. Singleflight and
  admission still bound work.
- **Lookup cancellation is endpoint-local.** Plaid SDK 46 accepts a second request-options
  argument and merges it over global Axios options. Pass both `timeout: 5000` and
  `signal: AbortSignal.timeout(5000)` so the request actively cancels below Plaid's
  ten-second delivery window. A bare `Promise.race` would leave work alive.
- **Five-minute metadata freshness is a local security/availability tradeoff.** It can
  accept a just-expired key for at most that additional interval, while refreshing every
  request would recreate provider dependence. Keep the interval aligned with Plaid's
  maximum accepted JWT age unless Plaid publishes a stronger cache directive.
- **401 rejection ratio is inherited.** Malicious invalid traffic can raise Plaid's
  observed rejection ratio only if it reaches the same endpoint attribution. Do not ack
  unverifiable traffic to manipulate this metric; platform filtering is the proper
  outer layer.

## Explicit non-goals

No Redis/KV, database-backed quota, provider-generic JWK manager, IP allowlist, durable
challenge, queue, cron, new dependency, webhook payload persistence, asynchronous ack,
or global availability claim. Do not alter valid-webhook processing, replay semantics,
active-connection ownership mapping, transaction synchronization, or ITEM handling.
