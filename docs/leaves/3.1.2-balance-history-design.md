# 3.1.2 Balance History — Approved Design

Status: Approved by the founder on 2026-09-16.

Prior art: [`3.1.2-prior-art.md`](./3.1.2-prior-art.md)

## Scope

> Daily balance snapshots per account, enabling trends and net worth over time.

This leaf creates the account-level historical truth that later trends and net-worth features can consume. It owns observation capture, manual-anchor history, a daily range-read contract, freshness/provenance, idempotency, isolation, and recovery semantics.

It does not own a net-worth total, FX conversion, charts, account-detail UI, institution health history, transaction reconstruction for provider accounts, or a platform-wide scheduler.

## Current constraints

- `account_balances` has `account_id` as its primary key and therefore holds exactly one mutable current row per account.
- Provider connection and balance refresh overwrite that row. Its `as_of` is currently the Cash Lens acquisition instant, not a universally supplied provider event time.
- Plaid transaction activity and `SYNC_UPDATES_AVAILABLE` do not prove a fresh balance exists.
- Manual `account_balances.current_minor` is the raw user-entered anchor. `accountOverview()` derives the displayed value from posted transactions after (`reported_on`, `as_of`), adding for held accounts and subtracting for owed accounts.
- Account currency is immutable in the current product. Missing current balance remains unavailable rather than falling back to available or zero.
- Runtime access uses non-owner `cashlens_app`, forced RLS, `withRequestScope`, and identity derived from `auth()`. That role cannot enumerate every user or connection.
- Production runs on Vercel Functions and Neon. Vercel Cron and durable work are at-least-once triggers, not exactly-once storage guarantees.

## Approved product model

### One corrected daily observation per account

Keep `account_balances` unchanged as the current projection. Add `account_balance_snapshots` as a separate user-owned relation with one row per `(account_id, snapshot_day)`.

A snapshot is an observed balance, not a guarantee that the institution refreshed at a particular cutoff. A later, more authoritative observation on the same logical day may correct the row atomically. Intraday observations are not retained as a separate audit log.

Provider rows hold the provider current balance exactly as Cash Lens received it. Manual rows hold the raw user-entered anchor. Manual effective daily values are derived at read time from anchor history plus posted transactions, using the already-approved 2.2.3 rule. This preserves both facts without materializing values that would become stale after a transaction edit, deletion, or backdated import.

### Proposed canonical relation

```text
account_balance_snapshots
  account_id        uuid        not null
  user_id           uuid        not null
  snapshot_day      date        not null
  current_minor     bigint      not null
  currency          varchar(3)  not null
  source             enum        not null  -- provider | manual_anchor
  capture_reason     enum        not null  -- event | bootstrap | reconciliation
  observed_at       timestamptz not null
  provider_as_of    timestamptz null
  created_at        timestamptz not null default now()
  updated_at        timestamptz not null default now()

  primary key (account_id, snapshot_day)
  foreign key (account_id, user_id)
    references accounts(id, user_id)
    on delete cascade
  index (user_id, snapshot_day, account_id)
```

Field semantics:

- `snapshot_day`: the logical date represented by the row. Under the approved rule, a manual anchor uses its existing explicit `reported_on`; a timestamped provider observation uses the UTC calendar date of `observed_at`.
- `current_minor`: the usable current balance. A null provider current creates no row. Zero is a valid observed value.
- `currency`: copied from the immutable account currency so every historical amount is self-describing and later currency edits cannot silently reinterpret history.
- `source`: `provider` for a provider balance observation; `manual_anchor` for the exact balance entered by the person. Transaction-import source does not create a third balance source because imported transactions belong to the manual anchor's derived series.
- `capture_reason`: `event` for an initial connection, fresh provider refresh, manual create, or manual re-anchor written at its authoritative seam; `bootstrap` for the one-time existing-row migration; `reconciliation` for delayed signed-in catch-up. This identifies how history learned an observation without pretending the capture path changes the underlying balance's freshness.
- `observed_at`: the exact instant Cash Lens acquired the balance from the provider or accepted the manual anchor. Read-time catch-up copies the original current projection's `as_of`; it never substitutes the read time.
- `provider_as_of`: a genuine provider-supplied balance timestamp when one exists. It stays null when the provider does not supply one. Plaid request time must not be written here.
- `created_at` and `updated_at`: first history capture and last same-day correction. They are not provider timestamps.

No `available_minor` or `limit_minor` is stored. They do not answer the leaf's trend/net-worth use case, are not consistently available, and would enlarge both storage and correction semantics. No synthetic-row flag is needed because synthetic rows are never persisted.

### Logical-day policy

The approved MVP rule is deterministic without introducing a profile-timezone subsystem:

- manual anchor: existing browser-supplied and validated `reported_on`;
- provider observation: `(observed_at AT TIME ZONE 'UTC')::date`;
- genuine provider timestamps remain provenance and do not silently change the bucket after capture.

This deliberately treats a date-only manual declaration as authoritative while using UTC for timestamped observations. Institution-local time is rejected because providers do not consistently supply an institution IANA zone. User-local day remains viable only with a persisted IANA timezone, explicit DST-safe boundaries, a rule for zone changes, and a fallback for provider events that arrive before the browser has reported a zone.

The date is always computed explicitly. No `timestamptz::date` may depend on the database session timezone.

## Capture paths

All writes use one owner-scoped DAL primitive that accepts canonical trusted data, not request bodies. It inserts or corrects the account/day row in the same transaction as the corresponding current-state mutation where that is possible.

### Initial provider connection

After `/accounts/get` has produced the server-trusted accounts and current balances, each non-null current value writes both:

- the existing `account_balances` current projection; and
- a `provider` snapshot for the observation day.

The two writes are atomic. A failed history write must not leave a current row that can never be reconciled except by a later read.

### Successful provider balance refresh

A successful `/accounts/balance/get` refresh upserts current projection and daily snapshot together inside one request scope. Provider failure changes neither. Transaction-sync completion or webhook receipt alone writes no balance history.

The approved MVP does not add a paid live-balance call solely to manufacture a calendar row. It captures every genuine balance response the app already obtains. A later product ruling may request at most one live refresh per connection/day, with explicit cost and rate-limit controls.

A fresh response that reports the same amount as yesterday still creates today's observation. An unchanged amount is meaningful when freshness is genuine; equality of amounts is not evidence that the call was redundant.

### Manual create and re-anchor

Manual account creation and every balance re-anchor write the current anchor and a `manual_anchor` snapshot atomically. `snapshot_day` is `reported_on`; `observed_at` is the same database-clock instant as the current anchor's `as_of`.

A later anchor on the same `reported_on` day corrects that day because its `observed_at` is later. Earlier-day anchors remain. Updating an anchor never creates a transaction.

### Signed-in read-time catch-up

A history read may reconcile an existing current projection whose original observation is absent from history:

- provider current: candidate day comes from the original `account_balances.as_of`, never today merely because the page was opened;
- manual current: candidate day comes from `reported_on`, and the raw anchor remains the stored value;
- null current or missing manual `reported_on`: no candidate;
- work is bounded to the accounts already being read and one candidate per account.

This path repairs interrupted or pre-feature captures. It does not fetch a provider, fill a range, or turn stale state into a new observation. The UPSERT makes repeated reads no-ops.

### Scheduled/background capture

No global schedule is part of the approved MVP. Event capture plus read-time reconciliation stays inside existing authentication and RLS boundaries and honestly permits gaps.

If wall-clock capture is selected in a later leaf, it is a separate security capability. The only acceptable shape is an authenticated Cron starter, a least-privileged opaque dispatcher, and bounded per-owner durable work. It must not use the owner/superuser URL, a `BYPASSRLS` role, browser-visible credentials, or workflow/queue payloads containing provider tokens or financial data.

## Idempotency and correction

The primary key is the semantic idempotency key. Capture uses one `INSERT ... ON CONFLICT ... DO UPDATE` statement with a correction predicate.

Candidate ordering:

1. The same underlying observation (`source`, amount, `observed_at`, and `provider_as_of`) is a no-op even when it arrives through a different `capture_reason`; replay never rewrites capture metadata or bumps `updated_at`.
2. For two provider rows with genuine `provider_as_of` values, an older provider time cannot replace a newer one.
3. Otherwise, a later `observed_at` may replace an earlier observation on the same day and carries its own `capture_reason` into the corrected row.
4. The same `observed_at` with contradictory amount, source, or provider time is an invariant conflict, not last-writer-wins. Keep the existing row, emit a sanitized conflict event, and allow a later genuine observation to correct it.

The atomic unique-key write is the correctness boundary under concurrency. A transaction advisory lock may reduce duplicated provider or manual-derivation work, but it cannot replace the unique key and only protects cooperating callers. Existing Plaid cursor compare-and-set behavior remains independent and continues to make overlapping sync runs safe.

A scheduled worker, if selected in a later leaf, also takes a stable transaction-level lock per connection before a provider call/reconciliation attempt, caps concurrency, and treats retries as normal at-least-once execution.

## Manual effective history

Manual history exposes both the reported anchor and the effective daily value without persisting redundant closes.

For each requested day, choose the latest anchor whose `snapshot_day` is on or before that day. Until the next anchor, apply posted transactions after that anchor boundary:

```text
same anchor-day inclusion:
  transaction.date = anchor.snapshot_day
  and transaction.created_at > anchor.observed_at

later-day inclusion:
  transaction.date > anchor.snapshot_day
  and transaction.date <= requested_day

effective balance:
  anchor.current_minor + signed transaction sum  for depository, investment, other
  anchor.current_minor - signed transaction sum  for credit, loan
```

This is the 2.2.3 rule evaluated at a historical day. Transaction edits, deletes, and backdated imports therefore correct subsequent reads automatically. A new anchor resets the series from its day forward. If two anchors share a day, the corrected daily row retains the later anchor and its later same-day cutoff.

The returned point identifies the raw anchor day/amount and marks the displayed value `derived`. Nothing writes a `manual_effective` row. Provider histories never use this transaction derivation.

## Range-read contract

The internal DAL accepts a validated inclusive date range and optional owned account ids. It returns stable account ordering and one point per requested account/day:

```ts
type BalanceHistoryPoint =
  | {
      day: string;
      basis: "observed" | "carried";
      currentMinor: number;
      observedDay: string;
      observedAt: Date;
      providerAsOf: Date | null;
      captureReason: "event" | "bootstrap" | "reconciliation";
    }
  | {
      day: string;
      basis: "derived";
      currentMinor: number;
      anchorMinor: number;
      anchorDay: string;
      anchorObservedAt: Date;
      captureReason: "event" | "bootstrap" | "reconciliation";
    }
  | {
      day: string;
      basis: "unavailable";
      currentMinor: null;
    };

type AccountBalanceHistory = {
  accountId: string;
  accountType: AccountType;
  currency: string;
  points: BalanceHistoryPoint[];
};
```

Provider points:

- row on that day: `observed`;
- no row after a prior observation: copy its amount as `carried`, retaining the original `observedDay`, `observedAt`, and `providerAsOf`;
- before the first usable observation: `unavailable` with a null amount;
- null is never converted to zero.

Manual points:

- an anchor exists but no later qualifying transaction: `derived` with the effective value equal to the anchor;
- qualifying transactions exist: `derived` using the rule above;
- before the first anchor: `unavailable`;
- `anchorMinor` and `anchorDay` expose the raw reported fact without making callers query storage internals.

The contract does not sum accounts. It supplies account type, currency, availability, and provenance so 6.3.2 can apply asset/liability signs, keep currencies separate, show incomplete days honestly, and distinguish stale carry-forward from a fresh observation.

No public arbitrary-history mutation route is introduced. A future GET surface, if needed, uses a closed parser, explicit maximum range, owned account predicates in addition to forced RLS, and byte-identical results for unknown versus cross-user account ids.

## Missing days, backfill, and retention

### Missed days

Stored gaps remain gaps. Provider range reads carry forward the latest prior observation and label it `carried`. Manual values are labeled `derived`. Neither becomes a stored observation.

A missed provider day cannot be repaired after the fact from today's balance. A scheduler can retry a failed current attempt, but after the provider's state changes the old close is unknowable.

### One-time bootstrap

The approved historical bootstrap is at most one row per existing account:

- require non-null `account_balances.current_minor`;
- provider account: day from the existing `as_of` under the selected day rule, source `provider`, observed time from that same `as_of`;
- manual account: require `reported_on`, day from `reported_on`, source `manual_anchor`, observed time from `as_of`;
- currency from the owned account;
- no earlier rows and no copied daily range.

This can be a deterministic migration-time insert from existing trusted columns. Re-running it is conflict-safe. It does not call a provider or expose a runtime all-user role.

### Bounds

A read is bounded to 3,660 inclusive days and the caller's owned accounts. This supports ten years of daily history while preventing an accidental unbounded Cartesian expansion. The internal implementation may page accounts without changing the result contract.

Provider backfill is exactly the one known bootstrap observation. Manual derivation begins only at a stored anchor and ends at the requested day. A future scheduled reconciliation attempt may inspect only bounded stale connection metadata; it still cannot invent past balances.

### Retention

The approved retention is the lifetime of the account. One row per account/day is small, history is the feature's primary data, and deleting old rows would silently corrupt trends. Account purge and whole-user deletion remove snapshots through the composite-FK cascade. The app role receives no standalone history-delete grant.

## Multi-currency and signs

- Every row stores one three-letter account currency. Unlike currencies never share a series or total.
- No exchange rate is stored or inferred in this leaf.
- Provider and manual anchor amounts keep existing Cash Lens semantics: held account types are positive when held; credit/loan current is positive when owed.
- Historical storage does not negate liabilities. The future net-worth consumer applies `+` to assets and `-` to liabilities at aggregation time.
- Currency mismatch between a candidate and its owned account is an invariant failure; no row is written and no amount is logged.

## Security and least privilege

`account_balance_snapshots` is user data and receives the full existing boundary:

- composite `(account_id, user_id)` foreign key to prevent cross-owner attachment;
- own-row `SELECT`, `INSERT`, and `UPDATE` policies plus `FORCE ROW LEVEL SECURITY`;
- explicit owner predicates in every DAL read/write in addition to RLS;
- runtime grants limited to `SELECT`, column-scoped `INSERT` for `account_id`, `user_id`, `snapshot_day`, `current_minor`, `currency`, `source`, `capture_reason`, `observed_at`, and `provider_as_of`, plus column-scoped `UPDATE` of `current_minor`, `capture_reason`, `observed_at`, `provider_as_of`, and `updated_at`;
- no runtime update of `account_id`, `user_id`, `snapshot_day`, `currency`, `source`, or `created_at`;
- no runtime `DELETE` or `TRUNCATE`; account deletion cascades in the database;
- authenticated identity derived by `requireUser()` and `withRequestScope`, never from a body/query owner id;
- no provider token, balance, currency amount, account name, raw payload, or request body in logs;
- sanitized events limited to opaque ids, source, day, counts, and error class. Even day may be omitted from public production logs if it is not needed for action.

Provider secrets remain encrypted at rest and are exposed only inside the existing provider-call seam. History capture receives normalized balance values, never credential material.

A background dispatcher, if approved, is named in the PR as new risk surface. Its role can enumerate only the opaque identifiers required for fan-out. It cannot select financial columns or ciphertext. Each worker re-enters one owner's ordinary scope. Cron authentication, bounds, retries, locks, failure monitoring, and log redaction are behavioral proof, not operational assumptions.

## Failure and recovery behavior

- Provider request fails: current projection and history stay unchanged; sanitized existing provider handling applies.
- Current projection transaction fails: snapshot in that transaction also rolls back.
- Snapshot conflict loses to a newer observation: treat as successful idempotent convergence.
- Equal-time contradictory candidate: preserve existing row, emit sanitized invariant conflict, and surface failure to the initiating trusted path rather than silently choosing.
- Read-time catch-up fails: the history read may return existing data but must expose/log a sanitized catch-up failure; it must not claim the missing observation was persisted.
- Manual derivation encounters no anchor: return unavailable, not zero.
- Provider history has no prior point: return unavailable, not zero.
- Concurrent account purge: composite cascade leaves no orphan; a racing insert either loses the parent relation or is removed with the account.
- Durable work exhausts retries, if later approved: terminal failure remains visible to operations and the next bounded reconciliation may retry. No dead-letter payload contains user financial data.

## Behavioral proof

Implementation begins with observed RED tests and includes mutation proof for the feature's decision points.

### Seed and API/database proof

- Deterministic provider snapshots across multiple days, including one unchanged fresh value, one correction on the same day, one gap, one zero, one unavailable current, USD and EUR accounts, held and owed account types.
- Deterministic manual anchors across days with exact effective values before/after posted transactions, same-day `created_at` cutoff, later re-anchor, backdated import, edited/deleted transaction, and held/owed sign behavior.
- Exact range output for `observed`, `carried`, `derived`, and `unavailable`; no persisted row for carried/derived points.
- Initial connection, live refresh, manual create/re-anchor, one-row bootstrap, and read-time catch-up each write the expected canonical row.
- Replaying every trigger is a no-op; a newer same-day observation corrects; an older observation cannot regress; equal-time contradictory data fails closed.
- Two concurrent captures converge to one correct account/day row.
- Currency remains separated and cannot be changed through the correction grant.
- Account purge cascades history; no independent app-role delete is possible.
- Raw `cashlens_app` queries as user B see and affect zero of user A's snapshots, including unfiltered reads and attempted updates/inserts.
- Runtime privilege assertions pin the exact allowed columns and prove `account_id`, `user_id`, `snapshot_day`, `currency`, `source`, and `created_at` cannot be updated and that delete/truncate remain forbidden.

### Pure-rule proof

- UTC day derivation is independent of the database session timezone.
- Manual anchor-plus-ledger history follows the approved 2.2.3 cutoffs and sign rules for every day in a range.
- Range bounds reject invalid days, reversed ranges, and more than 3,660 days before SQL.

### Mutation proof

At minimum, observe failures after temporarily making each defect and then restore the code byte-for-byte:

- convert missing current to zero;
- stamp read time instead of the original `as_of` during catch-up;
- persist carried points;
- allow an older same-day observation to overwrite a newer one;
- omit `(account_id, snapshot_day)` uniqueness;
- flip the owed-account manual sign;
- include pending manual transactions;
- change the same-day cutoff from `created_at > observed_at` to `>=`;
- combine currencies;
- drop the explicit owner predicate or the raw RLS policy;
- broaden the update/delete grant.

The later implementation gate remains the repository gate: lint, typecheck, build, full API suite, full E2E suite, authenticated desktop and phone exercises, green CI, fresh Opus read-only review, independent Sonnet verification, fixes on the same PR, and no merge.

## Approved rulings

The founder approved every ruling below on 2026-09-16.

| Decision | Approved ruling | Rejected alternative and impact |
|---|---|---|
| Logical day | Explicit manual `reported_on`; UTC day for timestamped provider observations. | User-local requires persisted IANA timezone and zone-change rules. Institution-local is not reliably available. |
| Timezone persistence | Do not add it in this leaf under the UTC recommendation. | Add a user timezone only if user-local daily identity is selected. |
| Correction model | One corrected account/day row; no immutable intraday log. | First-observation-wins can preserve stale values. A raw event log adds a second materializer, retention, and consumer complexity. |
| Manual semantics | Persist raw anchors; derive effective daily closes on read; return both anchor provenance and effective value. | Raw-only is wrong for net worth after transactions. Persisted effective closes require invalidation/recomputation on every transaction mutation. |
| Balance fields | Store `current_minor` only. | Available and limit are distinct, nullable concepts without a trend/net-worth requirement. |
| Unchanged amount | Store it when a genuinely fresh observation occurred. Do not pay for a live provider call solely to make a row in the MVP. | Suppressing equal fresh values loses proof of freshness; forcing daily live calls adds provider cost/rate-limit risk. |
| Missed days | Keep storage gaps; carry provider values only in reads and label them. | Persisted fill rows fabricate observations and complicate corrections. |
| Existing-data backfill | At most one trusted current observation/anchor per account; no reverse history. | Transaction-based provider backfill is not trustworthy. |
| Retention | Keep for the account lifetime; remove only through account/user purge. | Shorter retention destroys trend history and requires a new deletion job/grant. |
| Scheduled execution | No global job in the MVP; event capture plus bounded signed-in catch-up. | Wall-clock attempts require the separately described Cron/dispatcher/durable-work security boundary. |
| Downstream contract | Account/day series with amount, currency, account type, freshness, and `observed`/`carried`/`derived`/`unavailable` basis; no aggregation. | Returning only amounts would let 6.3.2 mistake stale or missing values for fresh, complete net worth. |

## Explicit deferrals

- Net-worth aggregation and presentation (6.3.2).
- FX rates, base-currency selection, and cross-currency totals.
- Account-history charts or account-detail UI.
- Intraday balance audit log and user-visible correction history.
- Available-balance and credit-limit history.
- Provider-history reconstruction from transactions.
- Institution-local cutoff modeling.
- A global scheduler, dedicated dispatcher role, Workflow/Queue dependency, and operational dashboard.
- Public history mutation endpoints.
