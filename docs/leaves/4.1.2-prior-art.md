# 4.1.2 Custom Taxonomy Editing — Prior Art

> Add, rename, nest, and retire categories so the tree matches how you actually think.

Survey date: 2026-09-12; founder rulings 2026-09-13. Design: [`4.1.2-taxonomy-editing-design.md`](./4.1.2-taxonomy-editing-design.md). Builds on the 4.1.1 survey (`4.1.1-prior-art.md`), whose deferrals to this leaf were tombstones/retire (#4), delete-or-nullify (#16), protected built-ins and deeper nesting (#19/#21), and the PG15 `ON DELETE SET NULL (column_list)` note (#23).

## Questions the survey had to answer

1. When a category goes away, what happens to the transactions assigned to it — reassigned, nulled, or kept under a hidden category?
2. Is "retire" a hide (reversible, history intact) or a delete (irreversible), and do products offer both?
3. Does a retired category's name stay reserved, and can a retired category still be used as a filter?
4. How do products constrain nesting (depth, moving between groups, group deletion with children)?
5. Which categories are protected from editing, and why?
6. What does the database layer offer for delete-with-reassignment, and what does the ledger already constrain?
7. How should inline add/rename/retire forms behave for keyboard and screen-reader users?

### Database mechanics

| # | Source | What it does | Takeaway |
|---|--------|--------------|----------|
| 18 | PostgreSQL — [Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html), [column-list commit](https://postgresql.org/message-id/E1muuB2-0004XM-QE%40gemulon.postgresql.org) | `RESTRICT` cannot be deferred, `NO ACTION` can; PG15 `ON DELETE SET NULL (column_list)` nulls a subset of a composite FK (tenant column kept), ON DELETE only. | Cash Lens's composite `(category_id, user_id)` FK could use the column list if delete ever ships; today's NO ACTION already refuses referenced deletes. |

## Patterns adopted (confirmed by the founder rulings of 2026-09-13)

- **Retire is an archive, never a delete** (Linear, Lunch Money, YNAB hide, Monarch disable): a retired category leaves every picker and the auto-categorizer, keeps every past assignment, keeps rolling up in spending, and can be restored. No DELETE grant exists for the app role.
- **Retired names stay reserved** (Lunch Money #270): the per-level unique indexes already ignore state; a collision answers 409 and the copy points at restoring.
- **Rename is a pointer edit** (Quicken): transactions reference ids, so every history row, spending row, and proposal label follows the new name with no data rewrite.
- **Two levels, enforced on every write** (Maybe `category_level_limit`, PR #1730): a row with children cannot get a parent; a parent must be an own top-level row; both checks run under the taxonomy lock.
- **Group retirement covers its leaves** (Lunch Money): derived at read time from the parent's state, so a single-row write retires or restores a whole group.
- **One transaction per operation under the existing advisory lock** (Maybe's `replace_and_destroy!`, migration 0030): lock first, validate, write.
- **Defaults are ordinary editable rows** (Monarch, Copilot): nothing is protected; transfers are pair-based in Cash Lens, so no category needs guarding.
- **Inline forms with explicit save/cancel and focus return** (PatternFly, Pajamas): reuse the offline-accounts `RowForm` shape.

## Patterns rejected for this leaf

- **Delete with reassignment / merge** (Actual, YNAB, Quicken, GnuCash, Maybe): reassigning rewrites provenance on every affected row and would have to touch the 4.2.x proposals tables, which reference categories; retire keeps history and needs no DELETE privilege. Merge is a named deferral.
- **Delete nulls the assignment** (Firefly, Lunch Money delete, GitHub labels): silently loses history; the Firefly #6870 resurrection bug shows what dangling references do.
- **Deeper nesting** (GnuCash, Firefly requests): the assignment select's optgroups, spending's leaf rollups, the LLM's "Group > Leaf" labels, and `resolveAssignableCategory` all assume two levels.
- **Protected built-ins** (Actual's income group, Copilot's Other, Quicken's underscore categories): Cash Lens has no fallback category row (NULL is uncategorized) and no category-driven transfer logic.
- **Hard delete of unused categories**: the `(category_id, user_id)` FKs on transactions and proposals are NO ACTION, Drizzle cannot express the PG15 column-list SET NULL, and a deleted default would be re-planted on a zero-row read; a never-used category can simply be retired.
- **Drag reordering, colors, emoji, descriptions** (Monarch, Copilot, Linear): cosmetic; `sort_order` stays append-only.
