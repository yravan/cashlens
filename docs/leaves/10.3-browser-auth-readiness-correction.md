# 10.3 - Browser auth readiness correction

Scope: real-Clerk browser-test session readiness. No production authentication,
permissions, financial behavior, or provider configuration changes.

## Evidence

The merged-feature audit found two distinct failures: a signed-out Google
button absent at its five-second assertion deadline, and an authenticated
category POST redirected with Clerk's `session-token-but-no-client-uat` reason.
The latter is established by a scrubbed trace; it is not inferred from cookie
names. These failures do not establish that bot protection caused either one.

The existing helper trusts a saved session JWT with more than 20 seconds left.
Installed `@clerk/backend@3.16.4` checks selected client state before verifying
that JWT. A token's remaining lifetime alone cannot establish readiness.

## Prior art

This correction reuses the ten-source
[session-lifetime survey](10.3-e2e-session-lifetime-prior-art.md), the existing
storage-state fixture, and the installed Clerk testing SDK. Additional checks:

- [Clerk Playwright setup](https://clerk.com/docs/guides/development/testing/playwright/overview):
  initialize in project-based setup and register the testing token before
  navigation. Registration bypasses bot detection, not authentication.
- [Clerk authenticated flows](https://clerk.com/docs/guides/development/testing/playwright/test-authenticated-flows):
  verify the protected page before saving reusable state.
- Installed `@clerk/testing@2.2.22`: registration is idempotent per context and
  reads the existing testing token. It does not obtain a new backend token on
  every registration. This corrects the old survey's cost assumption.
- Installed `@clerk/backend@3.16.4`: suffixed-cookie selection and client-UAT
  validation belong to Clerk. Do not duplicate them in application tests or
  manufacture a positive client timestamp.

Adopt real protected-endpoint verification and normal SDK recovery. Retain
isolated contexts, bounded waits, original UI assertions, and the redacting
runner. Reject fabricated cookies, weaker middleware, sleeps, skipped tests,
and retries until green. Do not claim a loaded SDK alone proves server auth.

## Remaining navigation investigation

A separate Sol review confirmed the taxonomy setup waits for server-rendered
email on `/transactions`, not Clerk client readiness, before another hard
navigation to `/categories`. In the sanitized failure trace, late FAPI client
initialization overlaps that navigation, and UAT zeroing precedes the rejected
mutation. The client response body is absent, so its cause is not established.
Ordinary Next.js link navigation preserves the root provider; repeated test
`page.goto` does not. This suggests a harness lifecycle trigger without proving
production immune to fast interactions.

Next proof should compare a single freshly signed-in direct load, actual Link
navigation, and the harness's two hard navigations. Control the real external
FAPI client response timing, and record only loaded/session booleans, zero vs
nonzero client state, and mutation status. Do not fabricate successful auth or
replace owned app behavior. If only the last case fails, repair test setup;
if direct loading fails, scope a production readiness correction separately.
