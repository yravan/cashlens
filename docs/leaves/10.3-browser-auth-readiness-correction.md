# 10.3 - Browser auth readiness correction

Scope: real-Clerk browser-test session readiness. No production authentication,
permissions, financial behavior, or provider configuration changes.

## Evidence

The merged-feature audit found two distinct failures: a signed-out Google
button absent at its five-second assertion deadline, and an authenticated
category POST redirected with Clerk's `session-token-but-no-client-uat` reason.
The latter is established by a scrubbed trace; it is not inferred from cookie
names. These failures do not establish that bot protection caused either one.

The existing helper trusts a saved session JWT with more than 20 seconds left.
Installed `@clerk/backend@3.16.4` checks selected client state before verifying
that JWT. A token's remaining lifetime alone cannot establish readiness.

## Prior art

This correction reuses the ten-source
[session-lifetime survey](10.3-e2e-session-lifetime-prior-art.md), the existing
storage-state fixture, and the installed Clerk testing SDK. Additional checks:

- [Clerk Playwright setup](https://clerk.com/docs/guides/development/testing/playwright/overview):
  initialize in project-based setup and register the testing token before
  navigation. Registration bypasses bot detection, not authentication.
- [Clerk authenticated flows](https://clerk.com/docs/guides/development/testing/playwright/test-authenticated-flows):
  verify the protected page before saving reusable state.
- Installed `@clerk/testing@2.2.22`: registration is idempotent per context and
  reads the existing testing token. It does not obtain a new backend token on
  every registration. This corrects the old survey's cost assumption.
- Installed `@clerk/backend@3.16.4`: suffixed-cookie selection and client-UAT
  validation belong to Clerk. Do not duplicate them in application tests or
  manufacture a positive client timestamp.

Adopt real protected-endpoint verification and normal SDK recovery. Retain
isolated contexts, bounded waits, original UI assertions, and the redacting
runner. Reject fabricated cookies, weaker middleware, sleeps, skipped tests,
and retries until green. Do not claim a loaded SDK alone proves server auth.

## Validation

- RED on the unchanged helper: remove only client-UAT cookies from a state
  whose session has more than 20 seconds left. The negative control receives 307;
  `signedInState` incorrectly returns it unchanged, and the protected JSON
  assertion fails (expected 200, received 307). Two setup cases pass.
- GREEN: signed-out redirects and Google UI, dead-token recovery, and
  missing-client-state recovery: **7 passed /45.4s**, including setup, against
  real Clerk development sessions and isolated local PostgreSQL. Recovery
  returns 200 JSON with the expected response shape, not a followed sign-in page.
- The helper now checks the protected endpoint as well as lifetime, repairs
  using the SDK, and verifies both conditions before saving. Fresh valid state
  costs a temporary context and one local API request; no new backend sign-in
  ticket is minted by this helper. Production auth remains untouched.
- Testing-token registration now precedes navigation in setup, refreshed
  contexts, signed-in fixtures and the signed-out UI test. The original Google
  assertion is retained after SDK readiness; no test retry is added.

- Full local API: **738 passed /45 files**. Lint and typecheck pass.
- Full local browser at `1564cbd`: **120 passed, 1 failed /7.2m**.
  The narrow category create expected 201 but received 307. Its sanitized
  trace shows positive client timestamps on page load and the preflight,
  followed by zero timestamps and `session-token-but-no-client-uat` during
  page activity. This is not merely a stale saved snapshot. The exact cause
  of the transition is still under investigation; do not hide it by waiting
  in the test and declaring the product fixed. Sandbox credentials: zero after
  teardown. Production Categories draft cancellation also checked in Chrome;
  no saved mutation.
- Independent Luna review found manually created second-user contexts bypass
  the fixture hook, including two raw saved-state reads in the category suite.
  They now use `signedInContext` in the existing session module, with the same
  Desktop Chrome settings and testing-token registration. The recovery test
  also verifies a new page with the expected signed-in identity and a protected
  JSON response. Intentionally unauthenticated negative controls stay raw.
- Review correction focused run: **17 passed /48.2s** (category workflows,
  identity/RLS isolation, both recovery cases and setup). The intermittently
  failing narrow category case passed here; that is not a root-cause proof.
