# 10.2 Migration Test Budget Investigation

Scope: the existing real-database classification-journal upgrade regression.
No production migration, schema, assertion, timeout, or worker setting changed.

Two default full-suite runs on the aggregate correction passed 742/743 tests;
the migration test exceeded Vitest's five-second test budget, completing around
6.6 seconds. A separate isolated pass is not a full-suite pass or a diagnosis.
The later full run had no concurrent audit build, E2E run, or API run.

The test stages the pre-journal migration files, creates a physical database,
applies the baseline, seeds legacy records, upgrades, verifies preservation and
RLS, then drops the database. All of this was inside the test body. Concurrent
worker setup also creates physical databases. An aggregate activity sample
showed data-file synchronization and checkpoint waits. I/O contention is a
hypothesis, not an established causal explanation.

## Prior Art

Reviewed 2026-09-19:

1. [Vitest testTimeout](https://vitest.dev/config/testtimeout): Node's default
   is five seconds. Consider a test-specific DDL budget only after measuring;
   reject a global timeout increase.
2. [Vitest hookTimeout](https://vitest.dev/config/hooktimeout): a separate
   budget, not a fix for work in the test body.
3. [Vitest maxWorkers](https://vitest.dev/config/maxworkers): use worker count
   as a diagnostic variable; do not assume throttling proves the cause.
4. [Vitest fileParallelism](https://vitest.dev/config/fileparallelism): the
   suite deliberately isolates worker databases. Reject global serialization
   without evidence of an exclusive resource.
5. [Vitest sequential projects](https://vitest.dev/guide/recipes/parallel-sequential):
   project group ordering is an alternative if physical database setup must
   run outside the parallel group. Do not introduce that structure speculatively.
6. [Vitest parallelism](https://vitest.dev/guide/parallelism): distinguish
   parallel files from concurrent tests; this file has one sequential test.
7. [node-postgres Client](https://node-postgres.com/apis/client): connection,
   query, statement, and lock timeouts are distinct. Do not turn valid slow
   migration DDL into a fabricated application failure with a short SQL limit.
8. [PostgreSQL 16 CREATE DATABASE](https://www.postgresql.org/docs/16/sql-createdatabase.html):
   physical template cloning has WAL_LOG and FILE_COPY strategies; FILE_COPY
   requires checkpoints. Reject changing strategy without phase measurements.
9. [PostgreSQL 16 wait events](https://www.postgresql.org/docs/16/monitoring-stats.html):
   correlate aggregate wait classes with migration phases, without query text.
10. [PostgreSQL WAL/checkpoints](https://www.postgresql.org/docs/16/wal-configuration.html):
    checkpoint flushing can consume I/O. Reject tuning server durability or
    checkpoint settings merely to make the test pass.
11. [PostgreSQL CHECKPOINT](https://www.postgresql.org/docs/16/sql-checkpoint.html):
    reject adding manual checkpoints around the test.
12. [Drizzle migrate](https://orm.drizzle.team/docs/drizzle-kit-migrate) and
    [migration fundamentals](https://orm.drizzle.team/docs/migrations):
    preserve the real journal and upgrade path; reject schema push or mocks as
    substitutes.
13. [Vitest onTestFinished](https://vitest.dev/api/#ontestfinished): register
    cleanup as a test-finished hook so it runs after both passing and failing
    tests, with its own explicit hook timeout.

## Evidence

A third default full run retained every assertion and the five-second budget:
742/743 tests, 30.29 seconds total. Phase completion times were staging 20ms,
database creation 130ms, baseline migration 744ms, seed 789ms, upgrade 1062ms,
and verification 1087ms. Database deletion did not complete before the body
timeout; the reported test duration was 5170ms. Thus the measured failure was in
cleanup after successful migration assertions, not slow baseline setup. The
exact PostgreSQL wait within deletion remains unproven.

The fix registers the disposable database drop immediately after successful
creation with `onTestFinished(..., 30_000)`. This preserves the default five-
second behavior-test budget and makes cleanup mandatory on assertion failure as
well as success. The staging directory remains cleaned in `finally`; no retry,
skip, assertion weakening, or production configuration change is justified.
