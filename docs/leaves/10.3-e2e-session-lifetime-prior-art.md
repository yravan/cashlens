# 10.3 — e2e session lifetime: prior art

How other people keep a Playwright suite signed in for longer than the auth
provider's token lives, and which of it we took.

## The problem, stated the way the ecosystem states it

Playwright's `storageState` is a *snapshot*. It records cookies with their own
`expires` values, not the lifetime of whatever credential is inside them. Clerk
mints `__session` as a **60-second JWT** and Playwright saves the cookie
carrying it for a year, so the file stays syntactically valid roughly 500×
longer than the credential inside it.

This is a well-worn complaint, not a Clerk quirk:
[microsoft/playwright#16627](https://github.com/microsoft/playwright/issues/16627)
is the canonical thread — a Keycloak user whose suite "promptly at 30min fails",
asking whether `storageState` can be refreshed outside global setup. Playwright's
own [Authentication guide](https://playwright.dev/docs/auth) names the same
failure ("tests that run longer than the token expiration") and documents the
escape hatch we ended up using.

## Adopted

- **Override the `storageState` fixture** (source 1) — `e2e/fixtures.ts`, specs
  import `test` from it. It is the only seam `page`, `context`, and the
  standalone `request` fixture are all built from, so one override reaches all
  three with no per-spec discipline.
- **Validate-then-refresh, not refresh-always** (source 10) — decode the saved
  JWT's `exp` and only re-mint inside a 20s margin. A fresh file costs one
  `readFileSync` and a base64 decode; the browser work happens a handful of
  times per run.
- **Re-mint by booting clerk-js on a public route** (sources 3, 4) — the SDK's
  `POST /client/sessions/<id>/tokens` loop is the only supported refresh path,
  and it only runs where clerk-js boots. `/sign-in` is in `proxy.ts`
  `PUBLIC_PATHS`; a protected route is redirected before the app document
  loads, so clerk-js never starts there.
- **Keep the file authoritative** (source 9) — `signedInState()` rewrites the
  same path and returns it, so `browser.newContext({ storageState })` and
  `playwright.request.newContext({ storageState })` need no other change.

## Rejected

- **`setupClerkTestingToken()` on the refresh context** (sources 6, 7). It
  bypasses *bot detection*, which is a different failure. Measured: refresh
  succeeds without it, including from a state whose Cloudflare `__cf_bm`
  cookies have expired. Adding it would cost a Backend API call per refresh to
  solve a problem we do not have — and if bot detection ever does bite, the
  refresh fails loudly on its `expect.poll`, so it is a one-line fix then.
- **Re-signing in per context** (`clerk.signIn` again). Burns a single-use
  Backend-API sign-in ticket per call, and errors outright on a context that is
  already signed in (measured as S5 in the investigation). Re-authentication is
  the sledgehammer; the session only needs its token renewed.
- **A worker-scoped `workerStorageState` fixture** (source 1's other variant).
  Computed once per worker, so it ages exactly like the file it replaces. It
  solves per-worker *isolation*, not lifetime.
- **A background heartbeat** re-saving the state every ~30s. Keeps a browser
  context alive for the whole run and writes the file underneath running tests
  (torn reads unless made atomic), for no gain over a lazy check.
- **Raising the token lifetime.** Not configurable, by design (source 4).
- **Pre-navigating `page.goto("/")` before every `page.request` call** — the
  workaround already scattered through the specs. It works only because a
  *page* context can handshake; it does nothing for an `APIRequestContext`, and
  it encodes the constraint in prose that every future spec must remember.

## The misdiagnosis worth recording

The first investigation concluded that a stale state can *never* self-heal,
from probes that built contexts with a bare `chromium.newContext()`. The suite
uses `...devices["Desktop Chrome"]`. The only network-visible difference is the
User-Agent, and `HeadlessChrome/...` is refused at Clerk's handshake endpoint
(source 7 — bot detection) while `Chrome/151...` is not:

```
A  bare (headless UA)          docs=11 signedIn=false /api/me=307
A2 bare + Desktop UA only      docs= 4 signedIn=true  /api/me=200
B  devices[Desktop Chrome]     docs= 4 signedIn=true  /api/me=200
```

Page contexts recover fine. The real defect is narrower and worse: an
`APIRequestContext` has no clerk-js, cannot handshake, follows the bounce to
the sign-in page and returns **200 with HTML** — a silent pass for any caller
that checks `status()` alone. Lesson kept: measure the harness in the exact
shape the suite uses it, or you measure your probe.
