# 4.2.4 controlled automatic reclassification design

Survey date: 2026-09-10

Scope: allow a trusted operator to reclassify stale or incorrect automatic
assignments after a model or prompt iteration. The workflow may overwrite only
rows whose current `category_source` is exactly `auto`. It must preserve manual
assignments and pre-provenance rows with a NULL source. This note designs the
workflow; it does not implement it.

This is the explicitly requested operator slice of the existing 4.2.4
Re-categorization runs leaf, not evidence that the original 4.2.1 promised
historical replacement. The separately confirmed overlapping-inference defect
stays a 4.2.1 correction and will consume this shared journal foundation.

Out of scope: public reclassification endpoints, a queue or cron worker, a
generic quota service, rules learned from manual corrections, new taxonomy
management, provider changes, bulk deletion, or any change to ledger amounts,
dates, descriptions, merchants, accounts, connections, or transfer pairs.

## Existing contract and gap

The merged 4.2.1 implementation has these relevant boundaries:

- `apps/web/lib/data/auto-categorize.ts` selects only
  `category_id IS NULL`, excludes active `transfer_pairs`, batches at 40, and
  writes category plus auto provenance in a guarded update.
- `apps/web/lib/data/categories.ts` stamps manual assignment as
  `category_source='user'` and clears confidence/reason. A concurrent automatic
  write loses because its predicate still requires a NULL category.
- `apps/web/db/migrations/0019_auto_categorization.sql` deliberately leaves
  pre-4.2.1 categorized rows with `category_source IS NULL`; that is unknown
  provenance, not permission for a model to rewrite them.
- `apps/web/lib/llm/client.ts` selects `LLM_MODEL` at request time and sends the
  OpenRouter request with the existing schema and provider data controls.
- Plaid modified upserts do not write category columns, and transfer matching
  excludes active pair members from the classifier queue.

There is no durable record of a model response, prompt version, taxonomy
version, target row snapshot, approval, or rollback preimage. A second model
call therefore cannot be approved as the same operation that was previewed,
and a later rollback cannot prove which automatic write it should reverse.

## Design invariants

1. **Automatic-only target.** A candidate must have a non-NULL category and
   `category_source='auto'` at proposal time and again at apply time. A NULL
   source, including legacy categorized data, is never eligible.
2. **Manual wins.** Any user assignment, clear, or other category edit changes
   the source or one of the compare-and-set fields. Apply and rollback then
   affect zero rows and report a conflict; neither operation retries over it.
3. **No ABA.** A category assignment carries a durable current run id and a
   monotonic category revision on the transaction. A later automatic run that
   happens to choose the identical category, confidence, and reason still
   changes both identities, so an old proposal cannot apply or roll back it.
4. **One durable reclassification proposal.** Reclassification dry-run means
   model inference plus durable proposal creation, not a discarded preview.
   Apply consumes that exact proposal set and never calls the model again.
5. **Stable inference identity.** A run records requested model, provider
   response model when available, prompt version, assignment-schema version,
   taxonomy fingerprint, provider-policy fingerprint, and a proposal-set hash
   (or the initial run's completed result hash).
   Apply requires the run id and hash and refuses a changed taxonomy or a
   missing/edited proposal.
6. **Input snapshot.** Proposal creation records the exact transaction
   `updated_at` and category revision observed before inference. A description,
   merchant, or any other ledger mutation while the model is in flight makes
   the snapshot stale; the run is aborted or the affected row is skipped and
   never silently classified from stale input.
7. **Atomic category provenance.** Category id, source, confidence, and reason
   are updated or restored in one transaction and one statement. No operation
   clears a production field merely because a model entry was missing.
8. **Transfer safety.** Active transfer members are excluded while proposing
   and checked again in the apply predicate. A row paired after preview is
   skipped, not reclassified. It can be considered by a new explicit run after
   the transfer state changes.
9. **Owner isolation.** Every run and proposal has the target user's database
   UUID, composite foreign keys to that user's transaction/category, FORCE RLS,
   and the same request-local owner scope used by the existing DAL. No
   SECURITY DEFINER escape hatch is needed.
10. **No sensitive logs.** Prompts, completions, descriptions, merchants,
   amounts, currencies, account names, provider tokens, and request bodies are
   never logged. Run/proposal tables are user-owned product data under RLS, not
   an application log; operational logs contain only run ids, counts, statuses,
   error classes, model identifiers, and bounded cost counters.
11. **Admission before inference.** Initial classification and reclassification
   both acquire one owner-scoped active inference run before selecting rows or
   calling the provider. A second overlapping request makes no provider call.
   The admission is a lease, not `transactions.category_run_id`: that column
   remains the identity of the last completed automatic assignment.
12. **Fenced completion.** An inference run has a lease longer than the
   classifier's 30-second abort timeout (90 seconds by default). Every success,
   failure, and write transaction checks the run id and `status='inferring'`.
   Lease recovery first fences the old run as expired, so a late response cannot
   write after another request has reclaimed admission.

## Durable records

The names below are logical names; the migration should use the repository's
existing Drizzle/PostgreSQL naming conventions.

### Transaction assignment identity

Add two transaction columns before the workflow can write production rows:

- `category_run_id uuid NULL`, the durable run that most recently assigned the
  automatic category. It is owner-bound to `classification_runs` through a
  composite foreign key. A legacy `category_source='auto'` row created before
  this journal exists may have NULL here; every new automatic write must set a
  real run id.
- `category_revision bigint NOT NULL DEFAULT 0`, monotonically incremented on
  every category/provenance mutation, including first-pass auto assignment,
  manual assignment/clear, reclassification apply, and rollback. It is never
  decremented or reused.

Keep `updated_at` as the exact transaction-row freshness snapshot. Every writer
that changes description, merchant, amount, date, status, or category fields
must update it in the same statement. A proposal stores the complete-precision
`before_updated_at`, `before_category_revision`, and `before_category_run_id`.
The apply predicate checks all three, so model input cannot become stale while
the provider is in flight. The revision catches category ABA; the timestamp
catches non-category ledger edits.

The proposal snapshot timestamps use Drizzle string mode. Candidate selection must read
`transactions.updated_at` as PostgreSQL text and carry that exact value through proposal
insert and CAS; converting it to a JavaScript `Date` would truncate microseconds.

Writer rules are explicit:

- The existing NULL-only first-pass auto path must create a durable
  `classification_runs` row and set `category_run_id` to that run id while
  incrementing `category_revision`. A migration may leave old automatic rows
  with a NULL run id, but it must initialize their revision deterministically
  and never pretend to know their historical model run.
- Manual assignment sets source `user`, sets `category_run_id` to NULL, clears
  confidence/reason as it does today, increments the revision, and updates the
  timestamp. Manual clear sets category and all provenance fields NULL, also
  clears the run id, increments the revision, and updates the timestamp.
- Reclassification apply sets source `auto`, the new run id, confidence, and
  reason together, increments the revision, and updates the timestamp.
- Rollback restores the recorded prior category/source/confidence/reason and
  prior run id together, but increments the revision again and updates the
  timestamp. It never rewinds the revision to the before-image value.

The schema may allow NULL `category_run_id` only for legacy automatic rows and
manual/uncategorized states; new DAL paths must enforce the writer rules. Add a
check that a non-NULL run id can only accompany `category_source='auto'`.

### `classification_runs`

One row is the control and provenance record for one bounded inference. The row
is created before the provider call and is immutable except for its state,
counts, timestamps, lease, and sanitized result metadata:

- `id`, `owner_user_id`, `kind='automatic_initial' | 'automatic_reclassification'`;
- `status`: `inferring`, `succeeded`, `proposed`, `applied`,
  `partially_applied`, `rolled_back`, `partially_rolled_back`, `expired`,
  `cancelled`, or `failed`. `automatic_initial` uses `inferring -> succeeded`
  (or `failed`/`expired`); reclassification uses `inferring -> proposed` and
  the apply/rollback states;
- `requested_model`, `response_model`, `prompt_version`,
  `assignment_schema_version`, `taxonomy_fingerprint`, and
  `provider_policy_fingerprint`;
- nullable `proposal_set_hash` (reclassification approval handle) and nullable
  `result_set_hash` (canonical completed assignments for either kind),
  deterministic candidate order, `batch_size`,
  `attempted`, `proposed`, `applied`, `skipped`, `conflicted`, and bounded
  provider usage counters if the provider returns them;
- nullable `operator_actor` (initial runs are user-triggered), `created_at`,
  `approved_at`, `applied_at`, `inference_lease_until`, and an explicit short
  proposal `expires_at` (for example 24 hours), with no raw prompt or response.

The database has a partial unique index for one `status='inferring'` row per
owner. Claiming admission and selecting the bounded candidate snapshot happen
in one owner-scoped transaction. A stale lease is changed to `expired` before
the insert is retried. The lease is not a quota: it only prevents overlapping
inference. Every finalizer includes the run id and `status='inferring'` in its
CAS, and the lease is checked again in the transaction that writes results.

The model and fingerprint fields are provenance, not a live configuration
lookup. A later `LLM_MODEL` change cannot silently reinterpret an existing run.
An expired proposal must be regenerated, not revived.

### `classification_proposals`

Reclassification only: one row per candidate and valid model result. Initial
classification does not create proposals; its completed transaction writes are
journaled by `category_run_id` and the completed initial run's result hash:

- `id`, `run_id`, `owner_user_id`, `transaction_id`, and proposed leaf
  `category_id`;
- proposed `category_confidence` and `category_reason`;
- the complete before-image: `before_category_id`,
  `before_category_source`, `before_category_confidence`,
  `before_category_reason`, `before_category_run_id`,
  `before_category_revision`, and exact `before_updated_at`;
- after apply, the exact `applied_category_revision` and `applied_updated_at`
  returned by the database. The applied tuple is the immutable proposed tuple,
  source `auto`, and the proposal's run id, so it is derived rather than copied;
- `state`: `proposed`, `applied`, `skipped`, `conflicted`, `rolled_back`, or
  `rollback_conflict`; timestamps for each state transition.

The before-image is category metadata only. Do not copy descriptions, amounts,
dates, merchants, account names, or prompt text into this table. Use a
composite foreign key `(transaction_id, owner_user_id)` and the equivalent
owner-bound category key so a proposal cannot cross a user's boundary. Keep the
proposal and before-image values append-only; only state, the applied
revision/timestamp, and transition timestamps are mutable. Do not add a delete
route. User deletion may cascade them with the owner's existing data policy.

The proposal-set hash is over canonical, sorted proposal fields and the run
fingerprints. It is a tamper check and an approval handle, not a substitute for
the row-level CAS predicates.

## Shared admission and provider seam

Before either kind calls OpenRouter, it must claim `classification_runs` in a
short owner-scoped transaction. The transaction records the exact candidate
snapshot, before-images as applicable, model/prompt/schema/taxonomy/provider
fingerprints, and a 90-second `inference_lease_until`. If the partial unique
index reports an active owner run, the caller returns an admission-conflict
result without invoking the provider. The 90-second lease exceeds the existing
30-second `AbortSignal.timeout`; it is configurable only as a bounded server
constant, and recovery must fence the old run before reuse.

The model metadata must come from the existing classifier seam at request
construction, not from a later environment lookup in the DAL. That seam should
return or expose the requested model, prompt version, assignment-schema
version, and provider-policy fingerprint captured for the request. Response
model, generation id, and usage are nullable because the current transport does
not guarantee them; store them only when the provider actually returns them.

The confirmed pre-fix reproduction is two same-owner overlapping POST/DAL
requests for one uncategorized row: both selected the row and issued a loopback
OpenRouter request, while the existing NULL-category CAS allowed only one write.
The CAS protects data integrity but is too late to protect inference cost. The
admission gate is therefore required even when the provider key has its own
spending limit.

## Initial automatic flow

The existing user-triggered NULL-only classifier becomes an
`automatic_initial` run. After admission, it selects at most 40 newest
uncategorized, unpaired rows and records their input snapshot and category
revision/`updated_at`. It calls the existing classifier exactly once. In a
short owner-scoped transaction fenced by run id, it validates the response and
updates only rows still NULL, still unpaired, and still matching the snapshot:
category, source, confidence, reason, `category_run_id=run.id`, revision + 1,
and `updated_at` change together. Manual assignment, a ledger edit, or a new
transfer therefore wins. Invalid/missing results are skipped, the canonical
completed assignments get `result_set_hash`, and the run becomes `succeeded`.
Provider or validation failure marks the run `failed` without category writes.

This path has no proposal/apply/rollback state. It still creates a real run
before inference, so every automatic assignment has durable provenance and an
overlapping request cannot spend again. A late response whose run was expired
or fenced records no transaction writes.

## Proposal flow

The only entry point is a server-only operator script. It accepts an explicit
owner Clerk user id, a bounded maximum row count, and an explicit target policy
such as all automatic rows or a confidence subset. It resolves that id to the
existing `users` row inside the same RLS owner scope and fails if no row exists.
It never accepts a user id from a browser request or from `auth()` inferred for
the operator's own session. The trusted execution environment supplies the
operator actor identity; access to that script and its database credentials is
the administrative authorization boundary.

Proposal transaction and admission:

1. Claim the shared `inferring` run admission in an owner-scoped transaction,
   compute the canonical leaf taxonomy
   fingerprint from ids and labels. Select at most 40 newest candidates in a
   deterministic order where source is `auto`, category is non-NULL, the row is
   owned by the target user, and no active transfer pair references it. Capture
   each row's category tuple, current run id, monotonic category revision, and
   exact `updated_at`.
2. Record the model/prompt/schema/provider fingerprints and the selected row
   ids plus before-images. Do not hold database locks while calling OpenRouter.
3. Send exactly one existing classifier request for that batch through the
   existing HTTP seam. Use the same least-data input contract and validate every
   returned index, leaf, confidence enum, and reason length. Invalid or missing
   entries become no proposal and leave their transactions untouched.
4. In a short owner-scoped transaction, verify the selected rows and taxonomy
   still match the snapshot, including run id, category revision, exact
   `updated_at`, and the category tuple, then insert the valid proposals and
   commit the run. If the taxonomy or a row's before-image changed, abort the
   run rather than storing a misleading preview. This second check closes the
   window between candidate selection and the provider call. Finalization is
   fenced by the run id, `status='inferring'`, and an unexpired lease before
   transitioning to `proposed`; a late or reclaimed run creates no proposals.

The script prints a redacted summary: run id, owner-safe count, model id,
fingerprints, proposed/skipped counts, and bounded usage/cost counters. It does
not print transaction text, category reasons, JWTs, provider response bodies, or
database URLs. The operator separately reviews the durable proposal rows through
an owner-scoped server tool; there is no browser preview containing raw ledger
data.

## Apply and rollback

### Apply the same proposal

Apply takes only a run id and the exact proposal-set hash. It never reads the
current model, calls OpenRouter, rebuilds the prompt, or accepts replacement
category values from the caller. It verifies the run is unexpired and in
`proposed` state, the run hash still matches, every proposed category is still
the owner's assignable leaf, and the taxonomy fingerprint is unchanged.

For each proposal, one owner-scoped transaction executes an update equivalent
to:

```sql
UPDATE transactions
SET category_id = :proposed_category,
    category_source = 'auto',
    category_confidence = :proposed_confidence,
    category_reason = :proposed_reason,
    category_run_id = :run_id,
    category_revision = category_revision + 1,
    updated_at = now()
WHERE id = :transaction_id
  AND user_id = :owner_user_id
  AND category_source = 'auto'
  AND category_id IS NOT DISTINCT FROM :before_category
  AND category_run_id IS NOT DISTINCT FROM :before_category_run_id
  AND category_revision = :before_category_revision
  AND category_confidence IS NOT DISTINCT FROM :before_confidence
  AND category_reason IS NOT DISTINCT FROM :before_reason
  AND updated_at = :before_updated_at
  AND NOT EXISTS (
    SELECT 1 FROM transfer_pairs
    WHERE transfer_pairs.user_id = transactions.user_id
      AND transfer_pairs.dismissed_at IS NULL
      AND (transfer_pairs.outflow_transaction_id = transactions.id
        OR transfer_pairs.inflow_transaction_id = transactions.id)
  )
RETURNING id, category_revision, updated_at;
```

The real implementation should use Drizzle expressions, not interpolated SQL.
The `before_category_source` is retained and checked in the proposal record;
the eligible apply predicate remains exactly `auto`, so manual and legacy
rows cannot be converted by a stale proposal. The run id, revision, exact
timestamp, tuple, and transfer predicate together prevent both ordinary races
and ABA where a later automatic run recreates the old tuple. A returned row
records the applied revision and timestamp on the proposal and marks it
`applied`; zero rows marks it `skipped` or `conflicted` with a reason.
The run is `applied` only when all proposals applied or were explicitly
skipped; any CAS conflict yields `partially_applied` and is never silently
retried.

The operation may batch database updates, but each proposal's state update and
transaction update must commit together. A model result cannot update a
transaction while its audit row remains `proposed`.

### Rollback as a guarded inverse

Rollback takes an applied run id and an explicit operator confirmation. It does
not mean "clear automatic categories." For each `applied` proposal, update all
four category fields back to its before-image only when the current row still
has the immutable proposed category, source `auto`, proposed confidence/reason,
the proposal's run id, and the applied revision/timestamp recorded after the
write. Use `IS NOT DISTINCT FROM` for nullable comparisons. The transaction
also marks the proposal `rolled_back` only when the row update returns one row.

The guarded inverse sets `category_run_id` back to the recorded prior run id,
restores the prior category tuple, increments `category_revision` once more,
and writes a new `updated_at`. It never rewinds the revision. A later run that
produced the same category tuple is therefore still distinguishable by run id,
revision, and timestamp.

A manual edit, a later automatic run, a transfer pairing, deletion, or any
other mismatch produces `rollback_conflict` and leaves the current production
fields alone. Rollback reports conflicts for operator review; it has no force
flag. This restores category, confidence, and reason together and never
clears or overwrites a newer manual decision.

## RLS and grants

Both tables use `owner_user_id` as the policy key, are enabled and forced for
the app role, and expose only own rows under the existing
`app_current_user_id()` request-local scope. Composite foreign keys bind run,
proposal, transaction, and category to one owner. The app role gets only the
minimum SELECT/INSERT/UPDATE permissions needed by the server-only script;
there is no public route, no DELETE grant, and no cross-owner lookup path.

The script must run through the app role and the normal RLS scope, not an owner
or bypass-RLS connection. If a one-time migration needs the owner role, it may
create the tables and grants only; it must not perform classification or ledger
writes. Add cross-user tests that attempt to read, insert, apply, and rollback
using the other user's scope.

The migration must extend the existing column-scoped transaction UPDATE grant
with `category_run_id` and `category_revision` (while retaining the existing
category/provenance and `updated_at` columns). No grant may add amount, date,
description, merchant, account, source identity, or ownership columns to the
reclassification writer. Plaid/import writers must preserve category identity
when they do not touch category fields and must advance `updated_at` whenever
they change transaction input fields.

## Cost and operational bounds

- One model request handles at most the existing 40-row batch.
- One operator invocation has a hard maximum of one batch. Initial user
  classification also makes one provider call per admitted run; the existing
  client may request later batches only after the prior run has finalized. No
  hidden loop, retry-until-progress behavior, queue, or cron is introduced.
- The script computes an upper-bound token/cost estimate before inference and
  refuses a request over its configured cap. Provider retries are zero for this
  operation; a rate limit or malformed response fails the run without partial
  transaction writes.
- Admission and provider spending are separate controls. Keep one active
  inference per owner and one operator batch per invocation. No daily initial
  classification quota has been approved: the existing twelve client attempts
  are per visit, not per day. The overlap correction preserves existing backlog
  draining rather than silently stretching it across days. Any future daily
  quota needs a separate product decision and a DB-backed count/window check;
  an OpenRouter spending limit is not an application-side quota.
- Usage counters may be stored as counts and sanitized provider generation id,
  but not provider bodies or prompts. A provider generation id is optional and
  must never be emitted with transaction identifiers in logs.
- Inference is the cost-bearing step: initial classification calls the provider
  once per admitted run, while reclassification dry-run calls it once per
  proposal run. Apply and rollback are database-only and have no provider cost.

## Reviewable PR sequence

1. **Schema and proposal journal.** Add run/proposal tables, enums, owner-bound
   foreign keys, RLS/grants, fingerprints, immutable before-images, the
   per-owner active-inference partial unique index, lease/fencing fields, and
   migration/schema tests. No reclassification behavior writes transactions yet.
2. **Server-only propose/apply/rollback engine.** Reuse the existing classifier
   seam and the admission/provenance work in the separate 4.2.1 overlap correction.
   Add pure canonicalization and proposal hashing, durable reclassification
   dry-run creation, strict candidate and transfer filters,
   apply CAS, and guarded inverse rollback. Add API-level tests against real
   local PostgreSQL and the existing loopback OpenRouter substitute. No public
   HTTP endpoint and no new UI trigger.
3. **Operator command and evidence.** Add the trusted server-only script with
   explicit owner identity, redacted summaries, bounded one-batch cost guard,
   approval hash handling, and documented red/green execution. Keep operational
   logs count-only. A separate review may decide whether a user-facing review
   queue should consume these states; that is 5.1 territory.

The 4.2.1 dependency records initial-run provenance and category revisions,
preserves manual assignment/clear, and returns bounded retryable busy responses.
It must not add a daily quota or create journal rows repeatedly for an already
empty backlog. The 4.2.4 engine shares its owner admission and fencing rules.

## Required verification

### Foundation execution record (pre-simplification)

The schema foundation remains unpublished and does not implement inference
admission, reclassification, apply, or rollback. Its initial local PostgreSQL
run caught three test defects: a qualified `UPDATE SET` target, a UTC formatting
assumption, and an incorrect retained-run count. These were corrected with the
typed update API, UTC-normalized microsecond assertions, and exact retained IDs.
The four focused journal test groups then passed (6.44s), followed by all 394
API tests in 30 files (125.97s), production build, and lint.

Five deliberate migration mutations each produced the intended focused RED:
removing the run-kind foreign-key component, allowing a different applied
category, reducing timestamp precision to milliseconds, disabling RLS, and
removing owner-level inference uniqueness. Each was restored. The complete
browser suite passed all 77 tests (2.7m) against the actual app and a separate
local PostgreSQL 16 database with the journal migrations. Clerk development
and Plaid Sandbox were real; the model transport used the local substitute.
Temporary ports were restored. No production rows or provider settings changed.

An additional upgrade regression stages the actual migration prefix before the
journal, creates synthetic automatic/manual/legacy-NULL-source rows, applies the
full real migration chain, and compares every pre-existing transaction field.
It separately checks NULL run IDs, zero revisions, and forced RLS. The focused
test passed (5.76s); a deliberate migration rewriting an old automatic reason
produced the intended RED and was removed. A local-only URL guard, random
test-database name, owner-role migrations, and acknowledged-create cleanup keep
the test isolated. Losing the CREATE acknowledgement can leave a uniquely named
local test database; it does not justify dropping a database whose creation was
not confirmed.

The added live-owner cascade test exposed a genuine new-schema defect:
deleting an owner with a transaction linked to its current run and an applied
proposal referencing both prior/current runs failed on the before-category FK.
The six new non-cascading provenance FKs were made `DEFERRABLE INITIALLY DEFERRED`
in the custom grant migration. Their `NO ACTION` behavior is preserved: an
individual referenced category cannot be deleted, but complete owner deletion
can finish before integrity is checked at commit. Admission uniqueness remains
immediate. The installed Drizzle FK builder cannot express deferral, so the
custom migration and live-graph test carry that contract. PostgreSQL documents
this distinction in [foreign-key actions](https://www.postgresql.org/docs/16/ddl-constraints.html)
and [constraint timing](https://www.postgresql.org/docs/16/sql-createtable.html).
The corrected six focused tests passed (7.75s). Final validation after the FK
timing correction passed all 396 API tests in 31 files (68.86s), production
build, lint, and typecheck. All 77 browser tests passed (1.6m) against a freshly
created local PostgreSQL database migrated through the final SQL, not the prior
already-migrated database. Temporary ports were restored and browser artifacts
scrubbed. Fresh independent Sol static review approved the then-six explicit FK
deferrals and migration/owner-deletion tests.

### Post-PR simplification record

Post-PR simplification removed the five copied applied-tuple columns and their
two foreign keys. The immutable proposed category/confidence/reason, source
`auto`, and run id already determine that tuple exactly; rollback needs to store
only the database-returned revision and full-precision timestamp. Mutation
coverage now protects that paired snapshot and the immutable values it derives
from. The old applied-category equality mutation is no longer applicable because
the redundant value cannot be represented; partial snapshots, non-increasing
revisions, mismatched state, and proposed-value rewrites replace it. Four explicit
FK deferrals remain.

The simplified code at `28e430f` passes all 396 API tests in 31 files (17.02s),
all 89 Playwright tests (1.8m), production build, lint, and typecheck. Browser
validation used another fresh local database with the reduced schema, real Clerk
development and Plaid Sandbox, and the loopback model substitute. Temporary ports
were restored and artifacts scrubbed. Bypassing the new state constraint produced
the intended RED (an incomplete applied snapshot was accepted); the mutation was
removed before the full pass. `pnpm --filter web db:generate` reports no schema
changes. Fresh independent Sol review of the complete simplified foundation
approves with no blockers. CI on the updated published head remains required.

### Complete workflow gates

The implementation must prove these exact behaviors before merge:

- a dry run changes no transaction row, persists the model/prompt/schema/
  taxonomy fingerprints and complete before-images, and records only valid
  proposals;
- both initial and reclassification calls claim admission before inference;
  overlapping same-owner calls produce one provider request, and a reclaimed
  lease fences the old finalizer;
- first-pass automatic assignment has a non-NULL durable run id and increments
  the category revision; manual assign/clear clears the run id and increments
  the revision; rollback restores the prior run id but never rewinds revision;
- apply makes no provider request and uses the stored proposal even when
  `LLM_MODEL` changes after dry-run;
- a user row with `category_source='user'` and a pre-4.2.1 row with NULL source
  remain byte-for-byte unchanged;
- a concurrent manual assignment, category clear, taxonomy edit, or active
  transfer causes a CAS skip/conflict, never an overwrite;
- an intervening automatic run that produces the identical category,
  confidence, and reason is rejected by run id/revision/timestamp CAS (ABA);
- changing description or merchant while the provider request is paused makes
  the proposal stale and prevents classification from committing;
- applying a changed proposal-set hash, changed taxonomy, expired run, or
  second apply is rejected without transaction changes;
- rollback restores category id, source, confidence, and reason together;
  a post-apply manual edit causes a rollback conflict and preserves the edit;
- an active transfer is excluded both before and after the model call;
- cross-user RLS reads and writes fail closed, including rollback;
- provider errors leave all transaction and proposal writes atomic, and logs
  contain no prompt, completion, merchant, amount, account, secret, or body;
- the one-batch and token/cost ceilings are enforced before any provider call.

Rejected: a public `POST /reclassify` endpoint, an in-memory preview, re-running
the model during apply, trusting a current environment model name, a blanket
`category_source != user` predicate (it would overwrite legacy unknown rows),
an unconditional `UPDATE` without CAS, rollback by clearing fields, a global
queue/cron, a generic quota platform, and logging full transaction rows for
audit. Each either weakens owner safety/provenance or expands this leaf beyond
the controlled operator workflow.
