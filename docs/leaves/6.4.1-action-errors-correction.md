# 6.4.1 recurring action errors correction

This correction covers the decision buttons on `/recurring`, whose POST can
fail after the user has clicked an action.

## Policy

- Disable every decision while one request is in flight and guard the handler
  with a ref, so same-tick double clicks cannot create concurrent mutations.
- Keep the decision id in local state after a failure and offer `Retry` for the
  exact same request. The recurring-status upsert is keyed by stream identity,
  so retrying is idempotent.
- Treat a non-404 HTTP response as a known save failure. Treat a thrown fetch as
  uncertain because the server may have committed before the response was lost;
  say so explicitly and still offer retry.
- Preserve the existing 404 behavior: a stream can disappear between render
  and click, so refresh silently rather than presenting a transport error.
- Scope the alert to the stream action row; multiple streams may be rendered at
  once and each action owns its own failure state.

## Prior art applied

The implementation follows the existing `useMutation` pattern in
`app/(app)/mutation-form.tsx` for a ref-based submission guard and retryable
error state. It follows the recurring route's existing 404 contract and the
identity-keyed upsert described in `docs/leaves/6.4.1-prior-art.md`. No new
dependency, persistence field, or API response contract was introduced.

## Verification

Browser coverage exercises a dropped request, a real cross-origin 403, a lost
successful response, and a stale-stream 404. API coverage remains the existing
real-Postgres route and isolation suite.
