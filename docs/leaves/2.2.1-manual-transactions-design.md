# 2.2.1 Manual Transactions — Approved Design

Status: founder-approved on 2026-09-11; implementation has not started.

Prior art: [`2.2.1-prior-art.md`](./2.2.1-prior-art.md)

## Scope and approved rulings

> Add, edit, and delete transactions by hand — cash spending and anything no feed can see.

This leaf adds three user-data mutations and a Transactions-page form over the existing ledger. It does not add another ledger model, change provider authority, or derive account balances from transactions.

The founder approved both product decisions:

1. Any existing owned account may receive a manual transaction, regardless of whether its source is `plaid`, `manual`, or `import`.
2. Editing may reassign the transaction to another owned account. Account and destination currency change atomically; Cash Lens performs no FX conversion.

Creating, editing, or deleting a transaction never writes `account_balances`.

## Existing seams

- `transactions` is the canonical ledger; `ledger_source` already includes `manual`, and `transaction_status` includes `posted`.
- Transactions already carry account, optional category and provenance, signed minor amount, currency, date, description, optional merchant, status, source, source ID, `categoryRunId`, and `categoryRevision`.
- Explicit own-user predicates, forced RLS under non-owner `cashlens_app`, and composite `(id, user_id)` foreign keys protect transaction/account/category ownership.
- `guardPost()` already enforces authentication and same-origin browser POSTs.
- `setTransactionCategory()` contains the current assignable-leaf and category-journal behavior; manual mutations need a shared transaction-scoped resolver, not a nested public DAL call.
- `matchTransfersFor()` recomputes active pairs, but the Transactions-page trigger runs only on mount; `router.refresh()` is not a sufficient mutation trigger.
- History, cash flow, spending, recurring detection, and auto-categorization already consume canonical posted rows.
- History account options currently omit currency, and `currencies.length === 0` incorrectly doubles as the no-account/no-transaction distinction.
- Existing grants cover INSERT, DELETE, and all editable transaction columns except `account_id`.

## Canonical row

Create inserts one ordinary transaction:

```ts
{
  userId: authenticatedUser.id,
  accountId: ownedAccount.id,
  categoryId,
  categorySource: categoryId === null ? null : "user",
  categoryConfidence: null,
  categoryReason: null,
  categoryRunId: null,
  categoryRevision: 0,
  amountMinor: direction === "outflow" ? -minor : minor,
  currency: ownedAccount.currency,
  date,
  description,
  merchant,
  status: "posted",
  source: "manual",
  sourceId: null,
}
```

`categoryRevision` may use its database default. Manual rows have no provider settlement phase or provider identifier, so they are never pending and cannot impersonate imported rows.

## API and validation boundary

All mutations stay POST-only to reuse the established guard without a neighboring HTTP-method refactor.

| Operation | Route | Request | Success |
|---|---|---|---|
| Create | `POST /api/transactions/manual` | full manual input | `201 {"transactionId":"<uuid>"}` |
| Edit | `POST /api/transactions/[transactionId]/manual` | full manual input | `200 {"transactionId":"<uuid>"}` |
| Delete | `POST /api/transactions/[transactionId]/manual/delete` | exactly `{}` | `200 {"transactionId":"<uuid>"}` |

Create and edit accept exactly:

```ts
type ManualTransactionInput = {
  accountId: string;
  direction: "outflow" | "inflow";
  amount: string;
  date: string;
  description: string;
  merchant: string | null;
  categoryId: string | null;
};
```

The parser accepts only a plain, non-null, non-array JSON object with exactly those seven keys. Required nullable keys prevent omitted values from gaining defaults. Identity, currency, source, source ID, status, provenance, revision, and timestamps are therefore impossible to submit.

- `accountId`: string; a non-UUID string maps to `account_not_found`.
- `categoryId`: null or string; a non-UUID string maps to `category_not_found`.
- `direction`: exactly `outflow` or `inflow`.
- `amount`: string of at most 32 characters matching `^\d+(\.\d+)?$`; no sign, whitespace, separators, or exponent notation; after the owned account is resolved, precision must not exceed its currency exponent and the result must be a positive, non-zero safe minor-unit integer.
- `date`: a real `YYYY-MM-DD` calendar date through the shared `isIsoDate()`; there is no future-date or wall-clock restriction.
- `description`: trim, then require 1–200 characters.
- `merchant`: null or string; trim, convert blank to null, otherwise limit to 200 characters.
- An identifier in the wrong JSON type is `invalid_request`; an identifier-shaped string that is malformed, unknown, or cross-user uses its resource-class 404.

Extract two exact helpers from the private history-query logic into `lib/ledger/minor-units.ts`: major-decimal string to safe minor integer, and safe minor integer to an unadorned major-decimal string. They compose/slice integer digits under `currencyExponent()` and never parse the complete major-unit value through JavaScript floating point. History filters reuse them; edit initialization formats `abs(amountMinor)` through the inverse helper. The existing number-based `toMinorUnits()` remains for numeric provider data.

Errors are exact JSON objects:

| Status | Body | Meaning |
|---:|---|---|
| 400 | `{"error":"invalid_request"}` | malformed JSON/body/key set, wrong JSON types, or invalid non-resource field |
| 401 | `{"error":"unauthorized"}` | no authenticated session |
| 403 | `{"error":"cross_origin"}` | browser origin does not match host |
| 404 | `{"error":"transaction_not_found"}` | malformed, unknown, cross-user, Plaid, or imported transaction target |
| 404 | `{"error":"account_not_found"}` | malformed, unknown, or cross-user account ID |
| 404 | `{"error":"category_not_found"}` | malformed, unknown, or cross-user category ID |
| 422 | `{"error":"category_not_assignable"}` | owned category is a group rather than a leaf |

After the guard and closed body validation, edit resolves the manual target before returning account/category lookup errors; then it resolves account, account-dependent amount precision, and category in that order. Create follows account, amount, category. Delete validates `{}` before resolving its target. Cross-user and unknown values are byte-identical within each resource class.

## DAL and transaction ordering

Add `lib/data/manual-transactions.ts` with:

```ts
createManualTransaction(input: ManualTransactionInput): Promise<ManualMutationResult>
updateManualTransaction(transactionId: string, input: ManualTransactionInput): Promise<ManualMutationResult>
deleteManualTransaction(transactionId: string): Promise<ManualMutationResult>
```

`ManualMutationResult` is `{ transactionId: string }` or one listed domain error. Every function derives identity through `requireUser()`, enters `withRequestScope()` itself, and retains explicit `user_id` predicates in addition to RLS. No caller supplies a user ID.

Share a transaction-scoped assignable-category resolver from `lib/data/categories.ts`. It distinguishes unknown/cross-user categories from an owned group and runs inside the caller's mutation transaction.

### Create

In one request-scoped transaction:

1. Resolve the owned account and currency.
2. Convert amount exactly under that currency.
3. Resolve the optional owned leaf category.
4. Insert the canonical row and return its ID.

### Edit

In one request-scoped transaction:

1. Resolve and lock the target by ID, own user, and `source='manual'`.
2. Resolve the destination owned account and currency, then convert the full submitted amount in that denomination.
3. Resolve the optional owned leaf category.
4. Atomically replace account, currency, signed amount, date, description, and merchant; source, source ID, and status are absent from the write set.
5. Apply the category transition and set `updatedAt=now()`.
6. If account/currency, signed amount, or date changed, delete any active transfer pair containing the target before commit.

The body is full-state, not a patch. Moving `12.34 USD` to a JPY account is rejected rather than rounded or converted; the user must provide a valid JPY-denominated amount.

Category transition is exact:

- Unchanged ID, including null: preserve category ID, all provenance, `categoryRunId`, and `categoryRevision`.
- Changed to a leaf: set it, stamp `categorySource='user'`, clear confidence/reason/run ID, and increment revision once.
- Changed to null: clear category and all provenance/run fields, and increment revision once.

Every successful edit updates `updatedAt`, including a category-preserving edit. Reclassification proposals snapshot `updatedAt` and revision, so an already-proposed classification conflicts rather than overwriting newer transaction evidence.

Only active (`dismissed_at IS NULL`) transfer pairs are invalidated on a match-defining edit. Dismissed pairs remain negative memory. Status is immutable and already `posted` for every eligible target.

### Delete

Delete and return one row constrained by target ID, own user, and `source='manual'`; no returned row maps to `transaction_not_found`. Existing foreign-key cascades remove dependent transfer pairs and classification proposals. Provider rows, source account data, and balances are untouched.

### Post-commit transfer repair

After each successful mutation transaction commits, await `matchTransfersFor(authenticatedUser)`. A matcher failure must not turn the committed mutation into an API failure, because retrying create could duplicate it. Catch it, emit only `transfer_match.run_failed` with operation and `errorClass(error)`, and return mutation success; never log the body, amount, description, merchant, category, account name, or raw error. Existing page triggers remain the eventual repair path.

## Least-privilege migration

Add one migration and no schema object:

```sql
GRANT UPDATE ("account_id") ON TABLE "transactions" TO "cashlens_app";
```

Existing column grants cover the other writes. Manual code still omits `status` and `source_id` even though neighboring DAL paths hold those privileges.

## Transactions page

History account options become `{ id, name, currency }`; the server still re-resolves currency. Show **Add transaction** whenever at least one account exists, including an empty ledger or invalid/no-match filter state.

The create form has required Account (name and currency), Money out/Money in (default out), positive amount text input with decimal input mode, browser-local initial date, required description, optional merchant, and optional existing leaf category. Text fields start empty and category starts uncategorized; there is no server-side account default.

Only `source === 'manual'` rows receive Edit and Delete. Edit expands the same full-state form, deriving direction from sign and amount through the exact unadorned formatter; account/currency consequences are visible, but source/status/currency are not editable fields. Delete first reveals inline **Delete permanently?** Confirm/Cancel controls.

Each mutation disables duplicate submission. Failure preserves values/row and shows an inline error; success closes/resets the control and calls `router.refresh()`.

Render three distinct base states:

1. No accounts: explain that an account is required, link to Accounts, and show no form.
2. Accounts but no transactions: offer Add transaction; do not imply a bank connection is the only path.
3. Existing ledger: preserve filters, list, pagination, and filtered no-match/Clear behavior while adding manual controls.

Plaid/import rows retain their existing category selector but gain no general edit/delete authority in this leaf.

## Downstream and security invariants

No consumer gets a manual-only branch. Posted manual rows appear in history, cash flow, and category spending at their exact signed amount; active transfer members remain excluded from true-spend reports; eligible uncategorized rows enter auto-categorization; repeated rows may form recurring streams; opposite legs in different owned accounts may pair as transfers. User category provenance controls whether a cleared row re-enters automatic categorization. Balances never change.

Security remains structural:

- Clerk identity only through `requireUser()`; no request identity.
- All user data in `lib/data`, inside `withRequestScope()`, with explicit ownership predicates plus forced RLS and composite ownership foreign keys.
- Wrong-source/cross-user/unknown transaction targets and cross-user/unknown account/category IDs disclose no existence distinction.
- Closed, bounded input before SQL; account-authoritative currency and exact money conversion.
- Same-origin guard before body parsing; provider rows immutable; manual-only confirmed delete.
- Financial text and raw errors never logged.
- Only column-scoped `UPDATE(account_id)` is added; no dependency, secret, provider scope, upload, webhook, external request, or background job is introduced.

## TDD and behavioral proof

Write each test first and observe it fail against absent or deliberately broken behavior.

Pure tests cover closed objects and every key/type; UUID/null classification; direction; real dates; trimming/limits; USD/JPY/KWD parse and inverse-format round trips; zero, sign, whitespace, separator, exponent, excess precision, and safe-integer overflow; exact inflow/outflow sign.

Real-PostgreSQL API tests cover:

- create's exact manual/posted/null-source-ID row, signed amount, account-derived currency, all owned account sources, category provenance/null run ID, uncategorized queue eligibility, and unchanged balance;
- edit's atomic full replacement and denomination reassignment; rollback on destination precision failure; unchanged versus changed/cleared category provenance, run ID, and revision; stale classification conflict; active-pair invalidation/rematch; dismissed-pair preservation; and unchanged balance;
- delete's manual-only hard removal, pair/proposal cascades, repeat-not-found result, rematch, and unchanged balance;
- malformed, wrong-source, unknown, and cross-user identifiers with exact error precedence and byte-identical resource-class responses; group-category, signed-out, cross-origin, malformed body, and extra-key rejection;
- raw `cashlens_app` isolation proving forced RLS blocks user B even without a DAL predicate;
- an induced post-commit matcher database failure proving the transaction remains committed, the API reports success, and only the sanitized event is logged.

Downstream seam tests mutate through the API and assert exact history, monthly cash-flow, category-spending, recurring-stream, and transfer-exclusion numbers, including edit/delete repair.

The real signed-in browser path creates an expense, asserts exact account/sign/amount/currency/date/category/source/status, edits account and direction, cancels deletion once, confirms deletion, and proves the neighbor sees nothing. It separately exercises no-account and account-with-empty-ledger states at desktop and phone width; the browser clock is pinned when asserting the local-date default.

Mutation proof must include accepting an extra key, floating-point major parsing, invalid JPY/KWD precision, trusting caller currency, removing manual-source or origin guards, creating pending rows, omitting active-pair invalidation, mutating balances, and weakening ownership/RLS isolation; restore byte-identical code after every red observation.

Completion requires `pnpm lint`, `pnpm typecheck`, `pnpm build`, full `pnpm test:api`, full `pnpm test:e2e`, authenticated desktop/phone exercise, security review, CI green, and an independent fresh-context simplification pass after the PR opens.
