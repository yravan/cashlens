# 6.4.2 year-boundary correction

## Scope

Keep upcoming projections finite when a valid four-digit ISO date reaches the
end of year 9999. This is a pure projector correction: no database, API,
detector, or `nextExpectedDate` contract changes.

## Reproduction and failure

`isIsoDate` accepts `9999-12-01`, and manual transaction/reference boundaries
therefore make this input reachable. With a monthly stream ending on
`9999-11-30`, projection emits `9999-12-30`, then advances to year 10000. The
monthly formatter returns `10000-01-30`; weekly/biweekly native date formatting
returns `+010000-01-*`. A lexical comparison against `9999-12-31` can admit
these invalid values, and an invalid first date can also throw or be treated as
an overdue/stale date incorrectly.

The bounded red probe ran the four-cadence matrix under `gtimeout 2s`. It
completed with exit 1 (not a worker timeout): 4 tests failed; monthly and
annual emitted invalid dates, while weekly and biweekly raised `RangeError`
after continued advancement. The probe was bounded and never ran against the
production or database harness.

## Correction

The projector now rejects an invalid first occurrence before stale handling,
only compares a valid successor to the reference when deciding staleness, and
requires every loop date to pass `isIsoDate` before comparing or emitting it.
Valid overdue occurrences through `9999-12-31` remain listed with their
existing totals; the first occurrence after the supported domain is omitted.

## Prior art reused

The existing [6.4.2 prior-art survey](6.4.2-prior-art.md) establishes that the
projector derives occurrences for a requested month, while the
[6.4.1 recurring survey](6.4.1-prior-art.md) keeps observed dates separate from
forecast state. The correction follows those boundaries and reuses the
existing `isIsoDate` validator rather than introducing another date engine.
