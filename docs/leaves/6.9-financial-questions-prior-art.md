# 6.9 - Natural-language spending questions: roadmap research

Research date: 2026-09-10. Scope: name the founder-requested capability in the
feature tree, not build a chat interface or select a vendor. The node stays
under 50 words. P1 is a proposed priority consistent with detailed spending
understanding; the 19-leaf MVP path is unchanged.

## Survey

| # | Primary source | Finding and roadmap consequence |
|---:|---|---|
| 1 | [dbt Semantic Layer](https://docs.getdbt.com/docs/use-dbt-semantic-layer/dbt-sl) | Central metric definitions keep answers consistent. Reuse Cash Lens spending semantics rather than letting each question invent its own. |
| 2 | [MetricFlow implementation](https://github.com/dbt-labs/metricflow) | Metric requests compile to query plans and SQL. Adopt bounded, validated query intent; do not introduce a warehouse stack for this leaf. |
| 3 | [Snowflake semantic views](https://docs.snowflake.com/en/user-guide/views-semantic/overview) | Explicit entities, relationships, and metrics provide business meaning. Distinguish purchases, payment legs, receipt items, and reimbursements. |
| 4 | [Snowflake verified queries](https://docs.snowflake.com/en/user-guide/views-semantic/verified-query-repository) | Known question/query pairs support accuracy checks. Maintain synthetic questions with hand-verified result sets and totals. |
| 5 | [Cortex Analyst REST API](https://docs.snowflake.com/en/user-guide/snowflake-cortex/cortex-analyst/rest-api) | Ambiguous questions can return suggestions instead of SQL. Clarification is a legitimate result, not a failed feature. |
| 6 | [Verified-query optimization](https://docs.snowflake.com/en/en/user-guide/snowflake-cortex/cortex-analyst/analyst-optimization) | Verified examples can improve shared concepts. Evaluate generalization to unseen merchants and paraphrases, not only memorized examples. |
| 7 | [Looker conversational analytics](https://docs.cloud.google.com/looker/docs/conversational-analytics-overview) | Natural-language intent resolves through defined fields, filters, joins, and permissions; generated answers can still be wrong. Require evidence and deterministic totals. |
| 8 | [OWASP prompt-injection prevention](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html) | Retrieved documents can carry hostile instructions. Treat transaction descriptions, receipts, and question text as untrusted data, not authority. |
| 9 | [PostgreSQL row security](https://www.postgresql.org/docs/16/ddl-rowsecurity.html) | Privileged roles can bypass RLS. Keep question execution on the existing owner-scoped, non-bypass application path. |
| 10 | [PostgreSQL transaction isolation](https://www.postgresql.org/docs/16/transaction-iso.html) | Separate reads can observe different committed states. An answer's supporting rows and total must describe one consistent result, even during sync. |

These are prior-art patterns, not claims that those products prove Cash Lens
accuracy or that Cash Lens should depend on them. No new package or service is
selected by this roadmap amendment.

## Product contract

- Understand concepts such as contact lenses across merchant names, categories,
  corrected labels, and receipt items. An optician or Costco charge alone does
  not establish that the whole payment bought contact lenses.
- State the interpreted date interval. Clarify materially ambiguous concepts,
  periods, or gross-versus-net intent. Do not silently equate calendar year with
  trailing twelve months.
- Compute from canonical purchases and item allocations, excluding duplicate
  payment representations and internal transfers. Never add both an item and
  its containing purchase. Keep currencies separate unless a conversion policy
  is explicitly available and disclosed.
- Show gross purchases, matched refunds, reimbursements, and the resulting
  out-of-pocket amount separately. An FSA reimbursement is not a duplicate
  purchase and must not be subtracted twice. Do not treat an arbitrary incoming
  payment as a reimbursement.
- Cite accessible supporting transactions/items; separate confirmed matches
  from uncertain candidates and missing coverage. No evidence is not evidence
  of zero spending. The model must not manufacture line items or amounts.
- Questions are read-only. Correcting a match or label uses existing reviewed
  edit flows, not an implicit write performed while answering.

## Dependencies and implementation boundary

Use 3.6.3 search, 3.3.2 duplicate merging, 3.3.3 receipt matching, 3.4.1 splitting,
3.4.2 reimbursements, and 4.3 line-item categories as they become available.
Incomplete coverage must be reported instead of blocking all useful answers or
claiming completeness. Apple data from 2.7 is one optional evidence source,
not a prerequisite for answering contact-lens questions from other sources.

Before implementation, confirm a 1-3 PR split for validated question intent,
evidence selection and deterministic aggregation, and the answer/clarification
view with end-to-end evaluation. Reuse existing DAL, RLS, money arithmetic,
and provider minimization. Reject unrestricted model-generated SQL, arbitrary
code execution, bank actions, account-wide prompt dumps, and general financial
advice as scope for this leaf. No runtime API or implementation is approved here.

## Required behavioral evidence when built

Synthetic fixtures must cover paraphrases and brands; a mixed contact-lens and
glasses receipt; duplicate bank/PayPal/receipt representations; a partial refund;
a separately matched FSA reimbursement; two currencies; ambiguous periods;
missing receipts; and a neighbor's otherwise identical purchases. Pin both
membership and exact minor-unit totals. Include hostile receipt instructions,
sync during answer generation, and model changes. Full real-DB and browser
tests must prove isolation and traceable totals; mutations must expose duplicate
counting, whole-merchant guessing, missing refund handling, and scope bypass.

This amendment changes documentation only; none of these behaviors are claimed
to be implemented or tested yet.
