# 10.3 — uncategorized drilldown determinism: prior art

The spending drilldown is a browser assertion over two asynchronous effects:
transfer matching preserves paired legs, while auto-categorization removes
ordinary uncategorized rows. The test must observe the real completion signal
and derive the remaining rows from the fixture's canonical transfer contract.

## Adopted

- Start `page.waitForResponse` before clicking the uncategorized link and
  require the actual categorization response to be successful with
  `remaining: 0`.
- Before clicking, wait for the spending page's exact `spend-transfer-note`
  contract (`${EXPECTED.demo.transfers.pairedRows} transactions are internal transfer legs — left out so nothing counts twice.`)
  so the canonical active-pair expectation is established before the drilldown.
- Do not assert a particular `categorized` count: an earlier in-flight request
  may validly have consumed some or all ordinary rows.
- Compute expected rows as seeded demo USD rows that are NULL-category members
  of the canonical active transfer pairs. Assert both the count and each row's
  merchant/description, so a stale pre-hydration count or unrelated row cannot
  satisfy the test.
- Leave transfer matching and categorization routes real. No sleeps, route
  mocks, or production-only timing assumptions are part of this leaf.

## Verification

The original full cleanup-branch browser run recorded 91 passes and this failure:
eight expected uncategorized USD rows became four after a real categorization
response reported five assignments and zero remaining candidates. No application
filter regression was inferred from that timing-dependent expectation.

Independent Sol review found a second race in the initial correction: the
canonical seeder inserts transactions, not transfer pairs. The exact spending
transfer-note prerequisite now establishes the real match-and-refresh completion
before categorization can run. Final row assertions use exact visible names plus
the canonical count, not substring-only matches.

The focused corrected test passed (three tests including real Clerk setup, 1.2m).
An initial setup attempt failed on a Clerk fetch before the test ran; unauthenticated
connectivity probes reached Clerk and GitHub and the local app health returned 200
before retrying. That infrastructure failure is not a product RED.

For behavioral mutation proof, the actual DAL's uncategorized predicate was
temporarily replaced with `true` in an isolated production build. The corrected
browser test failed as intended: four expected rows, 17 received. Restoring the
predicate and rebuilding passed the full 89-test browser suite (3.2m), including
the regression. All 388 API tests in 29 files passed (90.88s); production build,
lint, typecheck, and diff checks also passed.

Browser validation used local ports 3116/3196, real Clerk development and Plaid
Sandbox, and the actual app against isolated PostgreSQL 16. The model boundary
used the local synthetic stub; no paid inference or production financial records
were involved. Artifact scrubbing completed. Temporary ports and the runtime
mutation were restored; only this document and the spending test remain changed.
Post-PR review and CI are still required before declaring this leaf complete.
