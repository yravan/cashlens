# 2.1.4 Webhook body bound correction

Scope: enforce the Plaid webhook's 256 KiB body bound while the request stream
is being consumed. The correction is limited to body reading and its route-level
error mapping. It does not change Plaid verification, webhook-key caching, item
dispatch, replay policy, database ownership, or the webhook event set.

## Current failure

`apps/web/app/api/plaid/webhook/route.ts` calls `request.text()` before
`apps/web/lib/data/plaid-webhook.ts` checks `Buffer.byteLength(rawBody)`. The
check eventually returns 413, but the Web Request body has already been fully
read and materialized. The focused streamed-body test demonstrates the real
failure: a 1 MiB stream is consumed before the route rejects it, instead of
canceling near the 256 KiB limit.

The limit is a resource boundary, not just a JSON validation rule. Plaid sends
raw JSON and signs the SHA-256 of the exact body. Parsing, reformatting, or
hashing a partial body before verification would either change the signature
contract or spend resources on a request that must be rejected.

## Chosen design

Read `request.body` with a Web Streams reader and count bytes from each
`Uint8Array` chunk. As soon as the accumulated byte count exceeds 256 KiB,
cancel the reader, discard the partial body, and return the existing 413
`too_large` response without fetching a verification key or touching the DAL.
The bound is in bytes, not JavaScript string length, and applies equally to
fixed-length and chunked requests.

For a body within the limit, retain the exact valid UTF-8 content and pass it
unchanged to `handlePlaidWebhook`; verification must hash those bytes before
JSON parsing. A streaming UTF-8 decoder is required if chunks are converted to
text, because a multi-byte code point can be split across chunks. Decoder or
reader failures return a generic 400 response and never expose provider or body
details. No partial body is parsed, logged, or sent to verification.

The route remains a public unauthenticated POST: Plaid's ES256 JWT is the
authentication mechanism. A successful read does not alter the existing stale,
unknown-item, replay, or per-owner acknowledgement behavior.

## Rejected alternatives

- Keep `request.text()` and check its result afterward: preserves the current
  memory and bandwidth exposure; it is the behavior that failed the regression.
- Trust `Content-Length`: it is optional for chunked requests and is framing
  metadata, not a substitute for counting bytes received. The reader remains
  authoritative even when the header is present.
- Use Next's or Vercel's global payload limit: those limits are larger,
  platform-specific, and occur outside the route's Plaid-specific 256 KiB
  contract. They also do not provide the required immediate stream cancellation
  or the route's stable 413 body.
- Parse incrementally before the bound is known: JSON parsing cannot authenticate
  the request and risks acting on an over-limit prefix. Verification and parsing
  stay after the bounded read.
- Convert chunks with `String.fromCharCode` or decode each chunk separately:
  split UTF-8 sequences can be corrupted, changing the signed body. Use the
  platform UTF-8 streaming decoder or retain bytes until one final decode.
- Add a global request quota or change webhook-kid handling: those are separate
  operational/security concerns and are explicitly outside this leaf.

## Security invariants

- The maximum is enforced before verification-key lookup, JWT verification, JSON
  parsing, item lookup, or database work.
- Cancellation happens at the first chunk that makes the byte total exceed the
  bound; a small chunk-overrun is not acceptable as a substitute for canceling.
- Valid UTF-8 bodies hash exactly as Plaid signed them, including whitespace and
  non-ASCII characters.
- Read failures produce only a generic 400. The route logs nothing on that path
  — the platform's status line is the operator signal — so no raw body, JWT,
  request hash, provider payload, or exception detail can reach a log.
- The route does not trust a declared `Content-Length` and does not create a
  second body reader after the stream has been consumed.

## Residual: the bound is the application's, not the socket's

Next buffers a request body for any path its proxy matcher covers — `next start`
logs `Request body exceeded 10MB for /api/plaid/webhook` on a larger delivery,
the default `middlewareClientMaxBodySize`. So the platform can still accept
megabytes before the handler runs (Vercel's own function ceiling is 4.5 MB), and
this bound is what the *application* will spend: past 262144 bytes nothing is
decoded, hashed, parsed, item-looked-up, or written, and the retained string
never exceeds the cap. Dropping `/api/plaid/webhook` from the proxy matcher
would remove that buffer too; it is a `proxy.ts` change and stays out of this
correction.

## Test evidence and pending verification

The existing API seam in `apps/web/tests/api/plaid-webhook.test.ts` uses a real
`ReadableStream` and an invalid signature, so the test can prove bounded
consumption without credentials, verification-key calls, database setup, or
live requests. Its required assertions are:

- a stream larger than 256 KiB returns 413;
- the source's `bytesRead` stops at the limit plus the crossing chunk and at
  most one prefetched chunk, and its `cancel()` hook runs;
- no verification key is fetched and no webhook side effect occurs;
- a valid signed body whose UTF-8 character is split across chunks still returns
  the normal acknowledgement and verifies the original hash;
- a stream that errors returns generic 400 without leaking the error or body;
- a demand-driven source (`highWaterMark` 0) is read for exactly 262145 bytes —
  the DAL re-checks the size and answers the same 413, so only counting a source
  that yields nothing unasked can prove the *route* stopped;
- a delivery with no body at all takes the null-body path and is rejected 401.

The oversized-stream test failed against the original route: it consumed the
complete 1 MiB source. A second regression exposed raw read exceptions. Both
pass after the counted-reader correction. The full local API suite passes with
one worker: 29 files, 395 tests. Build, lint, and typecheck pass. The default
parallel API run encountered local Postgres hook timeouts and connection resets;
the serialized run is the successful local evidence, not a claim that the
parallel run passed. The full browser suite passes: 77 tests in 2.6 minutes,
including real Clerk sessions, Plaid Sandbox, isolation, and phone viewports.
The first browser attempt had a local stub/port setup error and was interrupted;
the corrected full rerun is the successful evidence. Temporary port changes were
restored before commit. Independent PR review remains pending. No production
requests or financial data were used for this correction.

## Primary sources and adopted decisions

1. [WHATWG Fetch: Body mixin](https://fetch.spec.whatwg.org/#body-mixin) - a
   request body is a one-shot `ReadableStream`, with consumption methods such as
   `text()` operating on that body.
2. [WHATWG Fetch: Request class](https://fetch.spec.whatwg.org/#request-class) -
   `Request` exposes the body through the Fetch body contract; callers must not
   assume a second independent read.
3. [WHATWG Streams: readable-stream cancellation](https://streams.spec.whatwg.org/#rs-cancel)
   - cancellation is the standard way to signal that an underlying source is no
   longer needed.
4. [WHATWG Streams: default reader](https://streams.spec.whatwg.org/#default-reader)
   - `read()` yields chunks and `cancel()` is available on the active reader.
5. [WHATWG Encoding: TextDecoder](https://encoding.spec.whatwg.org/#interface-textdecoder)
   - streaming decode preserves fragmented input across calls; UTF-8 must be
   decoded as a stream rather than chunk-by-chunk strings.
6. [Node.js Web Streams API](https://nodejs.org/api/webstreams.html) - the
   deployed Node runtime exposes Web Streams readers, cancellation, and
   `TextDecoderStream`; the implementation can stay dependency-free.
7. [Node.js global fetch](https://nodejs.org/api/globals.html#fetch) - Node's
   fetch surface is browser-compatible and provides the Web `Request`/stream
   contract used by the route.
8. [Next.js Route Handlers](https://nextjs.org/docs/app/getting-started/route-handlers)
   - App Router handlers receive the standard Web `Request`, rather than a
   buffered legacy API request abstraction.
9. [Installed Next.js 16 route-handler guidance](https://nextjs.org/docs/app/api-reference/file-conventions/route)
   - the installed docs explicitly describe reading a route body through Web
   `Request` methods; the local copy is
   `apps/web/node_modules/next/dist/docs/01-app/01-getting-started/15-route-handlers.md`.
10. [Next.js `proxyClientMaxBodySize`](https://nextjs.org/docs/app/api-reference/config/next-config-js/proxyClientMaxBodySize)
    - proxy buffering is a separate, experimental platform behavior and may
    expose only a partial body; it cannot replace this route-local bound.
11. [Vercel Functions limits](https://vercel.com/docs/functions/limitations) -
    Vercel's 4.5 MB function payload ceiling is much larger than the application
    contract and is not an early cancellation guarantee.
12. [Vercel Node.js runtime](https://vercel.com/docs/functions/runtimes/node-js)
    - platform body helpers are runtime-specific; this route intentionally uses
    the standard Web Request stream so local and deployed behavior share one
    seam.
13. [Plaid webhook overview](https://plaid.com/docs/api/webhooks/) - Plaid
    delivers raw JSON webhooks, expects a dedicated endpoint, and recommends
    duplicate/out-of-order-safe handling with prompt acknowledgements.
14. [Plaid webhook verification](https://plaid.com/docs/api/webhooks/webhook-verification/)
    - the JWT's `request_body_sha256` is computed over the exact body bytes and
    is whitespace-sensitive; verification must precede parsing or dispatch.
15. [IETF RFC 9112, message body length](https://www.rfc-editor.org/rfc/rfc9112.html#section-6.3)
    - HTTP bodies may be chunked and `Content-Length` is framing metadata, so a
    receiver must handle streamed delivery rather than trust one header.
16. [IETF RFC 9110, 413 Content Too Large](https://www.rfc-editor.org/rfc/rfc9110.html#status.413)
    - 413 is the HTTP status for rejecting content that exceeds the server's
    willingness or ability to process it.
17. [OWASP API4:2023 Unrestricted Resource Consumption](https://owasp.org/API-Security/editions/2023/en/0xa4-unrestricted-resource-consumption/)
    - enforce maximum payload size and provider/resource limits server-side;
    otherwise a cheap request can consume disproportionate memory, CPU, or
    third-party cost.
