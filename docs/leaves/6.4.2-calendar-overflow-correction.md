# 6.4.2 calendar overflow correction

Survey date: 2026-09-18

## Scope and evidence

Keep the Upcoming calendar inside its own horizontal scroll container at phone
widths. Preserve the read-only table, full accessible weekday names, 36rem
minimum calendar width, and the existing projection totals and lists.

The live browser audit reproduced a 535px document scroll width in a 320px
viewport. The calendar's wrapper was correctly limited to 288px, with a 576px
table inside it. Its absolutely positioned `sr-only` labels escaped the static
scroll wrapper. The previous 390px regression measured `document.body` instead
of the document root and missed the page overflow.

## Prior art and decision

The existing [6.4.2 survey](6.4.2-prior-art.md) covers 15 sources and remains the
basis for the calendar-plus-list presentation, semantic table, and projection
behavior. This correction supplements its accessibility section with these
primary sources:

- [CSS 2.2 overflow and clipping](https://www.w3.org/TR/CSS22/visufx.html#overflow-clipping)
  explains that an absolutely positioned descendant can escape an overflow
  ancestor when its containing block lies outside that ancestor.
- [Tailwind screen-reader-only utilities](https://tailwindcss.com/docs/display#screen-reader-only)
  define `sr-only` using absolute positioning while retaining accessible text.
- [CSSOM View scrollWidth](https://drafts.csswg.org/cssom-view/#dom-element-scrollwidth)
  defines the document-root measurement used to detect viewport overflow.
- [WCAG reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)
  permits two-dimensional tables in their own scrollable area while surrounding
  content reflows at 320 CSS pixels.

Make the existing calendar scroll wrapper `relative`, establishing the local
containing block for its screen-reader labels. This requires no new component,
dependency, global overflow rule, or change to accessible text. Hiding overflow
on the document would mask the escaped content; shrinking the seven-column
table would change the existing readable calendar layout.

## Verification

Extend the existing real-browser phone test to both 320px and 390px viewports.
Each case pins the April projection, verifies its exact charge total and list,
checks all seven full accessible weekday names, and requires root scroll width
to equal root client width. It also checks the table remains 576px wide and
scrolls its wrapper through the full horizontal range.

The regression failed against the original page at both widths:

```text
320px: Expected root scrollWidth 320; Received 535
390px: Expected root scrollWidth 390; Received 535
2 failed, 2 setup tests passed (28.8s)
```

With the one-class correction, the complete Upcoming browser file passed:

```text
11 passed (36.8s)
Test Files 45 passed (45)
Tests 738 passed (738)
API duration 12.29s
```

Production builds for both browser runs, lint, typecheck, and diff checks also
passed. The browser file includes existing projection totals, overdue semantics,
month anchors, invalid queries, and cross-user isolation.

The green browser run temporarily used ports 3310/3399 and distinct Clerk
development test users to avoid another worktree's concurrent run on 3100/3199.
Those config overrides were restored after testing; no harness config change is
part of this correction. Database access was limited to the isolated local
Postgres on port 5548. No production data was modified.
