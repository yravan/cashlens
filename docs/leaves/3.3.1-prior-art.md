# 3.3.1 Internal Transfer Matching — Prior Art

Survey date: 2026-09-05 (in progress — sources land incrementally)

Scope: how production PFM apps and open-source ledgers detect transfers between a user's own accounts (credit-card payments, savings moves); the amount/date-window/account-pair heuristics and their false-positive management; how pairs are presented and corrected; whether transfers are auto-excluded from spend; what signals Plaid itself carries.

## Sources and decisions

| # | Source | Evidence | Cash Lens decision |
|---:|---|---|---|
| 1 | [Maybe Finance `Family::AutoTransferMatchable`](https://github.com/maybe-finance/maybe/blob/main/app/models/family/auto_transfer_matchable.rb) | Production-grade open-source matcher, one SQL self-join: opposite signs (`inflow.amount < 0 AND outflow.amount > 0` in their convention), `inflow.account_id <> outflow.account_id`, both accounts in the same family, date window `inflow.date BETWEEN outflow.date - 4 AND outflow.date + 4`, same currency requires exact inverse amounts; a LEFT JOIN on `transfers` excludes pairs where *either* side is already matched; candidates ordered `date_diff ASC`, then Ruby greedily claims pairs via a used-id set so each transaction lands in at most one pair. | Adopt the whole shape: equal-magnitude opposite-sign, different accounts, same user, bounded symmetric window, already-paired exclusion, greedy date-proximity claiming with a used set. Tighten their ordering: `date_diff ASC` alone leaves ties nondeterministic — add total tiebreakers (date, then ids) so re-runs are byte-stable. |
| 2 | [Maybe PR #1690 — RejectedTransfer model](https://github.com/maybe-finance/maybe/pull/1690) | They first modeled rejection as a `Transfer.status='rejected'`, then ripped it out: a transaction could belong to multiple transfer rows and sync-time filtering became "confusing and error prone"; a rejected transfer is "equivalent to 'no transfer'". The replacement is a standalone `RejectedTransfer` (inflow_id, outflow_id) exclusion list consulted during auto-matching, so a declined pair is never re-proposed. | Adopt the negative-memory pattern, but as one table, not two: a `transfer_pairs` row with `dismissed_at` set is exactly their RejectedTransfer (active-pair uniqueness enforced by partial indexes `WHERE dismissed_at IS NULL`). One table keeps the FK/RLS/grant surface half the size, and the combo-unique doubles as the exclusion key. |
| 3 | [Maybe issue #1602 + PR #1585](https://github.com/maybe-finance/maybe/issues/1602) | Bug report: auto-matching grouped an inflow dated *before* its outflow; initially "fixed" by requiring outflow-first, then reverted (#1661, shipped in #1690): loan/card providers routinely post the receiving side a day or two before the sending bank clears it, so the window must be symmetric. | Adopt the symmetric window — the receiving half may post before the sending half. The seed's card-payment pair (checking 03-05 → card 03-07) exercises one direction; unit tests cover both. |
| 4 | [Monarch: Transfers & Credit Card Payments](https://help.monarch.com/hc/en-us/articles/360048393292-Transfers-and-Credit-Card-Payments) + [coaching-site correction workflow](https://evolvingmoneycoaching.com/avoid-these-mistakes-in-monarch-money-and-an-explanation-on-transfers/) | Anything in the "Transfers" category group (Transfer, Credit Card Payment, Buy, Sell) is excluded from budget/cash-flow/spending "so that it is not double counted"; the card *purchase* counts as spend, the later payment never does. Known failure mode: Zelle/Venmo *to another person* auto-labeled Transfer silently inflates savings; the documented correction is recategorizing — a purely categorical model has no pair to inspect or unlink. | Adopt the exclusion contract (that is this leaf's reason to exist — 6.1.1 reads pair state). Reject the category-only mechanism: a pair link (two rows, two accounts, provable zero-sum) is structural truth a category can't fake; one-sided payments to other people fail the counterpart test instead of silently vanishing from spend. |
| 5 | [YNAB: Credit Card Payments, Now Smarter](https://www.ynab.com/blog/credit-card-payments-now-smarter) + [Approving & Matching guide](https://support.ynab.com/en_us/approving-and-matching-transactions-a-guide-ByYNZaQ1i) | When both sides of a card payment import "within a few days of each other and the amounts line up", YNAB now links them automatically — no payee rule required. They name the false-positive honestly: "a $10 refund on your card and a $10 transfer to a friend are the same number", so payee rules assist and ambiguous payees fall back to amount-only. Matches are surfaced for approval; users can unmatch. | Adopt "within a few days + amounts line up" as the industry-converged core rule, and the honesty about amount-collision false positives — which is why pairs render as visible, unlinkable markers rather than silent exclusions. Reject payee-string rules in this leaf (4.2.2's territory; bank transfer strings are too institution-specific to hardcode). |
| 6 | [Actual Budget: Transfers](https://actualbudget.org/docs/transactions/transfers/) + [Identify & Apply Transfers Historically](https://actualbudget.org/docs/advanced/scripts/modify-transfers/) | Native transfers are linked payee pairs (edit one side, the other follows). For already-imported two-sided data, their official script pairs rows where "the amounts are exactly the same but inverted", "the transaction dates are within 3 days of each other", and "the match only occurs once". Their import guidance: without an explicit link the reports double-count. | Adopt exact-inverse + small window + match-once (their 3 days and Maybe's 4 bracket the choice; see Distilled design for the pick). Their linked-payee mutation model (edits mirror across sides) stays rejected — Cash Lens rows are provider-owned facts; the pair is metadata over them. |
| 7 | [Firefly III: transfer discussions #1345/#10191 + maintainer position](https://github.com/firefly-iii/firefly-iii/issues/1345) | Firefly models a transfer as ONE double-entry row, so two-sided imports produce a withdrawal + deposit it cannot merge; a maintainer calls automatic pair-detection-and-merge "pretty complex" and unshipped; users pre-process with scripts matching dates/amounts/descriptions. | Reject the merge-into-one-row model: Cash Lens keeps both provider rows immutable (provenance, per-account balances, re-sync idempotence) and records the pair as a separate link row — which is precisely what makes auto-matching *tractable* where Firefly finds it complex (no destructive merge, trivially reversible). |
| 8 | [Copilot: Transaction Types](https://help.copilot.money/en/articles/3971267-transaction-types) + [Transactions FAQ](https://help.copilot.money/en/articles/10761907-transactions-faq) | "Internal Transfer" is a transaction *type*, auto-detected for connected accounts, shown as a boxed "T" marker; internal transfers are excluded from spending and **cannot be categorized** while typed as transfers (re-type to Regular to categorize); misses are corrected via "Mark as Internal Transfer", false hits via re-typing (e.g. a refund should be Regular). | Adopt the visible textual marker and the exclusion-implies-uncategorizable instinct in its reversible form: actively paired rows leave the auto-categorize queue (a transfer needs no spend category), and unlinking re-admits them automatically. Adopt their correction affordance asymmetry for MVP: unlink (false pair) ships now; mark-as-transfer (missed pair) is a pick-two-rows UI deferred with the review queue (5.1/5.4). |
| 9 | [Lunch Money: Transaction Actions](https://support.lunchmoney.app/finances/transactions/transaction-actions) + [Transaction Utilities](https://lunchmoney.app/features/transactions) | No silent auto-detection: users group the two sides of a transfer so they "cancel each other out" in budgets, or use the Create Transfer tool for manual accounts; rules can categorize transfer-payee strings into an excluded Transfers category. | Reinforces the zero-sum-group presentation (a pair is one event netting to zero) and that manual-account transfers matter too — the matcher treats manual/import rows identically to Plaid rows (the seed's rule-set already spans sources). Reject leaving detection entirely to the user: the wedge promise is flow numbers that are right by default. |
