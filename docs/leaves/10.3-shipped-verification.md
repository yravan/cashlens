## Additional battle-test evidence

- Editing drafts and pressing Clear without Apply exposed a second reset path that
  the original query-key fix did not cover. Both corrected workflows now assert every
  control plus exact results after a subsequent Apply, not merely an empty URL.
- One full Spending run failed the known Plaid sandbox zero-transaction case, with
  72 other passes. An unchanged full rerun passed all 73, including the sandbox case.
  No test was weakened or skipped; endpoint probes showed Clerk/Plaid reachable.
  CI hit the same sandbox assertion once; rerunning only the failed job passed.
  Further recurrence in #57 prompted investigation: one of five local fresh-item
  runs reproduced zero persisted rows with complete status. Direct provider probes
  reproduced complete status with an empty cursor followed by rows on the next poll.
  This is now a diagnosed premature-completion defect, not an unexplained flake.
  Plaid's [cursor contract](https://plaid.com/docs/api/products/transactions/)
  says an empty `next_cursor` means transactions are not yet available. Synthetic
  probe Items were removed successfully; no real connection was touched.
  With #63, five consecutive real-Sandbox import tests passed without weakening
  the exact fixture checks, and the full local and CI browser suites passed.
- Newly shipped Upcoming renders a calendar and both lists without desktop overflow;
  displayed charge/deposit totals equal their respective displayed row sums. This
  is an internal display check, not independent validation of projected payment intent.
- Production metadata confirms the custom domain serves the audited main commit.
  Public health is no-store, and protected routes redirect signed-out requests.
- All 12 protected mutation routes redirect unauthenticated empty-body POSTs to
  sign-in; an unsigned Plaid webhook returns 401. Fabricated identifiers were used,
  with no authenticated mutation or real financial-data changes.
- Read-only production catalog queries confirm all nine application tables force RLS,
  and both `cashlens_app` and `cashlens_owner` have neither superuser nor BYPASSRLS.
