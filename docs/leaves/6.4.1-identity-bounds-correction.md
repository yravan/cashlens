# 6.4.1 recurring identity bound correction

The original recurring decision contract capped `normalized_name` at 200
characters, but Plaid ingestion stores `name` and `merchant_name` after a
500-JavaScript-code-unit slice (`apps/web/lib/data/plaid-sync.ts:78-79`). The
detector uppercases before filtering (`apps/web/lib/ledger/recurring-detection.ts:66-75`).
The current Node runtime's exhaustive scalar-value check found a maximum uppercase
expansion of three UTF-16 code units per input unit; U+FB03 (`ﬃ`) expands to the
ASCII identity `FFI`. Therefore a valid 500-unit provider value can produce a
1,500-character normalized identity.

The parser and database check now use 1,500 as the shared bound
(`apps/web/lib/data/recurring.ts:39-47`, `apps/web/lib/db/schema.ts:622-626`,
migration `0041_fearless_zzzax.sql`). This follows the descriptor-normalization
prior art and adopted stripping policy in `docs/leaves/6.4.1-prior-art.md`; it
preserves the full identity and avoids collisions from truncation.

The API regression syncs six provider rows into real Postgres: two different
500-unit U+FB03-based descriptions share the same account, dates, and amounts,
and normalize to distinct 1,500-bound identities. It observes all six stored
descriptions at length 500, persists both decisions through the real route, and
checks annual/upcoming totals before and after canceling only one stream. A direct
Postgres observation after the test saw `max(char_length(normalized_name)) = 1500`,
`max(pg_column_size(normalized_name)) = 1504`, and two rows in the identity index.
The index relation was 16 kB allocated for that tiny table; this is not treated as
a tuple-size measurement. The key payload itself is about 1.5 kB of ASCII text
plus account UUID, currency, direction, and tuple overhead, below PostgreSQL's
roughly 2.7 kB B-tree tuple limit.
