# 4.2.1 LLM Auto-Categorization — Prior Art

Survey date: 2026-09-02

Scope: how production PFM apps auto-categorize (trigger, provenance, confidence, review flags), how open-source LLM categorizers structure prompts and validate responses, provider/model choice for cheap classification, structured-output patterns, batch sizing, what data may leave the system, and the provider's retention posture.

## Distilled design (what 4.2.1 builds)

1. **Scope & idempotency** (#1, #7, #9, #10): candidates are exactly `category_id IS NULL` rows for the signed-in user, newest first. The model must always pick a leaf (floor: `Other > Miscellaneous` at `low`), so every applied row permanently leaves the queue; rows whose response entry is missing/invalid stay NULL and are retried on a later run under fresh caps. Already-categorized rows are never re-sent.
2. **Provenance, confidence, reason** (#1, #4, #5, #12, #14, #22): three nullable columns on `transactions` — `category_source` (`user`/`auto`), `category_confidence` (`low`/`medium`/`high`, auto only), `category_reason` (auto only, ≤200 chars). Manual assignment stamps `user`; clearing clears all three; pre-leaf rows keep NULL source (unknown provenance, honest). `source='auto' AND confidence='low'` is the durable "flagged for review" state 5.1 will consume; the history row renders the flag now.
3. **Never overwrite the user** (#1, task contract): the auto write is `SET category_id=... WHERE id=? AND user_id=? AND category_id IS NULL` — a concurrent manual assignment wins the race by construction, and re-syncs already exclude `category_id` from the modified-upsert.
4. **Least data to the provider** (#2, #18, #19, #23): per transaction only `description`, `merchant`, and direction (`in`/`out`); per call the user's assignable leaf names with group prefix ("Food & Drink > Groceries"). No user/account/connection/transaction/category ids, no dates, no amounts, no currency, no balances. Items and categories are addressed by per-call indexes; the mapping back to UUIDs never leaves the process. Prompts and completions are never logged (`lib/log.ts` discipline: counts, error classes).
5. **Provider & model** (#15, #16, #19): Anthropic `claude-haiku-4-5` (documented classification tier, $1/$5 per MTok), temperature 0, structured outputs (#17). `ANTHROPIC_API_KEY` read lazily like `PLAID_*`; without it the feature is dormant (no trigger renders, route answers 503). The SDK is fenced to `lib/llm` (ESLint), errors are rethrown sanitized, and the api suite aliases `@anthropic-ai/sdk` to a harness substitute — zero secrets, zero network.
6. **Untrusted responses** (#17, #18, #20): schema-constrained JSON, then full server-side validation — item index in range and unseen, category index maps to a real leaf of *this* user's tree, confidence in enum, reason capped; anything else drops that entry. Unknown categories are never created (#9).
7. **Trigger & cost caps** (#3, #8, #15, #20, #21): pull-based, as the signed-in user, on transactions-page visit — the SyncResume precedent (Vercel Hobby: no queue; RLS forbids cross-user sweeps). One `POST /api/transactions/categorize` processes one batch of ≤40 in one LLM call (~$0.01); the client loops while progress continues, hard-capped per visit; provider 429/529 surface as 429+Retry-After to the same client backoff pollSync uses. No progress → stop, so a failing batch can't spin.
