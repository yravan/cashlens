# 4.1.2 Custom Taxonomy Editing — Design

> Add, rename, nest, and retire categories so the tree matches how you actually think.

Survey: [`4.1.2-prior-art.md`](./4.1.2-prior-art.md). Builds on 4.1.1 (per-user two-level tree, SELECT+INSERT only) and interacts with 4.2.x (taxonomy lock, fingerprint).

## Scope and rulings

In scope: create a group or a leaf, rename any row, move a leaf between groups (and nest or un-nest a row that has no leaves), retire and restore any row, and a page to do all of it. Every operation is one RLS-scoped transaction under the existing per-owner taxonomy lock.

Rulings decided by the founder on 2026-09-13 (the alternatives offered are recorded under Rejected alternatives):

1. **Retire is an archive — decided.** A retired category disappears from every assignment picker and from the auto-categorizer's label list, keeps every existing assignment, keeps rolling up in spending, and can be restored. Nothing is ever deleted; the app role gets no DELETE grant.
2. **Editor placement — decided.** A dedicated `/categories` page linked from the Spending heading and the Transactions filter. The tab bar stays six columns.
3. **Nesting — decided.** A leaf can move to any own group; a top-level row with no leaves can be nested under a group; a leaf can be promoted to top level; a group that has leaves stays where it is. Depth never exceeds two.
4. **No protected rows — decided.** Default groups and leaves are ordinary rows: renamable, movable, retirable. A retired or renamed default never comes back because planting only happens for a user with zero rows.

Non-goals: delete, merge with reassignment, reorder, colors or icons, deeper nesting, bulk recategorize, rules. Each is listed under deferrals.

## Existing seams

- `categories` (0017/0018): per-user rows, composite self-FK `(parent_id, user_id) → (id, user_id)`, partial unique names per level (`categories_user_root_name_key`, `categories_user_parent_name_key`), CHECK `name = btrim(name) and char_length(name) between 1 and 60`, own-row select/insert policies, FORCE RLS, app role SELECT+INSERT only.
- `lib/data/categories.ts`: `ownCategories`, `plantDefaults` (conflict-ignore + parent re-read when a user has zero rows), `categoryGroupsFor(tx, userId)` → `CategoryGroup[]` (`{id,name,categories:[{id,name}]}`), `listCategoryGroups()`, `resolveAssignableCategory(tx, userId, categoryId)` (UUID pre-check; a row with children is `category_not_assignable`), `setTransactionCategory`.
- Consumers of `categoryGroupsFor`: `ledger.ts` `historyOptions` (filter form, `CategorySelect`, manual-transaction form) and `spendingByCategory` (id→name and leaf→group maps); `auto-categorize.ts` line 73 and `reclassification.ts` `taxonomyFor` (leaf labels, fingerprinted as `sha256(JSON.stringify(leaves))`).
- History rows already carry `categoryName` through a left join keyed on `(id, user_id)`, so a retired category's name still renders on its rows without any tree lookup.
- Migration 0030: trigger `categories_taxonomy_write_lock` takes `pg_advisory_xact_lock(hashtextextended('cashlens.category-taxonomy:' || owner, 0))` on every categories write; `app_lock_category_taxonomy()` (EXECUTE granted to the app role) takes the same lock explicitly. Advisory xact locks are re-entrant within a session, so lock-then-write never self-deadlocks.
- FKs into categories: `transactions.category_id` (NO ACTION) and the 4.2.x `classification_proposals.proposed_category_id` / `before_category_id` (NO ACTION, DEFERRABLE INITIALLY DEFERRED). Any referenced row is undeletable, and reassigning proposals is 4.2.x territory: this is why retire is soft.
- Route conventions: `guardPost` (401 `unauthorized` → 403 `cross_origin`), closed plain-object parsers in `lib/ledger/*` (`isPlainObject` from `manual-transactions.ts`, `hasExactKeys` private in `offline-accounts.ts`), `UUID_PATTERN` checked in the DAL (`lib/crypto` is fenced to `lib/data`), byte-identical 404s, `lib/api/*` response mappers.
- UI patterns: `app/(app)/accounts/offline-account-controls.tsx` (`RowForm`, `useMutation`, button classes, `role="alert"` errors, `router.refresh()`), `app/(app)/mutation-form.ts` (`inputClass`, `responseErrorFor`), nav `ITEMS` (six) and `TabBar` `grid-cols-6`.

## Canonical rows

`categories` gains one nullable column:

| column | type | meaning |
|--------|------|---------|
| `retired_at` | `timestamptz null` | NULL = active. Set once on retire (preserved on repeat), cleared on restore. |

Effective state is derived at read time: a leaf is retired when its own `retired_at` or its parent's is set. No cascade write, no denormalized flag on leaves. `sort_order` is untouched by every edit; new rows take `max(sort_order) + 1` among their siblings (roots or one parent), so they land last.

Uniqueness stays exactly as 4.1.1 built it: the partial unique indexes ignore `retired_at`, so a retired "Coffee Shops" reserves its name at that level (Lunch Money's rule). A collision answers 409 `name_taken` and the page copy says the name may belong to a retired category.

Depth is a DAL rule under the lock, not a constraint: a row may take a parent only if the parent is an own top-level row and the row itself has no children. The self-FK alone would allow chains; the lock makes the two pre-checks race-free.

## API and validation boundary

| Route | Body | Success | Errors |
|-------|------|---------|--------|
| `POST /api/categories` | `{ name, parentId }` (`parentId` null = new group) | 201 `{ categoryId }` | 400 `invalid_request`, 404 `parent_not_found`, 409 `name_taken` |
| `POST /api/categories/[categoryId]` | `{ name, parentId, retired }` (full state) | 200 `{ categoryId }` | 400 `invalid_request`, 404 `category_not_found`, 404 `parent_not_found`, 409 `has_children`, 409 `name_taken` |

Parsers live in `lib/ledger/categories.ts` (`parseCategoryCreate`, `parseCategoryEdit`): plain object, exact key set, `name` trimmed with 1–60 characters (the CHECK's rule), `parentId` `null` or a string (UUID shape verified in the DAL, as offline accounts do), `retired` a boolean. `hasExactKeys` moves from private to exported in `offline-accounts.ts` rather than being rewritten.

Error precedence per request:

| order | check | status |
|-------|-------|--------|
| 1 | signed out | 401 `unauthorized` |
| 2 | cross-origin browser request | 403 `cross_origin` |
| 3 | body fails the closed parser | 400 `invalid_request` |
| 4 | `categoryId` malformed, unknown, or another user's | 404 `category_not_found` (byte-identical) |
| 5 | `parentId` malformed, unknown, another user's, a leaf, or the row itself | 404 `parent_not_found` (byte-identical) |
| 6 | row has leaves and a parent was given | 409 `has_children` |
| 7 | name already used at the target level (retired included) | 409 `name_taken` |

The full-state edit keeps one route and one parser for rename, move, retire, and restore; the client always sends the row's current values for the fields it is not changing.

A moved or renamed category changes the 4.2.x fingerprint (labels are `Group > Leaf`), and a retired leaf leaves the list; by the 4.2.4 design a run whose taxonomy drifted skips or conflicts, never overwrites. 4.1.2 changes nothing in 4.2.x code.

## DAL and transaction ordering

`lib/data/categories.ts` gains:

- `categoryTreeFor(tx, userId)`: plants defaults when the user has zero rows (planting moves here from `categoryGroupsFor`), then returns every row as `CategoryNode` (`{ id, name, retiredAt, categories: CategoryNode[] }`, roots with their leaves, sort order preserved). `categoryGroupsFor` becomes `activeGroups(await categoryTreeFor(tx, userId))`, keeping its public shape and semantics ("assignable taxonomy") so `auto-categorize.ts`, `reclassification.ts`, and `historyOptions` need no edits. `activeGroups` and the retired-node helper are pure functions in `lib/ledger/categories.ts`.
- `listCategoryTree()`: the page's read (`requireUser` + `withRequestScope`).
- `createCategory(input)`: `lockTaxonomy(tx)` (`select public.app_lock_category_taxonomy()`, the same three lines `reclassification.ts` keeps private); when `parentId` is set, `select id from categories where id = $parent and user_id = $me and parent_id is null` else `parent_not_found`; sibling `max(sort_order)`; `insert … on conflict do nothing returning id`; an empty return is `name_taken`.
- `updateCategory(categoryId, input)`: `UUID_PATTERN` pre-check → `category_not_found`; `lockTaxonomy`; read the target with its child count (`user_id = $me`); `parentId` rules as above plus `parentId !== categoryId`; name pre-check `exists (select 1 … where user_id = $me and name = $name and parent_id is not distinct from $parent and id <> $id)` → `name_taken` (race-free under the lock, and an UPDATE has no ON CONFLICT); one `update … set name, parent_id, retired_at = case when $retired then coalesce(retired_at, now()) end, updated_at = now() where id = $id and user_id = $me returning id`.
- `resolveAssignableCategory(tx, userId, categoryId, keep = null)`: a retired leaf or a leaf under a retired group is `category_not_assignable` unless `categoryId === keep`. `updateManualTransaction` passes `target.categoryId` as `keep` (it already reads the row first), so editing the amount of a transaction that sits in a retired category still works; new assignments to retired categories are refused server-side, not only hidden.

Explicit `user_id` predicates stay on every statement in addition to RLS. Nothing reads caller-supplied ids into SQL before validation.

`spendingByCategory` swaps its `categoryGroupsFor` call for `categoryTreeFor` so a retired leaf with history keeps its name and its group. The rollup arithmetic is unchanged; per-currency totals still reconcile to the dashboard.

## Least-privilege migration

Two files, both committed in PR 1 so the privilege surface is reviewed once:

1. Generated (`pnpm db:generate --name category_retirement`, snapshot included): `ALTER TABLE "categories" ADD COLUMN "retired_at" timestamp with time zone;` and `CREATE POLICY "categories_update_own" ON "categories" AS PERMISSIVE FOR UPDATE TO "cashlens_app" USING (user_id = (select app_current_user_id())) WITH CHECK (user_id = (select app_current_user_id()));` (schema: `retiredAt` column, `pgPolicy` in the accounts style).
2. Hand-written, journal entry, no snapshot (the 0035 pattern): `GRANT UPDATE ("name", "parent_id", "retired_at", "updated_at") ON TABLE "categories" TO "cashlens_app";`

No DELETE. `user_id`, `sort_order`, `created_at` stay unwritable. The existing 0030 trigger fires on every UPDATE, so app edits serialize with classification runs automatically. Numbering follows merge order (currently 0036/0037; renumber after sibling merges).

The 4.1.1 assertion "the app role has no update or delete path on categories" changes to: UPDATE of `name` succeeds within scope, UPDATE of `user_id`/`sort_order` and DELETE still raise 42501. The PR names this edit.

## Page

`/categories` (server page + one client controls module), reached from a "Manage categories" link beside the Spending heading and an "Edit categories" link next to the Transactions filter's Category select. No seventh tab.

- Groups render as sections with their leaves; retired rows carry a "Retired" badge and quieter text; a retired group's leaves show the same badge.
- Top of page: "Add group" (name). Per group: "Add category" (name). Per row: Rename, Move (a select of own active groups, plus "Top level" for a row without leaves), Retire / Restore. Each action opens the `RowForm` inline form (aria-labelled, save/cancel buttons, `role="alert"` error, disabled while pending, focus returns to the row's action after close); retire/restore is a single-request button with the same error line.
- Error copy per code: `name_taken` "That name is already used here — it may belong to a retired category.", `has_children` "Move its categories out first.", `parent_not_found` "That group is no longer available.", `category_not_found` "That category is no longer available."
- `RowForm`, `useMutation`, and the button classes move from `offline-account-controls.tsx` into `app/(app)/mutation-form.tsx` and are imported by both pages (a mechanical extraction, behavior unchanged; noted in the PR).
- Pickers: a shared `CategoryOptions` component renders the active optgroups plus a trailing "Retired" optgroup from a caller-supplied list. `historyOptions` gains `retired: { id, name }[]` (derived from the same tree read). The filter form passes every retired row so spending drill links and old filters still show their selection; `CategorySelect` and the manual-transaction form pass only the row's current category when it is retired, labelled "Name (retired)", so the control shows the truth without offering retired rows for new picks.
- At 320px everything is one column: the group heading, rows, and forms stack; buttons wrap. At 1280px the page keeps the `max-w-5xl` shell and the forms cap at `sm:max-w-sm` like the accounts page.

## Downstream and security invariants

- Retire never loses data: assignments, provenance, proposals, and spending history stay exactly as they were; only pickers and the LLM label list change.
- Default re-planting stays idempotent and never resurrects: planting runs only for a user with zero rows, and rows are never deleted.
- Cross-user ids are indistinguishable from unknown ids on both routes (RLS plus explicit predicates; same 404 body).
- Two-level depth holds under concurrency: the explicit lock precedes validation, and the trigger re-takes the same lock on write.
- The app role's categories surface after this leaf is exactly SELECT, INSERT, and UPDATE(`name`, `parent_id`, `retired_at`, `updated_at`), all RLS-scoped; pinned in the api suite and probed in the e2e write-surface test.
- No new risk surface: no upload, webhook, background job, or dependency. The only new privilege is the column-scoped UPDATE above.
- Classification interaction: a taxonomy edit during a run changes the fingerprint; 4.2.4's apply step skips or conflicts by design. No 4.2.x file changes.

## TDD and behavioral proof

API (`tests/api/categories.test.ts`, extended; `provision`, `leafNamed`, `pgError` reused):

- Create group and leaf: 201, appears in groups last among siblings, `parentId` null vs group; duplicate name at each level → 409, including against a retired name; parent that is a leaf, unknown, malformed, or user B's → identical 404; 401/403/400 bodies exact.
- Rename: history rows' `categoryName` and spending group/leaf names reflect it with the same `EXPECTED` totals; same name on itself is fine; collision → 409.
- Move: a leaf moved between groups moves its totals in `spendingByCategory` (exact `EXPECTED`-derived numbers); a group with leaves → 409 `has_children`; a childless root nests; a leaf promotes; self as parent → 404.
- Retire: absent from `listCategoryGroups`, present in `listCategoryTree` with `retiredAt`; `setTransactionCategory` and the category route answer `category_not_assignable`; rows already assigned keep `categoryName` and spending totals unchanged; a manual transaction in a retired category can still be edited without changing category (the `keep` rule); retiring a group hides its leaves; retire is idempotent (`retired_at` preserved); restore returns it.
- Defaults: retire and rename a default, list again, count stays 80 and nothing is re-planted.
- Grants: scoped UPDATE of `name`/`parent_id`/`retired_at` affects only own rows (0 rows for the other user), UPDATE of `user_id`/`sort_order` and DELETE → 42501.
- Isolation: user B editing or retiring user A's category id gets the same 404 as an unknown id and A's row is unchanged; B creating under A's group → 404.

Unit (`tests/unit/categories.test.ts`): both parsers reject extra keys, wrong types, whitespace-only and 61-character names, non-boolean `retired`, non-string `parentId`; `activeGroups` drops retired leaves and whole retired groups.

E2E (`e2e/categories.signed-in.spec.ts`, extended; storage state A/B): rename "Groceries" on `/categories` → `/spending` shows the new name with the unchanged seed net; retire "Coffee Shops" → the transactions select no longer offers it while the Bean Barrel row still shows "Coffee Shops (retired)" selected; user B's tree is unchanged; the same flow at 320px. Write-surface probe in `e2e/ledger.signed-in.spec.ts`: scoped `update categories set name … returning user_id` returns only A's rows; `delete from categories` and `update categories set sort_order = 0` → 42501.

Every new test is observed red first (behavior stubbed or assertion inverted, output pasted in the PR).

## Rejected alternatives

Offered to the founder alongside the decided rulings, and not built:

- **Retire moves assignments to Uncategorized**: rewrites provenance on every affected row and silently loses history (the Firefly/GitHub delete model).
- **Retire asks for a replacement category (merge)**: reassigns transactions and would have to repoint the 4.2.x proposals tables; a named deferral, not a launch behavior.
- **Hard delete when unused, retire otherwise**: two verbs for one intent, a DELETE grant for the app role, and a deleted default would be re-planted on the next zero-row read.
- **Editor as a section at the bottom of `/spending`**, **a seventh nav tab**, or **settings under the account menu**: the spending page is a report, the tab bar is full at six, and there is no settings surface yet.
- **Create under a group only, no moves**: leaves the default tree's grouping frozen, which is the thing this leaf exists to change.
- **Deeper nesting**: the pickers, spending rollups, LLM labels, and `resolveAssignableCategory` all assume two levels.
- **Protected default rows**: Cash Lens has no fallback category row (NULL is uncategorized) and no category-driven transfer logic, so nothing needs guarding.
- **Per-verb routes (`/rename`, `/move`, `/retire`) in the 2.2.3 style**: three parsers and three handlers for the same validation; one full-state edit route is smaller.

## Explicit deferrals

- Merge with reassignment and delete of unused categories (needs a 4.2.x proposals decision and a hand-written column-list SET NULL migration).
- Reordering (`sort_order` stays append-only), colors, icons, descriptions.
- Deeper nesting.
- Bulk recategorize and rules (5.x).
- Spending rows marking retired categories; the retired label appears only in pickers.
- Group-id drill-through on spending (already deferred by 6.2.1).
