# 2.1.3 Sync readiness correction

Scope: prevent an initial Plaid backfill from being marked complete while the
provider has not issued a continuation cursor. This complements
[PR #57](https://github.com/yravan/cashlens/pull/57), which
corrects the browser's caller-local completion count; this note covers the
provider readiness invariant underneath that UI.

## Provider contract

Plaid's [Transactions API](https://plaid.com/docs/api/products/transactions/)
uses `next_cursor` to indicate the position at which the next sync should
continue. An empty cursor means that transactions are not yet available. A
nonempty cursor is the durable acknowledgement that this response has advanced
the item, even when the page contains zero changes. Therefore:

- `transactions_update_status=HISTORICAL_UPDATE_COMPLETE` with an empty
  `next_cursor` remains `in_progress` and must not store a completion marker.
- A nonempty cursor plus historical-complete status may complete an otherwise
  empty history; completion must not require a positive row count.
- A later sync may return rows after the empty-cursor response. Once that run
  supplies a cursor, the rows and cursor commit together and the backfill can
  complete.

## Evidence

The real sandbox probe produced two empty-cursor, not-ready responses, then an
empty-cursor historical-complete response, followed by a later poll returning
rows and a nonempty cursor. The same sequence was reproduced in the API
substitute without credentials or live requests. The existing implementation
completed at the historical-complete response, leaving zero rows and a null
cursor; the regression failed before the correction.

The synthetic coverage also pins the legitimate empty-history case: a
historical-complete response with a nonempty cursor completes and stores that
cursor. This distinguishes provider readiness from ledger cardinality and
preserves valid institutions with no historical transactions.

## Design

Completion is gated by the run's cursor being nonempty in addition to the
existing drained and historical-complete conditions. A prior `complete` marker
is retained only when the run retains or obtains a nonempty cursor. A legacy `complete` row
with a null cursor is consequently treated as resumable on its next sync; the
next provider response repairs the marker conservatively and never fabricates
history or infers readiness from row count.

The API regression asserts both exact imported rows after readiness and the
valid empty-history cursor case. It does not add sleeps, retries, provider
credentials, or a production-only mock.
