# 4.2.1 Taxonomy Finalization Correction

Scope: initial automatic categorization must not apply a model result after
the offered category ids or labels change. The existing row revision and
timestamp predicates protect transaction edits, but cannot detect a category
rename or a leaf becoming a group while inference is running.

## Existing prior art adopted

This correction extends the existing surveys and designs:

- [4.2.1 prior art](4.2.1-prior-art.md): NULL-only candidates, explicit auto
  provenance, and validation against the offered taxonomy.
- [4.2.1 inference admission](4.2.1-inference-admission-prior-art.md): short
  transactions, owner-run locking, lease fencing, and durable run identity.
- [4.2.4 reclassification design](4.2.4-reclassification-design.md): acquire
  the owner taxonomy advisory lock, reread and fingerprint the taxonomy,
  and hold the lock through the final writes. The implemented reclassification
  finalizer already uses this protocol.
- [4.1.2 taxonomy editing design](4.1.2-taxonomy-editing-design.md): category
  edits use the same owner lock as the migration 0030 write trigger.

Initial finalization now follows that existing protocol after locking its run.
The fingerprint still covers the ordered `{id, label}` list that was offered
to the model. A changed fingerprint fails the live run and returns zero
progress without changing any transaction field. A later trigger can claim a
fresh run with the current taxonomy. The lease is checked again after waiting
for the taxonomy lock and ordered candidate-row locks. No lock is held across
the provider call.

A fingerprint read without the lock would leave another edit window before
the transaction writes, so that approach was rejected. There is no schema,
provider, client-loop, retirement-policy, or reclassification change.

## Verification

All API runs used real isolated local PostgreSQL on port 5548 and the existing
loopback OpenRouter substitute. Only the external response hook coordinates
the race; category edits use the real authenticated DAL.

Before the fix, the new parameterized regression failed for all three cases:
rename the offered leaf, rename its group, and promote the leaf to a group
with a child. Every case incorrectly returned `categorized: 1, remaining: 0`
instead of `categorized: 0, remaining: 1` (3 failed, 16 filtered out, 1.80s).

With the fix, the tests assert the complete transaction is unchanged, the
run is failed with zero applied rows, and a fresh inference can categorize
the row successfully. Existing cross-user isolation remains covered.

Two additional tests reuse the reclassification suite's real PostgreSQL lock
helpers. One blocks the target transaction after the taxonomy read and proves
a concurrent category rename waits until assignment commits. Removing only
the taxonomy lock made that test fail: the rename did not wait (1 failed,
30 filtered out, 5.93s). The other holds the taxonomy lock until the run's
lease expires, then verifies zero assignments and no successful result hash.
Removing only the post-lock lease check made it incorrectly categorize one
row (1 failed, 30 filtered out, 1.93s). Both guards were restored. These
tests coordinate on PostgreSQL blocking state and its actual lease deadline,
without sleeps or owned-code substitutions.

Independent review follow-up added a third real-DB race: a target transaction
is held `FOR UPDATE` without changing it while the initial run's lease expires.
Before the follow-up fix, the finalizer's implicit `UPDATE` row lock waited,
then applied the assignment anyway (1 categorized, 0 remaining), proving RED.
The finalizer now locks all admitted candidate rows in id order before its
last lease check; the regression then passes with zero assignments and an
unchanged transaction. The four focused initial-finalization race tests pass.

The ordering seam is also covered by a taxonomy-lock-holder regression: the
holder renames the offered leaf before releasing the advisory lock. Moving
the taxonomy reread before the lock made it RED (1 categorized); keeping the
lock before the reread makes it fail closed with the unchanged transaction.

An expired finalizer retains the existing recovery behavior: zero progress,
with the expired `inferring` run reclaimed by a later admission. This
correction does not change immediate browser retries or expiration cleanup.
