# 3.2.1 Pending-to-posted reconciliation — prior art

Survey date: 2026-09-09

Scope: how transaction aggregators represent pending settlement, how consumers reconcile linked records without duplicates or data loss, what survives replacement, and what must happen when linkage is absent or events arrive out of order.

## Sources and decisions

| # | Source | Evidence | Cash Lens decision |
|---:|---|---|---|
| 1 | [Plaid transaction states](https://plaid.com/docs/transactions/transactions-data/) | Pending → posted is replacement, not mutation: the pending id enters `removed`, a new posted id enters `added`, and the posted row’s nullable `pending_transaction_id` links them when Plaid matched them. Name, amount, and date can change; holds can disappear without posting. | Treat only the explicit link as identity proof. Posted provider fields win. A removed pending without a linked posted row is an ordinary removal. |
| 2 | [Plaid Transactions API](https://plaid.com/docs/api/products/transactions/) | `/transactions/sync` pages `added`, `modified`, and `removed`; all pages belong to one logical update. `pending_transaction_id` is nullable and coverage varies. | Collect the full run before reconciliation. Never infer a link when Plaid omitted it. |
| 3 | [Plaid Sync migration guide](https://plaid.com/docs/transactions/sync-migration/) | Consumers patch local state from the three arrays and advance the cursor only after successfully applying the update. | Reconciliation and cursor CAS stay in the existing database transaction. No second reconciliation job or cursor. |
| 4 | [Plaid Pattern sync example](https://github.com/plaid/pattern/blob/master/server/update_transactions.js) | Official sample accumulates pages, applies upserts/removals, and recommends one atomic transaction with cursor advancement. | Preserve Cash Lens’s existing full-run + CAS transaction; add reconciliation inside it rather than after commit. |
| 5 | [Sure Plaid processor](https://github.com/we-promise/sure/blob/main/app/models/plaid_entry/processor.rb) | Passes both the posted `transaction_id` and `pending_transaction_id` into a provider-neutral import adapter. | Keep provider linkage at the ingestion boundary and isolate reconciliation in the data layer. |
| 6 | [Sure ProviderImportAdapter](https://github.com/we-promise/sure/blob/main/app/models/account/provider_import_adapter.rb) | Priority 1 claims the existing pending entry by Plaid’s link id, updates it to the posted external id, clears pending state, and keeps user-enriched fields. It records the old id to prevent resurrection. | Reuse the existing Cash Lens row id. Update provider fields/source id/status in place so category provenance, transfer links, and future annotations survive. Record no provider payload blob; the final source id is enough because Sync removals are applied in the same transaction. |
| 7 | [Sure reconciliation data-loss issue #2013](https://github.com/we-promise/sure/issues/2013) | Amount/currency/date-window fallback can overwrite a distinct same-amount transaction and permanently suppress the wrong row. | Explicitly reject heuristic fallback. Unknown/null link creates a separate posted row; correctness beats cosmetic deduplication. |
| 8 | [Actual Budget bank sync implementation](https://github.com/actualbudget/actual/blob/master/packages/loot-core/src/server/accounts/sync.ts) | Exact imported-id match precedes fuzzy matching; a provider id normally cannot fuzzy-match a row with a different provider id. Existing category, notes, payee, and lock state are protected during reconciliation. | Preserve all user-owned/enrichment columns while refreshing only provider-owned columns. Never match two differing Plaid ids without Plaid’s explicit link. |
| 9 | [Actual Budget sync tests](https://github.com/actualbudget/actual/blob/master/packages/loot-core/src/server/accounts/sync.test.ts) | Tests pin that differing non-null imported ids are not automatically merged. | Add the equivalent unknown-link case: same amount/date/name still stays two rows without `pending_transaction_id`. |
| 10 | [Actual Server pending support PR #315](https://github.com/actualbudget/actual-server/pull/315) | Pending transactions import as uncleared and later clear when booked. | A posted replacement must surface as posted immediately, but Cash Lens retains its existing internal row identity. |
| 11 | [Actual duplicate bank-sync issue #3762](https://github.com/actualbudget/actual/issues/3762) | Real users report duplicate pending/posted imports when provider identity changes or reconciliation misses. | Test event-order permutations explicitly; do not rely on UI suppression or eventual cleanup. |
| 12 | [Actual Budget manual merge](https://actualbudget.org/docs/transactions/merging/) | Manual merge exists as a recovery path for duplicates that automation cannot prove. | Do not add manual merge in 3.2.1; that belongs to merge review. Leave unlinked rows honest and separately visible. |
| 13 | [Teller transaction API](https://teller.io/docs/api/account/transactions) | IDs are generally stable, but materially changed posting can receive a new id; overlapping 7–10-day sync windows are recommended. | Provider-specific stable-id assumptions are unsafe. Cash Lens uses Plaid’s explicit transition field only. |
| 14 | [TrueLayer pending transactions](https://docs.truelayer.com/reference/getaccountpendingtransactions) | Pending and settled data are separate; `transaction_id` may change. Optional `normalised_provider_transaction_id` is the preferred stable key when available. | Model linkage as optional provider evidence, not as a universal transaction identity rule. |
| 15 | [MX transaction lifecycle](https://docs.mx.com/api-reference/platform-api/reference/transactions) | A matched pending row may retain its GUID; otherwise MX deletes it and creates a posted GUID. Pending and posted can coexist for up to 14 days. | The API surface can temporarily contain both forms; consumers must reconcile atomically when a reliable link exists. |
| 16 | [Salt Edge API v6](https://docs.saltedge.com/v6/api_reference/) | Pending rows are snapshots replaced on refresh; they may return under another id, become posted, or disappear. | Never treat a pending id as permanent financial identity. Preserve Cash Lens identity separately from Plaid source id. |
| 17 | [GoCardless Bank Account Data quickstart](https://docs.gocardless.com/docs/bank-account-data/quickstart-guide) | `booked` and `pending` arrays are separate and even provider/internal transaction ids can be absent. | Null linkage is normal. No guessed merge and no error when a posted row cannot be linked. |
| 18 | [Mastercard Open Finance transaction data](https://developer.mastercard.com/open-finance-us/documentation/products/manage/transaction-data/understanding-transaction-data/) | Pending data is short-lived; each refresh replaces currently available pending rows. A unique id helps identify records but is not documented as a guaranteed settlement link. | Avoid cross-provider folklore; implement only Plaid’s documented contract in this Plaid-specific sync path. |
| 19 | [plaid2text pending-transactions issue #32](https://github.com/madhat2r/plaid2text/issues/32) | Discusses pending/posted double-counting, tip-driven amount changes, and authorization holds that disappear. | Posted amount/date/merchant/description win; vanished holds delete normally. |
| 20 | [mbafford/plaid-sync](https://github.com/mbafford/plaid-sync) | Maintained cursor-based Plaid-to-SQLite synchronizer illustrating local persistence of the incremental feed. | Cursor replay/idempotency is a separate concern from settlement identity; Cash Lens keeps its existing source-key uniqueness and CAS. |

## Adopted design

- Add nullable `pending_source_id` to provider transaction ingestion. It stores Plaid’s `pending_transaction_id` on the incoming posted row shape long enough for the atomic sync transaction to resolve it; provider linkage is never accepted from browser input.
- When a posted Plaid row explicitly links to a pending Plaid row owned by the same user **and account**, update the pending database row in place with the posted provider fields and new source id. The internal UUID and user-owned enrichment (`category_id`, `category_source`, confidence, reason; later annotations) survive.
- Posted provider truth wins for amount, currency, date, description, merchant, status, and source id. Tips and changed descriptors therefore settle correctly.
- Apply linked replacements before ordinary additions and before removals. The subsequent removal of the old pending source id becomes a harmless no-op. Different-page ordering cannot matter because the full sync run is accumulated first.
- Require the existing pending row to be `source='plaid'`, `status='pending'`, explicitly owned by the request user, and in the same registered account. A cross-user or cross-account id is indistinguishable from an unknown id and cannot be claimed.
- No amount/date/name fallback. A posted row with null or unknown linkage inserts independently; an unlinked pending remains until Plaid removes it.
- Replays are idempotent under the existing `(account_id, source, source_id)` partial unique index. CAS-losing runs commit nothing. Replaying the posted record finds its new source id; the old removal stays a no-op.
- Existing ledgers cannot be retroactively reconciled after the feed event is gone: Cash Lens did not retain `pending_transaction_id` before this leaf. New and replayed Sync events reconcile going forward; the PR must say this plainly.

## Rejected or deferred

- **Heuristic amount/date matching:** rejected as destructive and unprovable; Sure’s issue #2013 documents the data-loss failure.
- **Delete pending + insert posted:** rejected because it discards internal identity and cascades transfer links while orphaning current/future user edits.
- **Provider payload retention:** rejected by least-data policy. Store only the link field needed for reconciliation, not raw Plaid JSON.
- **Manual duplicate merge/review:** belongs to 5.4 / 3.3.2.
- **Generic multi-provider matching:** each provider has different guarantees; this leaf implements Plaid’s explicit link contract only.
