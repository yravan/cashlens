# 3.1.1 Exact Aggregate Correction

Status: regression contract for a bounded correction; runtime changes are not
part of this commit.

Individual money rows remain JavaScript safe integers and PostgreSQL `bigint`.
That accepted input contract must not be narrowed. Aggregates can exceed the
safe-integer boundary, so SQL `sum(bigint)` results and subsequent application
arithmetic must remain exact.

The correction contract is:

- decode aggregate money as `bigint` and keep intermediate arithmetic in
  `bigint`;
- retain row-level money inputs as safe `number` values;
- return aggregate money as `bigint` through Server Component props, which
  React supports;
- preserve currency separation and request-scoped user isolation;
- allow `formatMinorUnits` to format both safe row-level numbers and exact
  aggregate BigInts, while continuing to reject unsafe Number inputs.

The focused regressions cover positive and negative odd totals beyond
`Number.MAX_SAFE_INTEGER`, account anchor arithmetic for held and owed values,
cross-account totals, and currency exponents 0, 2, and 3. Recurring detection,
annualization, and upcoming projections are deferred to the follow-up
correction.

Before the correction, the focused API run failed 12 precision assertions:
`9007199254740993` was returned as `9007199254740992`, and BigInt formatting
was rejected. The browser regression also failed on the unchanged runtime:
the dashboard formatter threw before the exact KWD amount could render.
