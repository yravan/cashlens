# 3.1.1 Exact Aggregate Correction

Status: bounded aggregate correction. Recurring detection, annualization, and
upcoming projections remain in the explicit follow-up scope.

Individual money rows remain JavaScript safe integers and PostgreSQL `bigint`.
That accepted input contract must not be narrowed. Aggregates can exceed the
safe-integer boundary, so SQL `sum(bigint)` results and subsequent application
arithmetic must remain exact.

The correction contract is:

- decode aggregate money as `bigint` and keep intermediate arithmetic in
  `bigint`;
- retain row-level money inputs as safe `number` values;
- return aggregate money as `bigint` through Server Component props, which
  React supports;
- preserve currency separation and request-scoped user isolation;
- allow `formatMinorUnits` to format both safe row-level numbers and exact
  aggregate BigInts, while continuing to reject unsafe Number inputs.

The focused regressions cover positive and negative odd totals beyond
`Number.MAX_SAFE_INTEGER`, account anchor arithmetic for held and owed values,
cross-account totals, and currency exponents 0, 2, and 3. Recurring detection,
annualization, and upcoming projections are deferred to the follow-up
correction.

## Prior art and decisions

This correction preserves the repository's exact-input and ledger semantics in
`2.2.1-manual-transactions-design.md`, `2.2.2-statement-import-design.md`, and
`2.2.3-offline-accounts-design.md`. The implementation survey also reviewed:

- [PostgreSQL aggregates](https://www.postgresql.org/docs/17/functions-aggregate.html):
  `sum(bigint)` returns exact `numeric`; decode it without a Number boundary.
- [PostgreSQL numeric types](https://www.postgresql.org/docs/16/datatype-numeric.html):
  persisted `bigint` rows remain unchanged.
- [Drizzle SQL mappings](https://orm.drizzle.team/docs/sql#sqlmapwith) and
  [codecs](https://orm.drizzle.team/docs/codecs): use a focused aggregate
  decoder rather than migrating every row-level column mapping.
- [MDN BigInt](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/BigInt)
  and [Intl formatting](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/NumberFormat/format):
  keep aggregate arithmetic homogeneous and format the exact decimal value.
- [React's client-boundary contract](https://react.dev/reference/rsc/use-client):
  BigInt is supported in Server Component props, so ordinary JSON conversion
  is unnecessary on these page paths.
- [MDN Number.MAX_SAFE_INTEGER](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Number/MAX_SAFE_INTEGER):
  preserve the accepted exact row boundary while testing sums beyond it.
- [Next.js Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components):
  retain the existing Server Component data flow rather than adding an API.
- [MDN BigInt JSON serialization](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Errors/BigInt_not_serializable):
  use decimal strings only at an ordinary JSON boundary; these aggregates do
  not cross one.
- [MDN flex wrapping](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Flexible_box_layout/Wrapping_items):
  wrap complete labeled amounts when their content cannot fit adjacent columns.
- [MDN word-break](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/word-break):
  retain an emergency break for amounts wider than the whole available surface;
  no clipping or new numerical cap.
- [MDN Range geometry](https://developer.mozilla.org/en-US/docs/Web/API/Range/getClientRects):
  assert rendered text containment, label separation and line count, not just
  element scroll width. Capture all four viewport screenshots.

Rejected: lowering the accepted row cap, clipping totals, decoding SQL sums as
Number and fixing only display, converting every persisted money field to
BigInt, or introducing a decimal dependency. Each either loses accepted data
or expands beyond the aggregate defect.

Before the correction, the focused API run failed 12 precision assertions:
`9007199254740993` was returned as `9007199254740992`, and BigInt formatting
was rejected. The browser regression also failed on the unchanged runtime:
the dashboard formatter threw before the exact KWD amount could render.
Responsive browser coverage additionally uses accepted safe rows whose sum is
near the signed-`bigint` limit, asserting exact positive and negative text,
non-overlapping labels and values, and containment at 320, 640, 768, and 1280
pixels. The independently reproduced 768px application-shell overflow and the
mobile navigation-label collision are separate layout findings; this
correction changes only the affected money surfaces.

The stronger oracle also caught a tablet summary splitting its final digit
onto another line, and valid 60-character unbroken category/group names forcing
854px of content into a 640px viewport. The fixture now covers both names;
label checks measure text ranges rather than only their enclosing boxes.
Native flex wrapping and bounded token breaking fix these cases while ordinary
amounts retain adjacent layouts when they fit. No amount or name is truncated.

Validation of the responsive follow-up: full production-build browser suite
125/125 in 6.2 minutes, lint/typecheck pass, independent Sol review clear.
All four widths have screenshots; exact amounts, category subtotals, label
separation and nearest-container bounds are asserted. Temporary audit ports
and account names are not shipped. Two default full API runs instead passed
742/743 with the pre-existing migration-upgrade test exceeding its five-second
budget. The earlier numeric-only head had 743/743 and green CI; it does not
erase the newer failure. This correction stays draft pending that investigation
and fresh CI. No timeout or assertion was weakened to obtain a pass.
