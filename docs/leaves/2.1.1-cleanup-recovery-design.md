# 2.1.1 Plaid Connect Cleanup Recovery - Prior Art and Design

Survey date: 2026-09-10

Status: validated server recovery is committed on the parent branch. Bounded client
cleanup discovery, resume wiring, and duplicate-cancel correction are implemented but
uncommitted in this follow-on worktree.

Scope: close the token-loss windows in the existing Plaid connect and duplicate-cancel
flows. After `/item/public_token/exchange`, Cash Lens must never knowingly leave a live
Plaid Item without either a durable encrypted credential that can remove it later or
confirmation that the Item is already gone. Preserve the existing signed-in connect,
account registration, duplicate warning, encrypted credential, RLS, and sanitized-error
contracts. This is recovery for one provider workflow, not a generic queue framework.

## Confirmed shipped failures

`connectPlaidItem` exchanges the one-use public token, calls `/accounts/get`, and only
then creates the connection and encrypted credential (`apps/web/lib/data/plaid.ts`). A
transient account-read failure therefore loses the only credential capable of removing
the still-live Item. The focused real-Postgres API regression in
`apps/web/tests/api/plaid-connect.test.ts` observes the forbidden state exactly:

```text
{ remoteItemLive: true, durableCredentials: 0 }
```

The duplicate-warning Cancel action has the same shape by choice: `/api/plaid/abandon`
exchanges a public token solely to remove the resulting Item. If removal fails, the
endpoint reports 502 but has nowhere durable to retain the access token, while the
browser ignores both transport and HTTP failure. Plaid's duplicate guidance gives a
simpler contract: detect the duplicate before requesting an access token and do not
exchange its public token.

The database-conflict duplicate path has a separate destructive bug. On a duplicate
`item_id`, it calls `/item/remove` with the exchanged token. The current harness case
uses the same Item and same access token as the existing connection; removal therefore
revokes the credential backing the valid connection. A same `item_id` is the same
provider resource, not a second Item safe to clean up.

## Provider contracts and careful inferences

The provider documentation supports these claims directly:

- Initial exchange returns the access token and `item_id`; the token is the handle for
  later Item reads and removal.
- `/item/remove` is required to terminate a Transactions subscription and invalidates
  the access token.
- A detected duplicate should not be exchanged.
- Update mode does not rotate the Item access token and needs no exchange.
- `ITEM_NOT_FOUND` establishes that the Item is no longer available.

Two narrower behaviors are application inferences and must stay labeled as such:

- Retrying `/item/remove` after an ambiguous response is operationally safe for this
  integration because success removes the Item and a later `ITEM_NOT_FOUND` is terminal.
  Plaid does not document `/item/remove` as an idempotent-key endpoint.
- Dropping a duplicate public token follows Plaid's explicit prevention recipe. Cash
  Lens need not claim that Plaid has no temporary internal record before exchange; the
  important documented boundary is that no access token is requested for the duplicate.

## Minimal state model

Reuse `connections` and `connection_credentials`; do not add a jobs table. Extend
`connection_status` with two internal states:

```text
provisioning -> active
provisioning -> cleanup_required -> disconnected
```

- `provisioning`: the `item_id` and encrypted access token committed, but accounts are
  not registered and the client has not received success.
- `active`: the existing user-visible connected state.
- `cleanup_required`: connect has failed after exchange; the Item must not become active,
  and the encrypted token is retained only to remove it.
- `disconnected`: the existing terminal tombstone; the credential is absent.

Only `active` connections participate in sync, repair, webhook owner mapping, or the
active-institution warning. Normal lists continue to include disconnected connections
with retained ledger data so users can purge them, but filter out both internal states.
Internal states can be selected only by the cleanup DAL. A fully cleaned provisional
tombstone has no accounts and remains invisible, matching the current handling of fully
purged disconnected rows.

## Connect sequence

1. Authenticate and derive the user exactly as today. Database-backed user resolution
   occurs before exchange, so a database already known to be unavailable creates no
   Plaid side effect.
2. Exchange the public token once. Do not retry exchange: the public token is ephemeral
   and one-use, and Plaid documents no idempotency key for this endpoint.
3. As the first post-exchange operation, transactionally insert a `provisioning`
   connection keyed by `(user, plaid, item_id)` and its AES-GCM encrypted credential.
   Return no token, ciphertext, or provider object.
4. If the unique Item key conflicts, keep the existing connection and credential and
   return `already_connected`. Do not call `/item/remove`; see duplicate semantics below.
5. Call `/accounts/get` using the now-durable credential.
6. In one RLS-scoped transaction, insert the provider accounts and balances, fill the
   institution fields, and change `provisioning` to `active`. A compare-and-set status
   predicate prevents cleanup and activation from both winning.
7. On any failure after step 3 but before step 6 commits, compare-and-set the row to
   `cleanup_required`, then attempt one immediate cleanup. If marking fails, the row
   remains `provisioning`; stale-provisioning recovery handles it after a grace period.
8. Cleanup calls `/item/remove`. On success or `ITEM_NOT_FOUND`, transactionally delete
   the credential and tombstone the connection. On every other result, retain
   `cleanup_required` and the credential for a later attempt.

No failed request later becomes active behind the user's back. Once the API reports
connect failure, recovery moves only toward provider removal and a local tombstone. The
user may start a fresh Link session.

## Cleanup retry without a queue framework

Use the existing Accounts-page resume pattern without mutating during its GET render:

- A user-scoped DAL lists only that user's stale `provisioning` and eligible
  `cleanup_required` rows.
- A small client resumer posts a guarded cleanup route once per eligible connection when
  Accounts opens. The route re-derives the user and never accepts a user id.
- Claim cleanup with a status/`updated_at` compare-and-set and a short grace period. This
  acts as a lease: concurrent page loads do not issue parallel remove calls, while a
  crashed claimant becomes eligible again.
- Each invocation makes at most one provider removal call per claimed Item. No sleep,
  in-request retry loop, cross-user sweep, new role, broker, or cron is needed.
- If Plaid removal succeeded but the final database transaction failed, the credential
  remains. The next attempt receives `ITEM_NOT_FOUND` and completes the local tombstone.

The follow-on closes the server-only operational gap without making Accounts GET
mutative. Its server render selects at most five eligible ids for the signed-in owner and
passes only those ids to a silent client component. Mutation starts after hydration via
the authenticated cleanup POST. Each id gets at most two attempts per mount; a retryable
failure waits for both the server lease and any bounded `Retry-After` before the last
attempt. Normal connection lists still hide the internal rows.

This is eventual compensation, not exactly-once execution. The durable invariant is
that nonterminal work retains the encrypted access token.

## Duplicate and cancellation semantics

### Duplicate warning canceled before exchange

The current institution-id warning happens in Link `onSuccess`, while the public token
is still unexchanged. Cancel should clear the in-memory token and warning. It should not
call `/api/plaid/abandon`, exchange the token, or call `/item/remove`. The public token
expires naturally. Browser close or navigation has the same safe result.

The existing `/api/plaid/abandon` route can be removed with its tests, or retained for
one compatibility release as an authenticated no-op that never exchanges. Deletion is
smaller if no deployed client version requires backward compatibility.

### User continues after the institution warning

Institution identity is not Item identity. Multiple logins at one bank, shared accounts,
and deliberately repeated connections can be legitimate. Continue runs the normal
durable connect sequence. A different `item_id` is accepted even when institution ids
match. Precise account-overlap detection and abuse controls are outside this repair.

### Exchange returns an already-stored `item_id`

The database unique key is authoritative under races. The existing row already carries
the durable credential for that provider Item. The losing request returns
`already_connected` without provider removal, regardless of whether its in-memory token
bytes equal the stored token. This preserves the only documented same-Item contract:
one Item identity must stay live for the existing connection.

Plaid says normal update mode does not change the access token and is not exchanged, so
a different token returned for the same `item_id` would be a provider-contract anomaly,
not evidence of a second removable Item. Log only a sanitized anomaly class and local
connection id; never either token. Do not rotate the stored credential or remove the
Item without a separately researched provider contract.

### Concurrent requests

- Same user, same `item_id`: the unique index chooses one provisional/active row. Losers
  neither overwrite credentials nor remove the shared Item.
- Same institution, different `item_id`: both may succeed because the user explicitly
  continued and the provider resources are distinct.
- Different users: uniqueness remains user-scoped. RLS and explicit user predicates
  prevent either user's recovery rows or credentials from being observed or actioned by
  the other.
- Cleanup versus activation: status compare-and-set allows only one terminal direction.
  A request already reported failed cannot later activate.

## Unavoidable exchange-to-persistence boundary

Postgres cannot atomically commit Plaid's exchange with the encrypted credential row.
There is an unavoidable interval after Plaid returns the access token and before the
`provisioning` transaction commits. A process crash in that interval loses the token.
Likewise, if persistence fails and the immediate compensating `/item/remove` also fails,
the application has no durable handle to retry.

The implementation must shrink and expose this risk without claiming to eliminate it:

- resolve the authenticated user before exchange;
- make provisional persistence the first operation after exchange;
- on persistence failure while the process still has the token, immediately attempt
  `/item/remove` and treat success or `ITEM_NOT_FOUND` as compensated;
- emit a secret-free high-severity event when persistence and compensation both fail;
- retain provider request identifiers only if the sanitized Plaid error boundary can do
  so without retaining raw errors or credentials.

Pre-creating an empty attempt row before Link proves the database was available earlier
but cannot store a token that does not yet exist. Browser storage would expose the
secret. A broker/outbox written after exchange has the same dual-write boundary. A
durable workflow would also need a provider-supported replay/idempotency contract for
the one-use exchange; Plaid documents none. These options add machinery without making
the stated boundary atomic, so they are rejected for this leaf.

Operationally, the Plaid dashboard/billing inventory remains the last-resort detector
for this residual. The design materially closes all failures after the provisional row
commits but does not promise recovery from a crash before that commit.

## Security and database contract

- `provisioning` and `cleanup_required` rows use the existing forced RLS and explicit
  `user_id` predicates. Cleanup takes only a validated connection UUID, re-derives the
  signed-in user, and returns unknown for cross-user and nonexistent ids alike.
- The access token stays only in `connection_credentials.ciphertext`, encrypted with the
  existing `(userId, connectionId)` AAD. It never appears in browser state, route JSON,
  logs, test failure output, or provider error objects escaping `lib/plaid`.
- Extend app-role column grants only for the fields needed to finalize a provisional
  connection. A database trigger permits institution metadata changes only during
  `provisioning -> active` and rejects invalid status transitions, so the grant cannot
  rewrite an active or disconnected connection's identity. Do not grant credential
  UPDATE if delete-and-insert is unnecessary.
- Every normal connection/sync/webhook query must require `status = 'active'` unless it
  is explicitly the cleanup DAL. A live cleanup Item receiving a webhook must not start
  transaction ingestion.
- Existing same-origin POST guards remain on exchange and cleanup routes.
- Store no raw provider error message. The cleanup state and timestamps are sufficient;
  provider error history remains leaf 2.1.6 territory.

## Behavioral verification

All provider behavior uses the Plaid substitute through the production SDK interface;
all persistence assertions use real local Postgres through the app role and RLS.

1. The existing focused red regression: inject `/accounts/get` failure after successful
   exchange and forbid `{ remoteItemLive: true, durableCredentials: 0 }`.
2. Account-read failure plus successful immediate removal: 502, no active connection or
   accounts, remote Item gone, credential deleted, hidden tombstone only.
3. Account-read failure plus removal failure: 502, remote Item live, exactly one
   `cleanup_required` row, and one ciphertext that does not contain the access token.
4. Retry after removal failure: the signed-in owner removes the Item and credential;
   replay after provider success treats `ITEM_NOT_FOUND` as terminal and changes nothing.
5. Crash/failure after remote success but before local tombstone: a retained cleanup row
   heals on retry via `ITEM_NOT_FOUND`.
6. Stale `provisioning`: after the grace period it moves toward cleanup, never active;
   a fresh in-flight row is not claimed.
7. Duplicate warning Cancel: no exchange request, no remove request, and no database row.
8. Same-Item duplicate: 409 (or the existing idempotent response contract), original
   credential unchanged, remote Item live, and zero removal requests. This replaces the
   current assertion that the valid Item is removed.
9. Concurrent same-Item exchanges: one durable connection/credential, no removal of the
   winner's Item, no unhandled unique violation, and no token in either response.
10. Same institution with different Item ids after explicit Continue: both connections
    may register; institution id alone never becomes a server uniqueness rule.
11. Persistence rejection after exchange: induce a real Postgres insert failure, assert
    the in-process compensating remove is attempted, and assert successful compensation
    leaves no remote Item. The simultaneous process-crash/remove-failure case remains the
    explicit non-guarantee above, not a test with a dishonest expected outcome.
12. User B cannot list, claim, remove, read, or infer user A's provisional/cleanup row or
    credential. A raw app-role query supplies the RLS backstop.
13. Response body/header and inspected-error sweeps cover exchange and cleanup failures;
    neither access token, ciphertext, nor substitute API secret appears.
14. Mutation proof: removing provisional persistence, deleting the credential on failed
    remove, permitting cleanup of another user's row, or restoring duplicate
    `/item/remove` makes a focused test fail.

The exact focused invariant command is:

```bash
pnpm --filter web exec vitest run tests/api/plaid-connect.test.ts -t "an accounts/get failure removes the Item or retains an encrypted cleanup credential"
```

## Bounded implementation sequence

Keep the repair within three reviewable PRs, each targeting roughly 500 changed lines or
less excluding generated migration metadata:

1. **Research:** this document records the separately confirmed RED evidence, but does
   not merge an intentionally failing test or production behavior.
2. **Durable server recovery:** the regression tests land with the fix: status migration
   and least-privilege grants; provisional encrypted persistence; atomic activation;
   immediate cleanup; same-Item no-remove; stale/user-scoped retry DAL and authenticated
   POST route; failure, concurrency, isolation, and secret sweeps. Accounts GET remains
   read-only. No generic worker or provider abstraction.
3. **Client cancellation and resume:** cancel duplicate without exchange, remove the
   unsafe client call to the compatibility no-op abandon route, mount the small Accounts
   cleanup resumer, and cover the browser behavior. Preserve the existing connect and
   initial-backfill user experience.

If PR 2 exceeds the bound, split migration/DAL from orchestration/tests; do not solve it
by weakening state, isolation, or failure coverage.

## Explicit deferrals

No global queue or cron, provider-agnostic saga framework, cross-user duplicate/fraud
detection, precise account-overlap matching, automatic credential rotation for an
undocumented same-Item token change, historical cleanup dashboard, raw provider error
timeline, or guarantee across the exchange-to-Postgres crash boundary. Those are not
required to stop the confirmed orphan and same-Item revocation regressions.
