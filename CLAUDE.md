# CLAUDE.md — Cash Lens

Ledger-first personal finance app. Read `specs/vision.md` for the product thesis and `FEATURES.md` for the feature tree — the tree is the single source of truth for scope and priorities.

## Working model

- The unit of work is ONE leaf node from FEATURES.md. Stay inside it: 1–3 PRs, roughly ≤500 changed lines, reviewable in one sitting.
- Research before building: every leaf starts with a survey of how production systems and open-source projects solve the same problem — at least 10 sources for a simple leaf, up to 50 for a complex one (implementations, libraries, docs, post-mortems). Prefer assembling proven libraries and patterns over custom code; write custom code only where this product's wedge demands it. Open the PR with a prior-art note: what you found, adopted, and rejected.
- Each leaf PR checks in its full prior-art survey and any approved design doc under `docs/leaves/` (e.g. `docs/leaves/4.1.1-prior-art.md`) — the repo is the single memory of record; scratch space is ephemeral.
- Before coding, restate the leaf's scope. Anything beyond the node's description is scope creep — note it in the PR instead of building it.
- Don't refactor neighboring code or touch other leaves' territory in the same PR.
- If implementation reveals the tree is wrong (bad split, missing dependency), update FEATURES.md in its own small commit and say so in the PR.
- After the leaf PR is opened, an independent simplification pass reviews it with fresh eyes (no builder context): condense and aggressively simplify the diff — same behavior, same tests, fewer lines — pushed to the same PR before founder review.

## Code style

- Comments, docstrings, and prose in code: minimum, ideally zero. Code explains itself through names and structure; comment only a constraint the code can't express. Never narrate what a line does or restate it in English.

## Security — the defining tenet

One person's complete financial life lives in this system. Every leaf is built like that's true, because it is.

- Least data, least privilege: store only what the feature needs; request the narrowest provider scopes that work.
- Secrets and provider tokens are encrypted at rest and never appear in the browser, logs, fixtures, or test output.
- Any surface touching user data ships with a cross-user isolation test: user B can never read user A's anything.
- All input is validated at the boundary; queries and commands are never assembled from raw input.
- A new dependency is a security decision — prefer maintained, widely used ones, and keep scanning green.
- If a leaf introduces new risk surface (uploads, webhooks, background jobs), name it in the PR with its mitigation.

- Credential storage (leaf 2.1.2): provider secrets live only in `connection_credentials.ciphertext`, sealed by `lib/crypto/credentials.ts` — AES-256-GCM envelopes (`v1.<keyId>.<nonce>.<ct>`) under keys HKDF-derived from the `CREDENTIAL_ENCRYPTION_KEYS` env keyring (`id:64hex,…`; first entry encrypts, all decrypt; rotate by prepending; read lazily so builds/boots never need it). AAD binds each ciphertext to `(userId, connectionId)` — rows can't be transplanted, even by SQL. The crypto module is importable only from `lib/data` (ESLint fence); reads return a `SecretString` whose `toJSON` throws — call `.expose()` only where the value is spent. Disconnect hard-deletes the credential row and tombstones the connection (`status='disconnected'`; since 2.1.5 only after `/item/remove` succeeds — see below); the app role has no DELETE on `connections` and column-scoped UPDATE only (`status`,`updated_at`; 2.1.3 adds `backfill_status`,`sync_cursor`; 2.1.5 adds `provider_error`,`webhook_url`). The api harness generates an ephemeral keyring per run (CI stays zero-secret); production needs the var set before 2.1.1 ships (docs/production.md).
- Plaid connect (leaf 2.1.1): `POST /api/plaid/link-token` mints a Link token (products `['transactions']` only, 730-day history consent, no redirect_uri — web OAuth uses Plaid's popup flow) and the Accounts-page Connect button (react-plaid-link) opens Link; `POST /api/plaid/exchange` validates `{publicToken}` at the boundary, exchanges it, vaults the access token via `createConnection`, then registers the item's accounts + initial balances from `/accounts/get` (server truth — Link metadata is never trusted). Balances are stored as Plaid reports them (credit/loan `current` positive = owed, matching the seeded dataset); transaction-sign negation is 2.1.3's. Duplicate item (same `provider_item_id`) → `/item/remove` the fresh token, 409. The `plaid` package and `lib/plaid/*` are ESLint-fenced to `lib/data` — raw Plaid client errors embed the API secret in `error.config.headers`, so `lib/plaid/client.ts` rethrows sanitized domain errors and nothing else may touch the SDK. Both POST routes reject cross-origin browser requests (no CSRF protection on route handlers otherwise). Env: `PLAID_CLIENT_ID`/`PLAID_SECRET`/`PLAID_ENV` (+ a real `CREDENTIAL_ENCRYPTION_KEYS`) — read lazily; the api suite needs none of them (vitest aliases `plaid` to `tests/harness/plaid.ts`, same pattern as Clerk: sandbox-shaped fixtures, single-use public tokens, loud throws elsewhere). Real-sandbox coverage lives in `e2e/plaid.signed-in.spec.ts` (headless `/sandbox/public_token/create` → exchange; Link UI is never driven per Plaid's own testing guidance), skipped when `PLAID_*` is unset; CI's e2e job carries sandbox-only repo secrets and generates an ephemeral e2e keyring per run.
- Sync engine (leaves 2.1.3 + 2.1.4): `lib/data/plaid-sync.ts` `advanceSync` pages Plaid `/transactions/sync` from the stored cursor (500/page, ≤20 provider calls per run — the budget spans mutation restarts, ≤2 restarts from the run's origin cursor) and applies `added` (insert-or-ignore), `modified` (upsert — an unseen id inserts), and `removed` (delete, pendings included; the leftover-pending linkage is 3.2.1's) in one transaction with `sync_cursor` + `backfill_status`. The cursor UPDATE runs first as a compare-and-set (`is not distinct from` the read cursor) — 0 rows = a concurrent run won; commit nothing, report zeros. Idempotent on `(account_id, source, source_id)`; sign convention lands at ingestion (Plaid positive = money out, negated into net-worth); provider rows with no usable currency fall back to the account's registered currency, never hard-coded USD. One malformed or unregistered-account row never poisons a run: it's skipped, counted in the response `skipped`, and logged (`lib/log.ts` one-line JSON events: ids, counts, error classes — never payloads, tokens, or amounts; `plaid_sync.run` / `run_failed` / `lost_race` / `update_status_unknown` / `balance_refresh_failed`). `RATE_LIMIT_EXCEEDED` → 429 + `Retry-After` (clients wait and retry); `TRANSACTIONS_UPDATE_STATUS_UNKNOWN` keeps `in_progress` honestly (never fakes complete) and heals via retriggers. Balances refresh through `/accounts/balance/get` (the endpoint that pulls live from the institution; 30-day `min_last_updated_datetime` floor for the Capital One quirk) only on drained runs that changed rows or flipped status — failures log and never fail the sync. Triggers: connect-button polls `POST /api/connections/:id/sync` to completion; `listResumableSyncs` + the accounts-page `SyncResume` component silently resume any `in_progress` connection older than a 2-min grace and re-sync any active connection idle >6h (`updated_at` is the freshness marker — only sync commits and disconnect touch it), so interrupted imports self-heal on the next visit; overlapping triggers are safe by the CAS. A global cron sweep is impossible by design — the app role can't enumerate users' connections under RLS; triggers run as the signed-in user or the verified webhook. Grants: the app role's `transactions` surface is INSERT + column-scoped UPDATE (`amount_minor,currency,date,description,merchant,status,updated_at` — identity/provenance columns immutable) + DELETE, all RLS-scoped (migrations 0010/0011).
- Plaid webhook (leaf 2.1.4): `POST /api/plaid/webhook` — public (in `proxy.ts` PUBLIC_PATHS), authenticated solely by Plaid's ES256 JWT in `Plaid-Verification`, verified in `lib/plaid/webhook.ts` per Plaid's documented steps: raw `request.text()` bytes hashed (never re-stringified — Plaid pretty-prints), alg pinned to ES256 before any crypto, per-kid key cache via `/webhook_verification_key/get` (expired keys rejected, unexpired ones re-fetched when a new kid appears, unknown kids negative-cached 5 min), `jose` `jwtVerify` + constant-time sha256 compare, 256KB body cap before any work. A correctly signed but stale (>5 min) delivery is acked 200 and *ignored* — Plaid retries up to 24h and a rejected retry feeds its 90%-rejection circuit breaker, while an ignored one costs nothing (replay-safe: processing is idempotent anyway). Verified `item_id` → owner via request-local-setting RLS policies (`connections_select_webhook_item` keyed on `app.plaid_item_id`, `users_select_webhook_owner` on `app.plaid_webhook_user_id` — no SECURITY DEFINER, no new roles; migration 0012) → one bounded `advanceSyncFor` per owning connection, inline (Vercel Hobby has no queue; typical steady-state run is one page, and a slow run's Plaid retry is absorbed by the CAS). Unknown items ack `{}` identically to known ones (no existence oracle); legacy TRANSACTIONS codes no-op silently; ITEM codes are actioned per leaf 2.1.5 below (`NEW_ACCOUNTS_AVAILABLE` stays the named 2.1.6 seam); everything else logs and acks. `SYNC_UPDATES_AVAILABLE` only starts flowing after the first `/transactions/sync` call on an item (the connect flow's backfill does this) *and* only if the item was linked with a webhook URL: `PLAID_WEBHOOK_URL` (unset locally — Plaid can't reach localhost; prod value in docs/production.md) is stamped at link-token time. The harness signs real ES256 JWTs with ephemeral per-run keypairs and serves the JWK through the substitute — webhook tests stay zero-secret and network-free.
- Connection health (leaf 2.1.5): `connections.provider_error` holds only allowlisted user-actionable Plaid codes (`LOGIN_REPAIR_CODES` = login-class, `WARNING_REPAIR_CODES` = consent-lapsing webhooks, both in `lib/data/plaid.ts`); transient provider errors are log-only by design (error timeline is 2.1.6). Login-class codes are set when `/transactions/sync` fails with them (the sync route answers 409 `reauth_required`) and cleared by any committed run; warning codes arrive via ITEM webhooks and survive working syncs until real re-consent. Verified ITEM webhooks act through the 2.1.4 owner mapping: `ERROR` marks (allowlisted `error.error_code` only), `LOGIN_REPAIRED` clears (Plaid sends it for out-of-band repairs only), `USER_PERMISSION_REVOKED` hard-deletes the credential and tombstones with the reason — ledger data stays until the user purges. Committed sync runs stamp `PLAID_WEBHOOK_URL` onto the item via `/item/webhook/update` whenever `connections.webhook_url` differs (items born before the URL existed self-arm; update-mode link tokens cannot carry a webhook). The accounts page renders per-connection status: Connected / Importing history / Needs attention / Disconnected. Actions: repair mints an update-mode link token on click (`/api/connections/[id]/repair-token`; 30-minute tokens, so never mint at page load; the access token never changes and the update-mode public_token is never exchanged; Link completion posts `/repaired` to clear the mark — Plaid won't webhook in-app repairs — then drives a sync; a mint failing ITEM_NOT_FOUND revokes the connection locally, 410). Disconnect (`/api/connections/[id]/disconnect` `{purge}`) is remote-first and fail-closed: `/item/remove` must succeed or answer ITEM_NOT_FOUND before the credential row is deleted and the connection tombstoned — any other provider failure aborts with nothing changed (a credential deleted after a failed remove would leave the item billing forever). Optional purge deletes the connection's accounts and lets the user-scoped composite-FK cascades take transactions and balances (the app role's only new privilege: RLS-scoped DELETE on `accounts`); a disconnected connection with data can be purged later, and fully purged tombstones leave the UI (rows stay in the DB). Declining the duplicate-institution warning in the connect flow posts `/api/plaid/abandon` (exchange → remove, never stored) so a backed-out Link session leaves no orphan item.
- Accounts overview (leaf 6.3.1): `lib/data/ledger.ts` `accountOverview` reads the signed-in user's accounts plus current balance through the normal RLS request scope and returns stable type/name ordering with separate per-currency `cashOnHand` (depository) and `creditOwed` (credit) totals — unlike currencies are never combined and a null current balance stays unavailable rather than falling back to available or zero. The Accounts page groups every retained account as Cash / Credit / Loans / Investments / Other while preserving the 2.1.5 connection controls; disconnected retained data remains visible and purged data disappears naturally. Canonical overview expectations live under `EXPECTED[persona].overview`; `tests/api/accounts-overview.test.ts` pins exact values, signed-out behavior, missing balances, and a raw-query RLS backstop, while the dual-user browser seam pins exact groups, balances, currency totals, empty state, and isolation.
- Categories (leaf 4.1.1): `categories` is per-user rows only — never shared system rows — with one nesting level via the composite self-FK `(parent_id, user_id) → (id, user_id)`, per-level unique names, own-row select/insert RLS + FORCE RLS; the app role gets SELECT+INSERT only (update/delete arrive with 4.1.2, so the default tree is immutable to the app today). The default taxonomy (15 groups / 65 leaves) lives in `lib/ledger/default-categories.ts` — single source for both the DAL and the seed dataset — and is planted idempotently (conflict-ignore + parent re-read) on a user's first `listCategoryGroups()` read, so pre-existing users get it too. `transactions.category_id` (nullable uuid, composite FK to categories, migrations 0017/0018) is the whole assignment model: NULL is uncategorized (never a fake row), and the app role's transactions UPDATE column list grows by exactly `category_id`. Writes go through `setTransactionCategory` (UUID-validated at the boundary, groups never assignable, cross-user transaction/category ids indistinguishable from unknown ids) behind origin-guarded `POST /api/transactions/[transactionId]/category`; the per-row assignment select rides inside the 3.6.1 history rows (same component, same route), and 4.2.1 will write the same column through the same DAL. - Transaction history (leaf 3.6.1, design: `docs/leaves/3.6.1-transaction-history-design.md`): `/transactions` is the chronological searchable ledger. The closed URL schema (`q`,`account`,`category`,`from`,`to`,`currency`,`min`,`max`,`page`) is validated by the pure parser `lib/ledger/history-query.ts` before any SQL — unknown or repeated params reject, empty strings mean absent (native GET forms submit them), `min`/`max` are non-negative major-unit decimals accepted only with `currency` and converted exactly at the currency exponent (`currencyExponent` in `lib/ledger/minor-units.ts`), search is a literal ILIKE with `\%_` escaped (wildcard input matches nothing). One DAL, `transactionHistory(parsed)` in `lib/data/ledger.ts`: rows (account name + category name joined, own-user predicates on every join in addition to RLS) ordered `date DESC, created_at DESC, id DESC`, fixed 50-row offset pages, honest `total`/`page`/`pageCount` (a well-formed page past the end is a valid empty result), plus form options (own accounts, category groups via the shared tx-scoped `categoryGroupsFor` — which plants the 4.1.1 defaults on first read — and the ledger's distinct currencies; empty `currencies` doubles as the ledger-empty signal). An invalid parse returns options only — malformed input never parameterizes SQL. Cross-user account/category ids produce byte-identical results to unknown ids. The page is a native GET `next/form` (Apply/Clear, push navigation, shareable URLs, back-button safe) with the form **keyed on the applied query** — soft navigation reuses uncontrolled inputs' DOM state, so without the key a Clear leaves stale control values that silently re-apply (caught in manual exercise, pinned in e2e). Amount filters compare absolute magnitude within one currency; sorting alternatives, fuzzy search, and detail views are 3.6.3/3.6.2. `EXPECTED[persona].history` carries the canonical chronology (`order`: date desc then id desc — seed rows share one `created_at`) and `currencies`.
- LLM auto-categorization (leaf 4.2.1): uncategorized transactions (`category_id IS NULL` — the only rows the engine may ever write) get a category, confidence, and one-line reason from `claude-haiku-4-5` (temperature 0, closed `json_schema` output). Provenance lives on `transactions`: `category_source` ('user'|'auto'), `category_confidence` ('low'|'medium'|'high'), `category_reason` (≤200 chars); CHECKs make source require a category and confidence/reason auto-only; migrations 0019/0020 grow the app role's UPDATE list by exactly those three columns; pre-4.2.1 categorized rows keep NULL source (unknown provenance). Manual assignment stamps 'user' and wipes the auto fields; the auto write's `IS NULL` predicate makes a concurrent manual pick win (and re-syncs already exclude category columns from the modified-upsert). `source='auto' AND confidence='low'` is the durable "flagged for review" state — rendered as the amber "Auto · low — check" marker on history rows; the review queue itself is 5.1. Trigger is pull-only as the signed-in user (no queue/cron by design): the transactions page mounts `AutoCategorize` when `llmConfigured()` and uncategorized rows exist; it loops `POST /api/transactions/categorize` (each POST = one Haiku call over the ≤40 newest uncategorized rows, ~$0.01) up to 12 batches with Retry-After backoff, stops on any no-progress batch, refreshes per progressing batch — so a failing batch can never spin. Least data is enforced inside `lib/llm/classify.ts`, not by caller discipline: prompts carry only description/merchant/direction plus indexed "Group > Leaf" labels — no ids, dates, amounts, currencies, or account names ever serialize (mutation-tested); JSON encoding defuses row/instruction spoofing; prompts and completions are never logged. Responses are untrusted input: per-entry allowlist validation (index ranges, enum confidence, reason cap), invalid entries dropped (their rows stay NULL and retry under later runs' caps), unknown categories never invented; the prompt offers leaves only and requires a pick for every row (generic fallback at low confidence), so runs are idempotent with no attempt-tracking column. `@anthropic-ai/sdk` is ESLint-fenced to `lib/llm` and `lib/llm` to `lib/data`; provider errors leave the module only as sanitized classes (`LlmUnconfiguredError`→503, `LlmRateLimitedError` incl. 529→429+Retry-After, otherwise→502 via `lib/api/llm-errors.ts`). `ANTHROPIC_API_KEY` is lazy like `PLAID_*`: unset = dormant feature (no trigger, 503) — the api suite aliases the SDK to `tests/harness/anthropic.ts` (zero secrets, zero network), and e2e drives the real UI against `e2e/llm-stub.ts` through the SDK's `ANTHROPIC_BASE_URL` override unless a real key is present, in which case `categorize.signed-in.spec.ts` doubles as the live-provider smoke. Provisioning the production key is a founder step (docs/production.md).
- Transfer matching (leaf 3.3.1, survey: `docs/leaves/3.3.1-prior-art.md`): `transfer_pairs` (migrations 0021/0022) links two POSTED transactions of one user as an internal transfer — same currency, exact inverse non-zero amounts, different accounts, dates ≤4 days apart in either direction (receivers can post first). The matcher is a pure function (`lib/ledger/transfer-matching.ts`, exhaustively unit-tested): candidate edges sorted (date distance, outflow date, ids) and claimed greedily, so runs are deterministic and each transaction sits in ≤1 active pair — a row's sign fixes which slot it can occupy, and a partial unique on each slot (`WHERE dismissed_at IS NULL`) holds that line in the DB; the full `(outflow,inflow)` unique is dismissal memory. `matchTransfersFor` (`lib/data/transfers.ts`) is one idempotent RLS-scoped transaction: dissolve active pairs whose re-synced halves broke the rule, then insert new pairs `ON CONFLICT DO NOTHING` (races and replays are no-ops); composite `(txn,user)` FKs cascade, so the 2.1.4 removed path and 2.1.5 purge unpair automatically. Triggers (no cron by design): inline after any committed sync with row activity (failures log `transfer_match.run_failed`, never fail the sync) and `POST /api/transfers/match` fired on every transactions-page visit (`TransferMatch` — this is what pairs seeded/manual/import ledgers). Paired rows render a textual "Transfer · to/from <account>" marker with "Not a transfer" (`POST /api/transfers/[pairId]/unlink`), which stamps `dismissed_at` — lossless (both transactions untouched), never re-proposed, both halves stay free for other pairs; manual mark-as-transfer is deferred to 5.1/5.4. Actively paired rows leave the 4.2.1 queue via the shared `uncategorized` predicate (batch select AND write, so mid-flight pairings win like manual picks) and re-enter on unlink; pairing never writes categories and never erases one already set. App grants: SELECT/INSERT/DELETE + UPDATE(`dismissed_at`,`updated_at`) only. Cross-currency transfers stay unmatched (no FX source; named deferral). 6.1.1 true spend = exclude rows in active pairs. `EXPECTED[persona].transfers` carries the seed's two pairs (savings move, card payment), `pairedRows`, and `autoQueue` (uncategorized minus paired).
- Cash flow (leaf 6.1.1, survey: `docs/leaves/6.1.1-prior-art.md`): the Dashboard (`app/(app)/page.tsx`) is the true-spend summary — `cashFlowSummary()` in `lib/data/ledger.ts` groups the signed-in user's POSTED transactions by currency + calendar month (`to_char` on the date-only column: no clock read, no timezone math — visible months derive from the data, so tests stay frozen-clock-free) and excludes any row in an active transfer_pair via NOT EXISTS — pair membership, not category (dismissed pairs count again; net is invariant either way because pairs are zero-sum). One section per currency (asc), never combined, no FX. Pending rows are disclosed (`pendingCount`), never counted: the 3.3.1 matcher's domain is posted-only, so an included pending transfer leg could never pair and would double-count, and 3.2.1 reconciliation hasn't landed; `transferRows` (posted rows in active pairs) renders as the visible exclusion count. `TransferMatch` mounts on the dashboard too, so the landing page pairs a seeded/manual/import ledger before its first numbers are read. Month rows link into `/transactions?from&to&currency` (3.6.1 schema reuse; drill-down proper is 6.1.2). `EXPECTED[persona].flow` carries the month anchors; the seed demonstration is March USD 477112/-220279 unpaired vs 272112/-15279 paired, net 256833 both ways. Group-level `app/(app)/loading.tsx`/`error.tsx` serve only the dashboard today (accounts/transactions carry their own); Next 16 error boundaries receive `retry`, not `reset`.

The e2e job runs in the pinned `mcr.microsoft.com/playwright` image (keep its tag in lockstep with `@playwright/test`) so no apt/CDN sits on the hot path. The repo is public — Actions logs and artifacts are world-readable: `e2e/scrub-secrets.ts` (Playwright `globalTeardown`) strips Clerk tokens from `test-results/`, and CI refuses to upload artifacts without its `.scrubbed` stamp; never enable `DEBUG=pw:api` and never assert with `toBeOK()` (lint-enforced), both print live session cookies into logs.
- Production (leaf 1.3, runbook + go-live checklist: `docs/production.md`): **Vercel** (project `cashlens`, root directory `apps/web`) deploys `main` only — `apps/web/vercel.json` skips non-production builds until leaf 10.6 and builds with `pnpm deploy:build`, which applies committed migrations as `cashlens_owner` (gated on `VERCEL_ENV=production`, direct URL) before `next build`, so a failed migration fails the deploy. Database is **Neon** (direct account, never Marketplace; same two-role model; runtime `DATABASE_URL` uses the `-pooler` host, owner/superuser URLs stay direct; all prod URLs pin `?sslmode=verify-full`). NEVER create roles in a provider console — console roles silently get `BYPASSRLS` (neondatabase/neon#12926); `pnpm db:setup` is the only role source and fails closed on `rolbypassrls`. `GET /api/health` reports app+db (200/503, public). DB fail-fast budgets: 5s connect / 20s client query / 15s statement / 30s idle-in-transaction (role-level).

## Testing policy (non-negotiable)

Tests exist to catch regressions in behavior users care about — not to demonstrate that code was written.

**Write tests at the seams:**

- Most coverage: API-level tests hitting real endpoints with a real local database.
- A few real-browser end-to-end tests for the money paths: sign in → connect → transactions appear → cash-flow numbers are right.
- Unit tests only where real logic lives — transfer matching, dedup, splits math, recurring detection, rules. Those deserve exhaustive cases.

**Banned (fake tests):**

- NEVER mock code this repo owns. Mock only true externals (Plaid, Gmail, the LLM) — behind the same interface production uses, with realistic sandbox/recorded fixtures.
- No render-without-crashing, element-is-visible, or snapshot-only tests. Every test asserts a behavior or a number.
- No sleeps to fix flaky tests — fix the race. No skipping or quarantining a test to get green.
- Don't test the framework (routing resolves, ORM persists). Test what this codebase decided.

**Determinism:** tests run against the seeded fixture dataset (known users, accounts, transactions with known totals) and a frozen clock, so assertions are exact — `true_spend == 1234.56`, never `> 0`.

**Prove the test works:** a new test must fail when the behavior it guards is broken. If you never saw it red, you don't know that it tests anything.

## Definition of done — every leaf, before claiming complete

1. Lint, typecheck, and the FULL test suite pass locally — paste the output, don't assert it.
2. Run the actual app and exercise the feature once as a user would.
3. New behavior has tests per the policy above. If you had to edit existing assertions, explain why in the PR.
4. Security rules hold — including the isolation test wherever user data is touched.
5. CI is green on the PR.

## Repository etiquette

- NEVER merge a PR. The founder personally reviews and merges every PR. Open it, report it, stop — even if all checks are green.
- Branch per leaf: `leaf/<node-id>-short-name` (e.g. `leaf/2.1.3-initial-backfill`).
- PR title starts with the node ID. Body: what the node promises, what shipped, evidence (test output), anything deferred.
- Never commit secrets. Env files stay untracked; `.gitignore` already covers them.
