# CLAUDE.md — Cash Lens

Ledger-first personal finance app. Read `specs/vision.md` for the product thesis and `FEATURES.md` for the feature tree — the tree is the single source of truth for scope and priorities.

## Working model

- The unit of work is ONE leaf node from FEATURES.md. Stay inside it: 1–3 PRs, roughly ≤500 changed lines, reviewable in one sitting.
- Research before building: every leaf starts with a survey of how production systems and open-source projects solve the same problem — at least 10 sources for a simple leaf, up to 50 for a complex one (implementations, libraries, docs, post-mortems). Prefer assembling proven libraries and patterns over custom code; write custom code only where this product's wedge demands it. Open the PR with a prior-art note: what you found, adopted, and rejected.
- Before coding, restate the leaf's scope. Anything beyond the node's description is scope creep — note it in the PR instead of building it.
- Don't refactor neighboring code or touch other leaves' territory in the same PR.
- If implementation reveals the tree is wrong (bad split, missing dependency), update FEATURES.md in its own small commit and say so in the PR.
- After the leaf PR is opened, an independent simplification pass reviews it with fresh eyes (no builder context): condense and aggressively simplify the diff — same behavior, same tests, fewer lines — pushed to the same PR before founder review.

## Code style

- Comments, docstrings, and prose in code: minimum, ideally zero. Code explains itself through names and structure; comment only a constraint the code can't express. Never narrate what a line does or restate it in English.

## Security — the defining tenet

One person's complete financial life lives in this system. Every leaf is built like that's true, because it is.

- Least data, least privilege: store only what the feature needs; request the narrowest provider scopes that work.
- Secrets and provider tokens are encrypted at rest and never appear in the browser, logs, fixtures, or test output.
- Any surface touching user data ships with a cross-user isolation test: user B can never read user A's anything.
- All input is validated at the boundary; queries and commands are never assembled from raw input.
- A new dependency is a security decision — prefer maintained, widely used ones, and keep scanning green.
- If a leaf introduces new risk surface (uploads, webhooks, background jobs), name it in the PR with its mitigation.

## Stack & commands

Chosen in leaf 1.1.1 (survey in that PR): **pnpm workspace** (root scripts delegate to apps); **apps/web** is **Next.js 16** (App Router, TypeScript, Tailwind v4, ESLint 9 flat config) with **Clerk** as the managed auth provider (Google-only sign-in). E2E tests are **Playwright** against a production build on port 3100 and the real Clerk development instance. YOU MUST keep this section current as the stack lands: exact dev-server, test, lint, and typecheck commands, per app, as used in CI.

- web (run from repo root, or inside `apps/web` without the filter): `pnpm dev` · `pnpm test:api` · `pnpm test:e2e` · `pnpm lint` · `pnpm typecheck` · `pnpm build`
- Env: copy `apps/web/.env.example` to `apps/web/.env.local` and fill the Clerk dev keys (`npx clerk@latest env pull` — the CLI is linked to the "Cash Lens" Clerk app). E2E tests need them, plus the database below.
- Database (chosen in leaf 1.1.2): **PostgreSQL 16** in Docker (`compose.yaml`, host port 5433) with **Drizzle ORM** and committed SQL migrations (`apps/web/db/migrations`). Setup: `pnpm db:up` then `pnpm db:setup` (idempotently creates roles + database, runs migrations; any Postgres 16+ works — point the `DATABASE_URL*` vars at it). Schema change: edit `apps/web/lib/db/schema.ts` → `pnpm db:generate` → commit the SQL → `pnpm db:migrate`. Full reset: `docker compose down -v`, then `pnpm db:up && pnpm db:setup`.
- Seeded data (leaf 10.4): one canonical deterministic dataset in `apps/web/db/seed/dataset.ts` — personas `demo` (5 accounts, 16 transactions, USD+EUR, every source and status, two zero-sum transfer pairs), `neighbor` (1 account/2 transactions, the isolation counterpart), `empty` (0/0). Aggregates are derived from the rows and exported as `EXPECTED`, with hand-verified anchors pinned in `tests/api/seed-dataset.test.ts`; tests assert against `EXPECTED`, never hand-recounted literals. Api tests call `seedDataset(adminDb())` (optionally mapping personas onto provisioned users), e2e calls `seedLedgerFixture({ demo, neighbor })` for the two real Clerk e2e users, and `pnpm db:seed [clerkUserId]` fills the local dev database — pass your own Clerk id to browse the demo ledger under your dev-instance sign-in. The dataset is fake: no real financial data or provider credentials anywhere, and `db:seed` fails closed on any non-loopback database URL (`db/seed/local-only.ts`, guard is tested). No frozen-clock helper yet — nothing under test reads the clock; dataset dates are fixed absolutes. Transaction signs follow the ledger's net-worth convention (Plaid's is the inverse; 2.1.3 negates at ingestion).
- Data scoping (leaf 1.1.2 — binding on every later leaf): the app connects as the non-owner role `cashlens_app`; every user-owned table declares RLS policies in the schema keyed on `current_setting('app.clerk_user_id', true)` and gets `FORCE ROW LEVEL SECURITY` in its migration (the e2e coverage test fails any public table without it). All user-data access goes through `lib/data` DAL functions that derive the user from `auth()` — never from caller input — inside `withRequestScope`. The db client is importable only within `lib/db`/`lib/data` (ESLint-enforced).
- Credential storage (leaf 2.1.2): provider secrets live only in `connection_credentials.ciphertext`, sealed by `lib/crypto/credentials.ts` — AES-256-GCM envelopes (`v1.<keyId>.<nonce>.<ct>`) under keys HKDF-derived from the `CREDENTIAL_ENCRYPTION_KEYS` env keyring (`id:64hex,…`; first entry encrypts, all decrypt; rotate by prepending; read lazily so builds/boots never need it). AAD binds each ciphertext to `(userId, connectionId)` — rows can't be transplanted, even by SQL. The crypto module is importable only from `lib/data` (ESLint fence); reads return a `SecretString` whose `toJSON` throws — call `.expose()` only where the value is spent. Disconnect hard-deletes the credential row and tombstones the connection (`status='disconnected'`); the app role has no DELETE on `connections` and column-scoped UPDATE only (`status`,`updated_at`; 2.1.3 adds `backfill_status`,`sync_cursor`). The api harness generates an ephemeral keyring per run (CI stays zero-secret); production needs the var set before 2.1.1 ships (docs/production.md).
- Plaid connect (leaf 2.1.1): `POST /api/plaid/link-token` mints a Link token (products `['transactions']` only, 730-day history consent, no redirect_uri — web OAuth uses Plaid's popup flow) and the Accounts-page Connect button (react-plaid-link) opens Link; `POST /api/plaid/exchange` validates `{publicToken}` at the boundary, exchanges it, vaults the access token via `createConnection`, then registers the item's accounts + initial balances from `/accounts/get` (server truth — Link metadata is never trusted). Balances are stored as Plaid reports them (credit/loan `current` positive = owed, matching the seeded dataset); transaction-sign negation is 2.1.3's. Duplicate item (same `provider_item_id`) → `/item/remove` the fresh token, 409. The `plaid` package and `lib/plaid/*` are ESLint-fenced to `lib/data` — raw Plaid client errors embed the API secret in `error.config.headers`, so `lib/plaid/client.ts` rethrows sanitized domain errors and nothing else may touch the SDK. Both POST routes reject cross-origin browser requests (no CSRF protection on route handlers otherwise). Env: `PLAID_CLIENT_ID`/`PLAID_SECRET`/`PLAID_ENV` (+ a real `CREDENTIAL_ENCRYPTION_KEYS`) — read lazily; the api suite needs none of them (vitest aliases `plaid` to `tests/harness/plaid.ts`, same pattern as Clerk: sandbox-shaped fixtures, single-use public tokens, loud throws elsewhere). Real-sandbox coverage lives in `e2e/plaid.signed-in.spec.ts` (headless `/sandbox/public_token/create` → exchange; Link UI is never driven per Plaid's own testing guidance), skipped when `PLAID_*` is unset; CI's e2e job carries sandbox-only repo secrets and generates an ephemeral e2e keyring per run.
- Sync engine (leaves 2.1.3 + 2.1.4): `lib/data/plaid-sync.ts` `advanceSync` pages Plaid `/transactions/sync` from the stored cursor (500/page, ≤20 provider calls per run — the budget spans mutation restarts, ≤2 restarts from the run's origin cursor) and applies `added` (insert-or-ignore), `modified` (upsert — an unseen id inserts), and `removed` (delete, pendings included; the leftover-pending linkage is 3.2.1's) in one transaction with `sync_cursor` + `backfill_status`. The cursor UPDATE runs first as a compare-and-set (`is not distinct from` the read cursor) — 0 rows = a concurrent run won; commit nothing, report zeros. Idempotent on `(account_id, source, source_id)`; sign convention lands at ingestion (Plaid positive = money out, negated into net-worth); provider rows with no usable currency fall back to the account's registered currency, never hard-coded USD. One malformed or unregistered-account row never poisons a run: it's skipped, counted in the response `skipped`, and logged (`lib/log.ts` one-line JSON events: ids, counts, error classes — never payloads, tokens, or amounts; `plaid_sync.run` / `run_failed` / `lost_race` / `update_status_unknown` / `balance_refresh_failed`). `RATE_LIMIT_EXCEEDED` → 429 + `Retry-After` (clients wait and retry); `TRANSACTIONS_UPDATE_STATUS_UNKNOWN` keeps `in_progress` honestly (never fakes complete) and heals via retriggers. Balances refresh through `/accounts/balance/get` (the endpoint that pulls live from the institution; 30-day `min_last_updated_datetime` floor for the Capital One quirk) only on drained runs that changed rows or flipped status — failures log and never fail the sync. Triggers: connect-button polls `POST /api/connections/:id/sync` to completion; `listResumableSyncs` + the accounts-page `SyncResume` component silently resume any `in_progress` connection older than a 2-min grace and re-sync any active connection idle >6h (`updated_at` is the freshness marker — only sync commits and disconnect touch it), so interrupted imports self-heal on the next visit; overlapping triggers are safe by the CAS. A global cron sweep is impossible by design — the app role can't enumerate users' connections under RLS; triggers run as the signed-in user (webhooks, 2.1.4 PR 2, map item→owner server-side). Grants: the app role's `transactions` surface is INSERT + column-scoped UPDATE (`amount_minor,currency,date,description,merchant,status,updated_at` — identity/provenance columns immutable) + DELETE, all RLS-scoped (migrations 0010/0011).
- The middleware file is `proxy.ts` (Next 16 renamed `middleware.ts`); it is an optimistic gate only — every protected page and route handler re-checks `auth()` itself (CVE-2025-29927 lesson).
- API tests (leaf 10.2, `apps/web/tests/`): `pnpm test:api` — Vitest calls route handlers and `lib/data` functions in-process against real Postgres through the runtime's own RLS chain (`cashlens_app` role, `withRequestScope`). Per run, `tests/harness/global-setup.ts` migrates a template database (`cashlens_test_template`); each worker clones it as `cashlens_test_<pool id>` and every test starts truncated, so cross-user isolation tests cost a few lines (patterns in `tests/api/`). Clerk is the one substituted external: `vitest.config.mts` aliases `@clerk/nextjs/server` to `tests/harness/clerk.ts` — signed-out by default, `withAuth(clerkUserId, fn)` scopes a signed-in user — so the suite needs no Clerk keys and no network; real-Clerk coverage stays in e2e. Fresh-process-per-file isolation is load-bearing (`DATABASE_URL` is read lazily once per process; `tests/api/health-down.test.ts` depends on it).
- CI (leaf 10.1; `api` job added in 10.2): `.github/workflows/ci.yml` runs `lint-typecheck`, `api` (the vitest suite above against a service-container Postgres — zero secrets, so it runs on fork PRs too), and `e2e` (production build + the full Playwright suite against a real Postgres 16 — service container in CI, compose locally — and the real Clerk dev instance) on every PR and on `main`; all three are required status checks, so red blocks merge. The e2e job runs in the pinned `mcr.microsoft.com/playwright` image (keep its tag in lockstep with `@playwright/test`) so no apt/CDN sits on the hot path. The repo is public — Actions logs and artifacts are world-readable: `e2e/scrub-secrets.ts` (Playwright `globalTeardown`) strips Clerk tokens from `test-results/`, and CI refuses to upload artifacts without its `.scrubbed` stamp; never enable `DEBUG=pw:api` and never assert with `toBeOK()` (lint-enforced), both print live session cookies into logs.
- Production (leaf 1.3, runbook + go-live checklist: `docs/production.md`): **Vercel** (project `cashlens`, root directory `apps/web`) deploys `main` only — `apps/web/vercel.json` skips non-production builds until leaf 10.6 and builds with `pnpm deploy:build`, which applies committed migrations as `cashlens_owner` (gated on `VERCEL_ENV=production`, direct URL) before `next build`, so a failed migration fails the deploy. Database is **Neon** (direct account, never Marketplace; same two-role model; runtime `DATABASE_URL` uses the `-pooler` host, owner/superuser URLs stay direct; all prod URLs pin `?sslmode=verify-full`). NEVER create roles in a provider console — console roles silently get `BYPASSRLS` (neondatabase/neon#12926); `pnpm db:setup` is the only role source and fails closed on `rolbypassrls`. `GET /api/health` reports app+db (200/503, public). DB fail-fast budgets: 5s connect / 20s client query / 15s statement / 30s idle-in-transaction (role-level).

## Testing policy (non-negotiable)

Tests exist to catch regressions in behavior users care about — not to demonstrate that code was written.

**Write tests at the seams:**

- Most coverage: API-level tests hitting real endpoints with a real local database.
- A few real-browser end-to-end tests for the money paths: sign in → connect → transactions appear → cash-flow numbers are right.
- Unit tests only where real logic lives — transfer matching, dedup, splits math, recurring detection, rules. Those deserve exhaustive cases.

**Banned (fake tests):**

- NEVER mock code this repo owns. Mock only true externals (Plaid, Gmail, the LLM) — behind the same interface production uses, with realistic sandbox/recorded fixtures.
- No render-without-crashing, element-is-visible, or snapshot-only tests. Every test asserts a behavior or a number.
- No sleeps to fix flaky tests — fix the race. No skipping or quarantining a test to get green.
- Don't test the framework (routing resolves, ORM persists). Test what this codebase decided.

**Determinism:** tests run against the seeded fixture dataset (known users, accounts, transactions with known totals) and a frozen clock, so assertions are exact — `true_spend == 1234.56`, never `> 0`.

**Prove the test works:** a new test must fail when the behavior it guards is broken. If you never saw it red, you don't know that it tests anything.

## Definition of done — every leaf, before claiming complete

1. Lint, typecheck, and the FULL test suite pass locally — paste the output, don't assert it.
2. Run the actual app and exercise the feature once as a user would.
3. New behavior has tests per the policy above. If you had to edit existing assertions, explain why in the PR.
4. Security rules hold — including the isolation test wherever user data is touched.
5. CI is green on the PR.
